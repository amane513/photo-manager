# 0006 決定記録

## 2026-09-11: 主HDDへの転送にrsync over SSHを使う

### 決定

- SDまたはMacの `PhotoWork` からUbuntuの主HDDへの転送にrsync over SSHを使う。
- rsyncデーモンは導入せず、構築済みのSSH接続を使う。
- 取り込みCLIはSMBマウントに依存させない。
- SMB共有は廃止せず、Amazon Photos Desktopからのバックアップと、必要時のFinder・現像ツールからの参照に使う。

### 理由

- 日常の取り込みからSMBのマウント、再接続、マウント位置への依存を外せる。
- SSH接続は構築済みであり、rsync用の別サービスや追加ポートを設ける必要がない。
- 転送の中断と異常終了をCLIから扱いやすく、ローカルの中間コピーを作らない通常経路を維持できる。
- Amazon Photos Desktopは主HDDをMacから参照する必要があるため、SMB自体を廃止すると構成全体は簡素にならない。

### 設計上の制約

- 撮影年月の分類、対応ファイルの組管理、同名候補の内容一致判定はrsyncに任せず、共通処理APIが転送計画を作る。
- 転送先は設定したSSHホストの `/mnt/camera_archive/` 以下に限定する。転送前にホスト、マウント元UUID、書き込み可否を確認する。
- コピー元削除、削除同期、インプレース書き込みは使わず、`--ignore-existing` を最後の上書き防止として使う。`--ignore-existing` によるスキップを内容一致とはみなさない。
- MacとUbuntuのrsyncの差異を実機で確認し、両方で確認したオプションだけを使う。

### 未決定事項

- 実際に使うrsyncオプションと一時ファイルの扱い
- ファイル数が多い場合のバッチ分割方法
- rsync出力と終了コードを構造化結果へ対応づける方法
- 既存同名ファイルの確認とチェックサム比較をMac側・Ubuntu側のどちらで行うか

## 2026-09-11: 実行環境はプロジェクト専用venvとrsync 3系に統一する

### 決定

- コピーCLIはPython 3.10以上を対象とし、プロジェクト専用の仮想環境（venv）へ導入する。
- macOSの送信側rsyncはHomebrewで導入するrsync 3系を使う。2026-09-11時点では3.5.0を確認した。Ubuntuの受信側はapt標準パッケージを使い、3.5.0へ更新しない。実機では3.2.7を確認し、3.2.6を互換性の下限とする。
- CLIは実行時にrsyncの実行ファイルとバージョンを検査し、使用した値を詳細ログへ記録する。転送オプションはmacOS 3.5.0とUbuntu 3.2.6の両方で使えるものに限定する。
- rsyncの導入・更新はdotfilesリポジトリで管理する。photo-managerには検査方法と、このCLIの導入・設定だけを置く。

### 理由

- macOS同梱のopenrsync 2.6.9へ合わせると、利用できる安全機能と実装選択が不必要に制限される。一方、UbuntuはOS標準パッケージの3.2.6を維持する。
- Pythonと依存ライブラリをOS環境から分離し、再構築時の導入内容を明示できる。
- rsync自体の管理責務をdotfilesに分離しながら、CLIが想定外の実行ファイルで動くことを防げる。

## 2026-09-11: 保存先はフラット化し、撮影日時をファイル名の先頭に付ける

### 決定

- SDカード内の `DCIM/` や `PRIVATE/` のサブフォルダは保存先へ持ち込まない。コピー先の `camera/` または `smartphone/` 直下へ配置する。
- ファイル名は、撮影日時のローカル時刻を `YYYYMMDD-HHMMSS_` として原名の前に付ける。原名と拡張子は保持する。
- RAW/JPEG/XMP、HEIC/MOVなど同じ撮影に属するファイルには同一の日時プレフィックスを付ける。
- 撮影日時を取得できないファイルは、推測で改名・配置せず未処理として結果とログへ記録する。
- 異なるファイルが同じ配置先名になった場合、自動的な連番付与や改名は行わず衝突として報告する。

### 理由

- 保存先のフォルダ構成を年月・機器別の2段階に保ち、SDカード固有の構成を日常の閲覧へ持ち込まない。
- 原名を残したまま日時を加えることで、人間が識別しやすく、カード交換や連番リセットによる同名衝突を減らせる。
- 未知の日時や衝突に対して推測・自動改名を行わず、安全性を優先する。

## 2026-09-11: ExifToolを撮影日時取得の共通実行環境とする

### 決定

- ARW、JPEG、HEIC、MOV、MP4、XMPの撮影日時取得にはExifToolを使う。
- ExifToolはphoto-managerの構築対象とし、MacとUbuntuの導入・検査手順を本リポジトリで管理する。
- CLIはExifToolのJSON出力を読み、写真では `DateTimeOriginal`、動画では `MediaCreateDate` を優先して日時を決める。後続候補として `CreateDate`、`TrackCreateDate` を使う。
- QuickTimeのUTC記録はExifToolの `QuickTimeUTC=1` を使い、実行ホストのローカル時刻へ変換してプレフィックスにする。

### 理由

- 対象形式に対して個別のPythonライブラリを組み合わせるより、取得規則を一つに統一できる。
- 外部コマンドとしてバージョンと出力を検査でき、Python仮想環境とは別に再構築できる。

## 2026-09-11: 基準不能な組ファイルはコピーせず未処理として記録する

### 決定

- SonyのRAW/JPEG/XMPはARWを、iPhoneのHEIC/MOVはHEICを撮影日時の基準ファイルとする。
- 基準ファイルがある組は、基準ファイルの撮影日時を組の全ファイルに適用する。
- 基準ファイルがない、または基準ファイルから日時を取得できない組は、保存先へコピーしない。コピー元は変更せず、組の全ファイルを未処理として要約と詳細ログへ記録する。
- 組に属さない対応形式のファイルは、そのファイル自身の日時を使う。未対応の形式も黙って除外せず、未処理として記録する。

### 理由

組を別の日時・月へ分断したり、日時を推測して改名したりすることを避ける。コピー元を保持して例外を明示するため、データを削除したり見失ったりしない。

## 2026-09-12: 配置の決め方を `--layout` で明示し、両モードで入力の形を検査する

### 決定

- 計画層に2つのモードを設け、`--layout classify|preserve` で明示する。既定は `classify` とする。自動判定は行わない。

  | モード | 振る舞い | 用途 |
  |---|---|---|
  | `classify` | 撮影日時を読み、組を判定し、`--year-month` と `--device` で分類して `YYYYMMDD-HHMMSS_` を付けて改名する | 経路a、経路b、イメージキャプチャで取得した未整理フォルダ |
  | `preserve` | コピー元からの相対配置をそのまま配置先へ写す。日時を読まず、組を判定せず、改名しない | 経路c |

- `preserve` では `--year-month` と `--device` が意味を持たないため受け付けない。指定された場合は実行不能（終了コード2）とする。
- `preserve` では ExifTool を呼ばない。組の基準ファイルの規則も適用しない。
- モードの取り違えを両方向とも入力の形で検出し、未処理として報告する。

  | 取り違え | 検出条件 |
  |---|---|
  | 配置済みのツリーを `classify` で処理する | 原名が `^[0-9]{8}-[0-9]{6}_` で始まる |
  | 未整理のフォルダを `preserve` で処理する | コピー元からの相対パスが `YYYY/YYYY-MM/{camera,smartphone}/名前` のちょうど4階層でない |

- `preserve` の形の検査では、年フォルダと月フォルダの年が一致しないもの、月が01〜12でないもの、機器名が `camera` と `smartphone` 以外のもの、5階層以上の深さにあるもの、シンボリックリンクを未処理とする。
- `preserve` では拡張子による絞り込みを行わない。形の検査を通ったファイルは拡張子を問わず転送する。
- OSが作る雑多ファイルは `excluded` として未処理と区別し、両モード共通で扱う。対象は `.DS_Store`、`._` で始まるファイル、`.Spotlight-V100`、`.Trashes`、`.fseventsd`、`Thumbs.db` とする。要約には件数を出し、詳細ログには全件を残す。`excluded` は利用者の対応を必要としないため終了コードに影響させない。
- `--source` は常に相対配置の基準となるルートとし、送る範囲は `--only` で相対パスの部分木として指定する。`--only` は繰り返し指定でき、両モードで有効とする。絶対パスや `..` を含む指定は実行不能とする。
- `preserve` と `--transport local` の組み合わせを許可する。隔離した試験先での確認に使う。
- どちらのモードでも、配置先が `--destination-root` の配下に収まることを確認する。

### 理由

経路cのコピー元である `PhotoWork` には、由来の異なる2種類が入る。経路bでこのCLI自身が配置したツリーは既に最終形であり再分類してはならない。一方、イメージキャプチャでiPhoneから取得したフォルダは未整理であり分類が要る。同じフォルダを指しても必要な処理が正反対になるため、コピー元の位置からモードを決められない。

自動判定を採らないのは、整理済みと未整理が混在する場合に判定が崩れるうえ、「推測で動かず例外として報告する」という本プランの方針と正反対になるためである。

サブコマンドを分けずフラグにしたのは、維持側に適切な名前がないことによる。`mirror` や `sync` は削除同期を連想させ、このCLIが行わない操作を想起させる。

形の検査を両モードに置くのは、モードの指定を誤った場合に安全機構が何も働かないためである。`classify` に配置済みのツリーを渡すと、日時プレフィックスが二重に付き、`--year-month` と `--device` が全ファイルへ一律適用される。配置先の名前は新しくなるので上書き禁止の衝突判定にも掛からず、壊れた配置がそのまま主HDDへ積まれる。`^[0-9]{8}-[0-9]{6}_` はSonyの `DSC00001.ARW` にもiPhoneの `IMG_0001.HEIC` にも一致しないため、誤検出の余地が小さい。

`preserve` で拡張子を絞らないのは、`classify` の絞り込みが撮影日時を読む必要から来ており、日時を読まない `preserve` では技術的な根拠がないためである。形の検査を通った時点でそのファイルは利用者が意図した位置にあり、拡張子で弾くとアーカイブの中身が現像ツールの出力形式に左右される。TIFF書き出しやDNGが主HDDへ届かなくなることを避ける。

`--source` をルートに固定するのは、`preserve` の配置先がコピー元からの相対パスで決まるためである。部分木を `--source` に渡せるようにすると相対パスの基準が曖昧になり、基準を別の引数で与える方式は片方の指定漏れが全件未処理を招く。

### 設計上の制約

- `preserve` で同じ範囲を2回実行すると、送信済みのファイルはすべて衝突として報告される。内容一致によるスキップは第2段階であるため、それまでは `--only` で範囲を絞って使う。

## 2026-09-12: 転送層をプロトコルとして分離し、共通処理を転送方式非依存にする

### 決定

- 転送層を `Transfer` プロトコルとして定義し、`preflight()`、`existing(destinations)`、`ensure_directories(directories)`、`send(source, destination)` の4操作だけを公開する。
- `service.execute_copy` は転送方式を知らず、上記4操作と2種類の例外（個別失敗の `TransferFailed`、継続不能の `TransferAborted`）だけを扱う。
- モジュール構成は次のとおりとする。

  | モジュール | 責務 |
  |---|---|
  | `transfer.py` | `Transfer` プロトコル、`TransferFailed`、`TransferAborted`、`TransferUnavailable` |
  | `local.py` | `LocalTransfer`。既存の `copy_file` をプロトコルへ適合させる |
  | `rsync.py` | `RsyncSshTransfer` |
  | `hosts.py` | `scripts/hosts/*.env` の読み込みと検証 |
  | `service.py` | 計画・衝突判定・結果生成のみ。転送方式に依存しない |

- `service.execute_copy` の処理順を次に固定する。

  1. `build_plan` で全ファイルの配置先を決める。
  2. `preflight()` を実行する。失敗した場合は1件も転送せず実行不能とする。
  3. 入力内で同じ配置先名になる項目を衝突にする。
  4. `existing()` の結果に含まれる配置先を衝突にする。
  5. dry-runの場合はここで結果を返す。`ensure_directories()` と `send()` は呼ばない。
  6. `ensure_directories()` で必要な親ディレクトリを作る。
  7. 1件ずつ `send()` する。`TransferFailed` は失敗として継続し、`TransferAborted` は残りを「転送中断のため未処理」として打ち切る。

### 理由

現在の `service.execute_copy` は `Path.exists()` とローカルコピーを直接呼んでおり、リモートの配置先に対してMac側のファイルシステムを検査してしまう。既存判定を転送層へ移すことで、保存先の実体を知っている側だけが存在確認と書き込みを行う。

dry-runで `preflight()` と `existing()` まで実行するのは、保存先を変更せずに接続先・マウント・衝突を確認できるようにするためである。

## 2026-09-12: rsync over SSHはファイルごとに呼び出し、SSH接続を多重化する

### 決定

- 共通処理が決めた1組の「コピー元・配置先」ごとに `rsync` を1回呼ぶ。複数ファイルをまとめて1回のrsyncへ渡す方式は採らない。
- SSH接続はOpenSSHのControlMasterで多重化する。`ControlPath` は `/tmp/photo-copy-<uid>/cm-%C`（パーミッション0700）とし、UNIXドメインソケットのパス長上限を避けるために一時ディレクトリの既定値は使わない。接続は `preflight()` で確立し、実行終了時に `ssh -O exit` で破棄する。
- ファイル数が多い場合のバッチ分割は行わない。既存判定は宛先一覧を標準入力へ渡す1回のSSHで済ませる。

### 理由

2026-09-12にMacと `ubuntu`（192.168.11.17）の間で実測した値は次のとおりである。

| 項目 | 実測値 |
|---|---|
| SSHハンドシェイク（多重化なし） | 0.36秒/回 |
| SSHハンドシェイク（ControlMaster多重化） | 0.035秒/回 |
| rsyncをファイルごとに呼ぶ（多重化あり） | 0.148秒/ファイル |
| rsyncをファイルごとに呼ぶ（多重化なし） | 0.434秒/ファイル |
| rsyncを一括で呼ぶ | 0.0034秒/ファイル |
| 実効転送速度 | 5.8 MB/s（素のSSHパイプは6.6 MB/s） |

ファイルごとの呼び出しと一括呼び出しの固定費の差は、1000ファイルあたり約2.4分でありファイルサイズに依存しない。ARW 25MBを1000枚（25GB）転送する場合の総時間は76.5分に対して74.1分であり、差は3%である。この代償で、どのファイルがコピー済み・衝突・失敗かをrsyncの終了コードから1件ずつ確定でき、`--ignore-existing` も1件ずつ適用できる。

一括転送はファイルごとに配置先名を変えられないため、最終名のシンボリックリンクを並べた中間ディレクトリを作って `rsync -L --files-from` で送ることになる。中間ディレクトリという可動部が増えるうえ、終了コードが全体で1つしか得られず、個別失敗と継続不能な失敗の区別がitemize出力の解釈に依存する。プランは両者の区別を最小版の要件としているため、この弱まり方を受け入れない。

多重化しない場合の固定費は1000ファイルで7.2分になるため、ControlMasterは前提とする。

## 2026-09-12: rsyncのオプションと終了コードを構造化結果へ対応づける

### 決定

- 転送は次の形で実行する。

  ```text
  rsync --times --itemize-changes --ignore-existing --timeout=300 \
    -e "ssh -o BatchMode=yes -o ConnectTimeout=10 -o ControlPath=<socket>" \
    -- <コピー元> <ユーザー>@<ホスト>:<配置先>
  ```

- `-a`、`--delete`、`--remove-source-files`、`--inplace`、`--partial`、`-z` は使わない。`-a` は所有者・グループの保存にリモートのroot権限を要求し、写真保存アカウントでの受信と噛み合わない。
- `-s`（`--secluded-args`、3.2.3以前の名称は `--protect-args`）は渡さない。rsync 3.2.4以降は引数保護が既定であり、下限として決めた3.2.6とmacOS側の3.5.0の双方で成立する。名称が版で変わるオプションを明示しない。
- 一時ファイルはrsyncの既定（配置先ディレクトリ内の `.<名前>.XXXXXX`）に任せる。`--partial` を使わないため、失敗・中断したファイルの一時ファイルは残らず、最終名の完成ファイルも生じない。再実行時は未転送のファイルとして再送される。
- 1回の `send()` の結果を次のとおり対応づける。

  | rsyncの結果 | 構造化結果 |
  |---|---|
  | 終了コード0、itemize行あり | コピー済み |
  | 終了コード0、出力なし | 衝突（`--ignore-existing` によるスキップ。内容一致とはみなさない） |
  | 終了コード23、24 | 失敗。以降のファイルは継続する |
  | 上記以外（1、2、3、10〜14、21、22、30、35、255など） | 中断。残りのファイルを未処理にして打ち切る |

- `preflight()` は1回のSSHでリモートの検査をまとめて行う。検査スクリプトは標準入力から与え、設定値は位置引数として渡す。リモートのシェルへ値を埋め込む場合は `shlex.quote` を通す。
  - 接続ユーザーが `ARCHIVE_OWNER` と一致する。
  - `ARCHIVE_MOUNT` がマウントされている。
  - `findmnt -n -o UUID --target` の値が `PRIMARY_STORAGE_UUID` と一致する。
  - 保存先ルートが `ARCHIVE_MOUNT` 配下にあり、書き込める。
  - リモートのrsyncが3.2.6以上である。
  - Mac側のrsyncが3.2.4以上である。
- `existing()` は1回のSSHで判定する。宛先をNUL区切りで標準入力へ渡し、リモートの `bash -s` が存在するものだけをNUL区切りで返す。改行またはNULを含む配置先名は計画の段階で未処理にし、リモートへ渡さない。
- `ensure_directories()` は1回のSSHで `mkdir -p` する。dry-runでは呼ばない。

### 理由

2026-09-12の実測で、保存先ディレクトリが存在しない場合は終了コード3、コピー元が読めない場合は終了コード23になることを確認した。既存ファイルを `--ignore-existing` でスキップした場合は終了コード0かつ出力が空になるため、終了コードだけではコピー済みと区別できない。itemize行の有無を併用してはじめて「転送した」と「存在したので触らなかった」を分離できる。

接続やマウントに起因する失敗を中断として扱うのは、保存先が失われた状態で残りのファイルを送り続けても成功しないためである。`BatchMode=yes` は鍵が使えない場合にパスワード入力待ちで固まることを防ぐ。`--timeout=300` は転送中の切断を検出する。

### 未決定事項

- 内容一致によるスキップのためのチェックサム比較をMac側・Ubuntu側のどちらで行うかは、第2段階で決める。最小版ではリモートでの存在確認だけを行い、`--ignore-existing` によるスキップは衝突として報告する。

## 2026-09-12: 転送先の設定は `scripts/hosts/*.env` を正本とする

### 決定

ホスト固有の値を `scripts/hosts/*.env` へ分離するのはリポジトリ全体の方針であり、同じUUIDやマウント先を2箇所で管理すると再構築時にずれる。設定形式を増やさないことで、`docs/setup/` の手順もホスト設定ファイル1つを起点にできる。

保存先を `ARCHIVE_MOUNT` 配下に限定する検査をMac側だけで行わないのは、Mac側の検査は設定値の妥当性しか見られず、実際にその位置へ主HDDがマウントされているかはリモートでしか確認できないためである。

## 2026-09-12: 転送の中断は部分完了として扱う

### 決定

- 終了コードは3分類を保つ。0は正常終了、1は部分完了、2は実行不能とする。
- 転送が途中で継続不能になった場合は、すでに転送したファイルがあるため部分完了（1）とする。`preflight()` の失敗は1件も転送していないため実行不能（2）とする。
- 中断した場合は、構造化結果とJSONログに `aborted` と中断理由を記録し、画面の要約にも中断した旨とrsyncの終了コードを表示する。
- 中断時点で未着手のファイルは未処理として、理由とともに記録する。

### 理由

プランは「正常終了、部分完了、実行不能」の3つを終了コードで表すとしている。中断は一部が完了した状態であり、部分完了に含めるのが自然である。終了コードを増やさずに `aborted` を結果へ持たせることで、中断と通常の部分完了を後続の処理からも区別できる。

## 2026-09-12: 撮影日時は基準ファイルだけを一括で読み、妥当性を検査する

### 決定

- 撮影日時を読むのは、組の基準ファイルと、組に属さない単独の対応形式ファイルだけとする。組の非基準メンバー（JPEG、XMP、MOVなど）に対してExifToolを呼ばない。
- ExifToolの呼び出しはファイルごとではなく一括にする。`metadata.py` に `capture_timestamps(paths) -> dict[Path, str | None]` を設け、`exiftool -@ -` で対象パスを標準入力から渡す。引数長の上限に依存しない。1件だけを読む `capture_timestamp` は一括版の薄い包みにする。
- タグの優先順位は `DateTimeOriginal` → `MediaCreateDate` → `CreateDate` → `TrackCreateDate` の順で固定し、形式ごとに分岐しない。写真にはMediaCreateDateが無く、動画にはDateTimeOriginalが無いため、この一つの順序で「写真はDateTimeOriginal、動画はMediaCreateDate」を満たす。
- QuickTimeのUTC記録は引き続き `-api QuickTimeUTC=1` で変換する。変換に使うタイムゾーンはExifTool実行時の環境変数 `TZ` で決まるため、CLIは `TZ` を明示的に与えられるようにし、実際に使った値を詳細ログへ記録する。既定は実行ホストのタイムゾーンとする。
- 取得した日時が次の範囲に収まらない場合は、値を使わず未処理にする。理由には取得した日時そのものを含める。
  - 1990-01-01 00:00:00 以降
  - 実行時刻の翌日以前
- ExifToolの一括呼び出しが全体として失敗した場合は、個々のファイルを未処理にせず実行不能（終了コード2）とする。

### 理由

基準ファイルだけを読めば組の日時は確定する。ARW+JPEG+XMPの3点セットでは読む件数が3分の1になり、第2段階で `--year-month` を省略した自動分類を既定にすると全ファイルの日時が必要になるため、この削減が効く。ExifToolはプロセス起動の固定費が大きく、1000件規模の取り込みでは一括呼び出しとの差が分単位になる。

日時の妥当性検査を入れるのは、電池切れでカメラの時計がリセットされた場合に、実在しない年月のフォルダが主HDDへ作られるためである。検出後は推測で補正せず、`--year-month` を明示した再実行へ回す。これは「推測で動かず例外として報告する」方針と一致する。

`TZ` を記録可能にするのは、同じMOVでも実行ホストのタイムゾーンが変わると配置先名が変わり、再実行で重複が生じるためである。固定値を採るかどうかは代表メディアの確認後に決める。

### 未決定事項

- 動画の `TZ` を固定値にするか、実行ホストに任せるかは、代表的なMOV・MP4を確認してから決める。
  → 2026-09-12（実データ確認）の決定で解消した。固定値 `Asia/Tokyo` を既定とする。
- ARW、HEIC、MOV、XMPの実データでタグの並びが想定どおりかは実機で確認する。
  → 2026-09-12にARW・JPG・MP4の実データで確認した（`validation.md` 参照）。HEIC・MOV（iPhone由来）・
  XMPは0007（イメージキャプチャでの取り込み手順の再現）で確認する。

## 2026-09-12: `--year-month` の省略で撮影年月へ自動分類し、指定時は食い違いを検出する

### 決定

- `layout=classify` の `--year-month` を省略可能にする。省略した場合は、組の基準日時から `YYYY/YYYY-MM/<機器>/` を1件ずつ決める。1回の実行で複数の年月へ分かれてよい。
- `--year-month` を指定した場合は、その年月を「この範囲はすべてこの月である」という利用者の主張として扱い、次のとおり分岐する。

  | 撮影日時 | `--year-month` 省略 | `--year-month` 指定 |
  |---|---|---|
  | 取得でき、年月が指定と一致 | 撮影年月へ配置。日時プレフィックスを付ける | 指定年月へ配置。日時プレフィックスを付ける |
  | 取得できるが、年月が指定と異なる | （該当しない） | 未処理。取得した年月を理由に記録する |
  | 取得できない | 未処理。「`--year-month` を指定して再実行する」を理由に記録する | 指定年月へ配置。日時プレフィックスは付けず原名のままにする |

- 組の扱いは基準ファイルの日時だけで決める。年月の判定も一致検査も基準ファイルに対して行い、結果を組の全メンバーへ適用する。
- `--device` は `layout=classify` で必須のまま残す。ExifToolのMakeやModelから機器種別を推測しない。1回の実行で扱う機器種別は1つとする。

### 理由

日常の取り込みでは、SDカードが月をまたぐことも、イメージキャプチャで取得したフォルダが複数月にわたることも普通に起きる。第1段階の `--year-month` 必須は、この場合に利用者が月ごとに `--only` を組み替える運用を強いる。自動分類を既定にすることで、正常系はコマンド1回で終わる。

`--year-month` を残すのは、日時不明のファイルを利用者の明示で配置するためである。このとき指定年月を無条件に全件へ適用すると、自動分類済みのツリーに対して誤って全範囲を指定した場合に、正しい月のファイルが別の月へ複製される。日時が取得でき年月が食い違うファイルを未処理にすれば、この誤りは転送前に検出できる。指定年月と一致するファイルを黙って通すのは、利用者の主張とファイルの記録が一致しているためである。

日時不明のファイルへ日時プレフィックスを付けないのは、`--year-month` が月までしか与えず、日と時刻を補えないためである。`YYYYMM00-000000_` のような値を作ると、存在しない日時が名前として残る。原名のままにすれば、そのファイルだけ日時が不明であることが保存先で見て分かる。

### 設計上の制約

- 日時プレフィックスを持たないファイルは、`classify` の取り違え検出（`^[0-9]{8}-[0-9]{6}_`）に掛からない。配置済みのツリーを誤って `classify` へ渡した場合、同じツリー内の他のファイルは検出されるため実行全体としては例外が報告されるが、この種のファイル単独では検出できない。
- `--year-month` の指定は、日時不明分を配置する目的に限る。手順書には `--only` で対象を絞ったうえで指定する形を正本として書く。

## 2026-09-12: 組の基準ファイルの優先順位を拡張する

### 決定

- 組の基準ファイルは、組内の対応形式から次の優先順位で一意に選ぶ。

  `.arw` > `.heic` > `.jpg` / `.jpeg` > `.mov` > `.mp4`

- `.xmp` は基準にしない。サイドカーであり、現像ツールが内容を書き換えるためである。
- 選ばれた基準ファイルから日時を取得できない場合、次の候補へ繰り下げない。組の全メンバーを未処理にする。
- 組に対応形式が1件も無い場合は、従来どおり全メンバーを未処理にする。

### 理由

2026-09-11の決定はARWとHEICだけを基準としていたため、JPEGとXMPだけの組（現像ツールが書き出したJPEGにサイドカーが付いた場合）や、Live Photoでない単独のMOVを含む組が、日時を取得できるにもかかわらず一律に未処理になる。優先順位を一意に決めておけば、基準が1件に定まる性質は変わらず、組が別の月へ分断されることもない。

繰り下げを行わないのは、繰り下げると「どのファイルの日時が採用されたか」が入力ごとに変わり、再実行時の配置先名が安定しないためである。基準から日時を取れない組は、`--year-month` を明示した再実行で扱う。

## 2026-09-12: 内容一致の判定はサイズとSHA-256で行い、ハッシュは各側で計算する

### 決定

- 転送層のプロトコルを次のとおり変更する。

  | 操作 | 変更 |
  |---|---|
  | `preflight()` | 変更なし |
  | `facts(destinations)` | `existing()` を置き換える。配置先ごとに、存在するかと通常ファイルのサイズを返す |
  | `digest(destinations)` | 追加。配置先のSHA-256を返す |
  | `ensure_directories(directories)` | 変更なし |
  | `send(source, destination)` | 変更なし |

- コピー元のSHA-256はMac側で計算する。`digest.py` に `file_digest(path)` を置き、`service.execute_copy` へ差し替え可能な形で注入する。配置先のSHA-256は保存先を持つ側が計算する。ネットワークを通るのはハッシュ値だけとする。
- 判定の順序を次に固定する。サイズが異なる時点で衝突とし、ハッシュを計算しない。

  | 配置先の状態 | 判定 |
  |---|---|
  | 存在しない | 転送する |
  | 通常ファイルでないものが存在する | 衝突（「同名のファイル以外が存在する」） |
  | 存在し、サイズが異なる | 衝突（「同名で内容が異なる」） |
  | 存在し、サイズが同じでハッシュが一致 | スキップ |
  | 存在し、サイズが同じでハッシュが異なる | 衝突（「同名で内容が異なる」） |
  | コピー元のハッシュを計算できない | 失敗。そのファイルは転送しない |

- `ItemStatus` に `skipped` を追加する。スキップは利用者の対応を必要としないため、`excluded` と同じく終了コードに影響させない。要約と詳細ログには件数と対象を出す。
- 衝突時の改名は引き続き自動化しない。
- リモートの `facts()` と `digest()` は、それぞれ1回のSSHで済ませる。配置先をNUL区切りで標準入力へ渡し、`値\0パス\0` の並びで受け取る。改行やNULを含む配置先名を計画の段階で未処理にする既存の規則をそのまま使う。
- rsyncの `--ignore-existing` は最後の上書き防止として残す。事前判定の後に同名ファイルが現れて `send()` が `EXISTING` を返した場合は、内容一致とみなさず衝突として報告する。理由には転送直前に現れたことを記録する。

### `service.execute_copy` の処理順（2026-09-12の転送層分離の決定を改訂）

第2段階以降は次の順を正本とする。ステップ4が `existing()` から `facts()`・`digest()` の2段階へ変わる点だけが、転送層分離のときの決定との差である。

1. `build_plan` で全ファイルの配置先を決める。
2. `preflight()` を実行する。失敗した場合は1件も転送せず実行不能とする。
3. 入力内で同じ配置先名になる項目を衝突にする。
4. `facts()` で配置先の存在とサイズを取得し、サイズが同じものだけ `digest()` とコピー元のハッシュを比較して、スキップと衝突を確定する。
5. dry-runの場合はここで結果を返す。`ensure_directories()` と `send()` は呼ばない。スキップと衝突はdry-runでも確定する。
6. `ensure_directories()` で必要な親ディレクトリを作る。
7. 1件ずつ `send()` する。`TransferFailed` は失敗として継続し、`TransferAborted` は残りを「転送中断のため未処理」として打ち切る。

画面の要約には `copied`、`planned`、`skipped`、`conflict`、`failed`、`unresolved`、`excluded` の件数を出す。終了コードは `conflict`、`failed`、`unresolved` のいずれかが1件以上あれば部分完了（1）とし、`skipped` と `excluded` は影響させない。

### 理由

2026-09-11に未決定としていた「チェックサム比較をMac側・Ubuntu側のどちらで行うか」は、両側で計算して値だけを突き合わせる形に決めた。片側へ寄せるとファイル本体をネットワークへ流すことになり、比較のためだけに転送と同じ時間が掛かる。

サイズ比較を先に置くのは、内容が異なる場合の大半をハッシュ計算なしで判定できるためである。2026-09-12の実測で実効転送速度は5.8 MB/sであり、主HDDの読み出しはこれより十分速い。既存ファイルのハッシュ計算は、同じファイルを送り直すより常に安い。

`skipped` を新設して終了コードから外すのは、再実行の正常系を成功にするためである。第1段階では、送信済みの範囲をもう一度実行するとすべて衝突となり終了コード1になる。この状態では「本当に確認が要る衝突」と「単に送信済み」を要約から区別できない。

### 設計上の制約

- 2026-09-12に記録した「`preserve` で同じ範囲を2回実行すると全件が衝突になる」制約は、この変更で解消する。
- 既存ファイルが多い範囲を再実行すると、リモートでのハッシュ計算に主HDDの読み出し時間が掛かる。実機確認で所要時間を計測し、`validation.md` へ記録する。

## 2026-09-12: 再実行は内容一致の判定だけで成立させ、一時ファイルの掃除は行わない

### 決定

- 部分失敗、中断、一時ファイル残存の後の再実行は、同じコマンドをもう一度実行する形とする。前回のログを読み直す `--resume` は設けない。
- 再実行時、コピー済みのファイルは内容一致でスキップし、未完了のファイルだけを転送する。失敗したファイルは再度転送を試みる。
- 残存した一時ファイルを検出・削除する機能はCLIに設けない。次を満たすことだけを保証する。
  - ローカル転送の一時名は `.<配置先名>.photo-copy-<乱数>.part` とし、最終名にはしない。
  - rsyncは `--partial` を使わないため、失敗・中断時に一時ファイルを残さない。
  - いずれの一時ファイルも `.` 始まりであり、対応形式の拡張子で終わらないため、次回以降の計画にも衝突判定にも影響しない。
- 実行の中断は引き続き部分完了（終了コード1）とし、`aborted` と中断理由を結果へ残す。

### 理由

内容一致によるスキップが入ると、再実行の安全性は「前回どこまで進んだか」を記録しなくても保存先の実体から判定できる。状態ファイルを持たないほうが、途中で電源が落ちた場合や別の端末から実行した場合にも正しく動く。

一時ファイルの掃除を入れないのは、これが安全性ではなく容量の問題であり、削除は本来避けたい操作だからである。photo-copyが作ったと確定できない一時ファイルを消す機能は、誤って他の処理の途中結果を消す危険のほうが大きい。必要が生じた場合は別プランで扱う。

## 2026-09-12: 定型設定は明示指定するプロファイルとし、実行ごとの判断は含めない

### 決定

- 定型値はプロファイル設定ファイルへ置く。形式はINI（`configparser`）とし、`[profile.<名前>]` のセクションで複数のプロファイルを持つ。Python 3.10には `tomllib` が無いため、標準ライブラリだけで読めるINIを採る。
- 既定の場所は `~/.config/photo-copy/profiles.ini` とし、`--profile-config FILE` で変更できる。
- プロファイルは `--profile <名前>` を指定したときだけ読む。既定プロファイルの暗黙適用は行わない。指定した名前が無い場合は実行不能（終了コード2）とする。
- 優先順位は「コマンドライン引数 > プロファイル > CLIの既定値」とする。
- プロファイルに書ける項目は次に限る。ここに無いキーが現れた場合は、誤字を黙って無視せず実行不能とする。

  | キー | 対応する引数 |
  |---|---|
  | `source` | `--source` |
  | `destination-root` | `--destination-root` |
  | `transport` | `--transport` |
  | `host-config` | `--host-config` |
  | `layout` | `--layout` |
  | `device` | `--device` |
  | `only` | `--only`（複数行で複数指定） |
  | `log-dir` | `--log-dir` |
  | `timezone` | ExifToolへ与える `TZ` |

- `year-month` と `dry-run` はプロファイルに書けない。どちらも実行ごとに判断すべき値であり、設定へ固定すると誤った年月を繰り返し適用したり、通常実行をdry-runと取り違えたりする。
- 相対パスは、プロファイル設定ファイルの位置ではなくカレントディレクトリを基準に解釈する。コマンドライン引数と同じ解釈にそろえる。
- 適用したプロファイル名と、解決後の全項目を詳細ログへ記録する。`--dry-run` の要約にも解決後のコピー元・配置先ルート・配置モード・機器種別を表示し、実行前に確認できるようにする。

### 理由

日常の取り込みで繰り返し入力するのは、コピー元、配置先ルート、転送方式、ホスト設定、機器種別である。これらは経路ごとにほぼ固定であり、毎回手で入力すると打ち間違いの機会が増える。

暗黙適用を避けるのは、設定ファイルの存在によってコマンドの意味が変わる状態を作らないためである。`--profile` を書いた実行だけが設定の影響を受けるなら、手順書のコマンドをそのまま貼っても結果が変わらない。

ホスト固有の値（UUID、マウント先、SSH接続先）は引き続き `scripts/hosts/*.env` を正本とし、プロファイルにはそのファイルの場所だけを書く。同じ値を2箇所で管理しない方針を崩さない。

## 2026-09-12: 動画のTZは固定値（Asia/Tokyo）とする

### 決定

- ExifToolのQuickTimeUTC変換に使う `TZ` は、`--timezone` またはプロファイルの `timezone` で明示しない場合、実行ホストの環境設定ではなく固定値 `Asia/Tokyo`（+09:00）とする。
- `metadata.resolve_timezone` 自体は汎用関数のまま変更しない。明示指定が無い場合に実行ホストのタイムゾーンへ解決する既存の動作は、ライブラリとしての一般的な既定として残す。CLI層（`cli.py`）が `capture_timestamps` へ渡す `tz` の既定値を `None` から `"Asia/Tokyo"`（`DEFAULT_TIMEZONE`）へ変更することで固定する。
- 撮影地でその場のタイムゾーンを配置先名へ反映したい場合は、引き続き `--timezone` またはプロファイルの `timezone` で明示的に上書きできる。この決定はその上書き手段を変更しない。
- 2026-09-11の決定「既定は実行ホストのタイムゾーンとする」は、この決定により「既定は固定値 `Asia/Tokyo` とする」へ置き換える。

### 理由

実機のSony α7C IIのMP4（`C0006.MP4`）で確認した。QuickTimeの生の記録は常にUTC（`03:21:04`、オフセット情報なし）であり、`-api QuickTimeUTC=1` による変換結果は与える `TZ` によって次のように変わることを確認した。

| `TZ` | 変換結果 |
|---|---|
| 未指定（実行ホスト、Asia/Tokyo相当） | 12:21:04+09:00 |
| `Asia/Tokyo` | 12:21:04+09:00 |
| `UTC` | 03:21:04+00:00 |
| `America/Los_Angeles` | 前日20:21:04-07:00 |

同じSDカードのARW/JPGでは `ExifIFD:DateTimeOriginal` が撮影時点のローカル時刻を、`OffsetTimeOriginal`（`+09:00`）とともに直接記録しており、実行環境のTZに依存しない。動画だけが実行環境のTZに依存する既定は、次の理由で採らない。

1. 内容一致によるスキップは配置先名が同じであることが前提である。`TZ` が実行環境（Macのシステム設定）に依存すると、同じ物理ファイルを異なるTZ設定の端末や、TZ設定が変わった後の同じ端末から再実行した場合に動画だけ配置先名が変わり、内容一致判定が効かないまま重複して転送される。
2. 実際の運用は「撮影地でその場で取り込む」より「帰宅後にまとめて取り込む」方が多い。この場合、実行ホストのTZは常に拠点（日本）であり、「実行ホストに任せる」設計は海外での撮影を正しく変換する目的を達成できない。
3. ARW/JPGは常にローカル時刻をEXIFへ直接記録するため実行環境に依存しないのに対し、動画だけ実行環境に依存する既定は、Live Photoなど組の中では基準ファイル選択（`.heic` が `.mov` より優先）によって偶然吸収されているに過ぎず、単独の動画（Live Photoでない単独のMOV/MP4）では吸収されない。

固定値を `Asia/Tokyo` とするのは、主HDDと日常の運用が日本国内であることによる。異なる地域での撮影を配置先名に正確に反映したい場合は、既存の `--timezone`/プロファイルの明示指定で対応する。

### 設計上の制約

- `docs/setup/mac.md` の手順書には、固定値を明示的に上書きしたい場合の `--timezone` の使い方を追記する（実機確認後、setup更新の作業でまとめて行う）。
