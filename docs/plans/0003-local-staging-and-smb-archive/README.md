# ローカル作業領域とSMB経由アーカイブへの運用変更

- Status: Draft
- Created: 2026-08-23
- Updated: 2026-08-23
- Exit criteria: 前提作業（P1・P2）の完了、未決事項（U1）の確定、仕様4文書とADRの改訂、`photo-backup` の実装とテスト通過、実機での受け入れ完了

この文書は方針だけを記述する。詳細な実装手順、モジュール分割、テスト設計は、P1・P2・U1が片付いた後に別途起こす。

## 0. 目的と背景

現行の運用は「SDカード → 外付けHDD（Mac直結）」の一段構成である。これを次の二段構成へ変更する。

1. SDカードからMacのローカルディスクへ取り込む
2. ローカルで不要カットの削除と現像を行う
3. 確定した内容をHDDへバックアップする

HDDはデスクトップのUbuntuへ接続し、SMBでMacから見えるようにする。この構成にする理由は、Mac上でファイル整理を終えてからバックアップしたいこと、および将来Ubuntu機をimmichで写真サーバー化したいことである。写真サーバー化そのものは本計画の対象外とする。

## 1. 新しい運用フロー

| 段階 | 実行するもの | 内容 |
|---|---|---|
| A | `photo-import` | SDカード → ローカル作業領域。撮影日時による命名と `YYYY/YYYY-MM/` への振り分けは現行どおり |
| B | 人手（Lightroom等） | セレクト削除と現像。ローカル作業領域の内容が増減する |
| C | `photo-backup`（新規） | ローカル作業領域 → HDD（SMB経由）。追記のみ |
| D | `photo-verify` | HDD上のビット腐敗検出。Aとは独立した頻度で実行する |

段階Aの完了時点ではコピーは1つしかない。SDカードの保持期間に関する運用指示を、現行の「取り込み成功後にカメラでフォーマット」から**「段階Cの成功まではカードを保持する」**へ改める。

## 2. 確定した方針

### D1. 台帳の正本はHDDのみに置く

`checksums.tsv` の第一の存在意義は、長期保管媒体上のビット腐敗を「正しかった時点のハッシュ」と照合して検出することにある。ローカル作業領域は段階Bで中身が変わり続ける前提なので、そこに台帳を置けば必ず破綻する。

帰結として、`photo-import` のeject判定条件を「台帳に全件記録済み」から**「全対象のコピーとハッシュ一致の確認に成功」**へ変更する。ローカル側には台帳を作らず、実行ログに結果を残すにとどめる。

### D2. 現像成果物は同じフォルダにsuffix付きで置く

```text
Camera/2026/2026-08/20260818_192925_DSC00001.ARW       ← 元
Camera/2026/2026-08/20260818_192925_DSC00001.JPG       ← 元
Camera/2026/2026-08/20260818_192925_DSC00001_edit.JPG  ← 現像成果物
```

日付フォルダ構成と `YYYYMMDD_HHMMSS_` 前置の命名規則をそのまま使えるため、撮影日時をファイル名から復元でき、`verify.py` のスコープ判定（`subdir/YYYY/YYYY-MM/ファイル` の3階層を前提とする）も無改修で通る。別ツリー（`Edited/` 等）にすると役割ディレクトリの概念拡張が必要になり、config・verify・backupへ広く波及する。Amazon Photosの対象設定も変更せずに済む。

**suffixは必ずファイル名の末尾に付ける。** `transfer.py` の一時ファイル名検証が `^\d{8}_\d{6}_.+\.part$` を要求するため、先頭の `YYYYMMDD_HHMMSS_` を崩す命名は採らない。

### D3. HDDは追記のみとし、削除を伝播しない

ローカルで削除した写真をHDDから消すことはしない。セレクトはHDDへ渡す前に済ませる運用とする。これにより photo-manager に破壊的操作を導入せず、「上書きしない・削除しない」という現行の安全原則をそのまま維持できる。

### D4. HDDへの書き込みはMacからSMB越しにphoto-managerが行う

Ubuntu側に転送・検証の実装を置かない。ただし段階Dの `photo-verify` 相当については、Ubuntu側でローカル実行する形を併用する（D6）。

### D5. ボリューム同定の仕組みを差し替える

現行の Volume UUID 照合（`diskutil info -plist`）は、ローカル作業領域とSMB共有のどちらでも使えない。実測で、非マウントポイントのパス（`~/Pictures`）に対して `diskutil info` はエラーを返すことを確認済みである。SMBマウントにはそもそも VolumeUUID が存在しない。

同定手段をマーカーファイル方式へ差し替える。加えて、**SMB未マウント時に `/Volumes/<share>` が空ディレクトリとして残り、Macの内蔵SSDへ書き込んでしまう事故**を構造的に防ぐことを要件とする。現行のUUID照合が担っていた「宛先を取り違えない」保証の代替であり、この計画で最も慎重に設計すべき箇所である。

### D6. 検証は「無駄な重複」を削り、総量を絞る

現行が重い検証を行っている根本理由は、SD→HDD直結でカードをフォーマットすればコピーが1つしか残らなかったことにある。新運用では段階Cの後も元がローカルに残るため（D3により消さない）、**「検証はコピーと同時に完了させねばならない」という制約が外れる**。総検証量を減らしても、システム全体の冗長性はむしろ上がる（最悪ケースが1コピーから2コピーへ）。

詳細は次節。

## 3. 現行設計で成立しなくなる前提

| 現行の前提 | 成立しなくなる理由 |
|---|---|
| 台帳＝アーカイブの完全な内容。未登録ファイルは失敗 | 段階Bで現像成果物が増える。`verify.py:_scan_unregistered` と `mirror.py:_source_records` が失敗する |
| 台帳の全レコードに実ファイルが存在する | 段階Bでセレクト削除が起きる。`mirror.py:_source_records` の「source ledger file is missing」で mirror が起動しない |
| 宛先はVolume UUIDで同定できる | D5のとおり |

したがって **`photo-mirror` は段階Cに転用できず、`photo-backup` を新設する**。`mirror.py` は廃止するか、将来の2台目HDD用に残置するかを実装時に決める。

## 4. 検証方針

### 現行の検証レイヤ

コピー1ファイルあたり、現行は元を1回・宛先を2回読んでいる。

| # | 検証 | コスト | 守っているもの | 方針 |
|---|---|---|---|---|
| L1 | コピー中の元ストリーミングhash | 0 | 比較の材料 | 残す |
| L2 | コピー前後の元 stat 比較 | 0 | コピー中に元が変わる事故 | 残す |
| L3 | `.part` の書き戻しhash（`F_NOCACHE`） | 宛先1回読み | 書き込み経路の破損 | 条件付きで残す（下記） |
| L4 | `_verify_records` の最終再hash | 宛先もう1回読み | L3〜eject判定の間の変化 | **stat比較へ置換** |
| L5 | 重複判定での既存宛先hash | 再実行時の宛先読み | 同名別内容の取り違え | **台帳digestの再利用へ置換** |
| L6 | mirrorの元アーカイブ全hash | 元全読み | 元が台帳通りである保証 | **`photo-backup` に持ち込まない** |
| L7 | mirrorの宛先全hash × 2回 | 宛先全読み × 2 | 公開前後の二重確認 | **`photo-backup` に持ち込まない** |
| L8 | `photo-verify` の全件再hash | 全読み | ビット腐敗 | 残す（頻度と実行場所で制御） |

L4は `digests.measure()` を呼んでおり、これはキャッシュを参照せず必ず再読み込みする（`src/photo_manager/naming.py:139`）。呼び出しは `src/photo_manager/importer.py:168`。宛先を2回読むのは意図的な設計である。

### なぜ削るのか

1GbEのSMB実効を110MB/sとすると、32GBの転送は次のようになる。

| 内容 | 所要 |
|---|---|
| コピーのみ | 4.9分 |
| ＋L3 | +4.9分 |
| ＋L4 | +4.9分 |
| 現行方式のまま | **約15分**（実効36MB/s） |

より深刻なのはL6・L7である。アーカイブが1TBに育つと、mirror方式をそのまま移植した場合、**毎回のバックアップで宛先を2回フルスキャンして5.4時間**かかる。運用不能であり、L6・L7の廃止は選択ではなく必須とする。`photo-backup` は最初から差分前提（HDD台帳とsize/mtimeで既転送分をスキップ）で設計する。

### 採用する方針

**L4とL5を軽量化し、L6とL7を持ち込まない。** これにより32GBあたり約15分が約10分になり、全件スキャンが消える。`_verify_records` は単純化され、実装量はむしろ減る。

**L3は `--no-verify-on-copy` 相当のオプションで外せるようにする。** 外した場合、32GBあたり約5分（実効110MB/s、ネットワーク上限）まで落ちる。判断材料はP2の `F_NOCACHE` 実測結果である。SMB上で `F_NOCACHE` が効かないなら、読み戻しているのはクライアントキャッシュであってHDD上のバイトではなく、L3に払うコストが対価に見合わない。

**L3を外す場合、台帳の意味が一段変わる点をADRに残す。** 追記時のdigestは「ローカル側で確認した正しい値」であって「HDD上で確認した値」ではなくなり、初回の `photo-verify` を通って初めて確定する。運用として、バックアップ直後に該当月だけ検証する手順（`photo-verify --month YYYY-MM`）を組み込む。

### 検証しないもの

- **ハッシュアルゴリズムは `sha256` のまま変更しない。** Apple SiliconはSHA-256をハードウェア支援し1.5〜2GB/s出る。律速はSMBの110MB/sなので、blake3等へ変えても速くならない。
- **size/mtimeだけの検証（ハッシュを捨てる方式）は採らない。** ビット腐敗を検出できず、長期保管という目的に反する。size/mtimeは「既に転送済みか」の差分判定にのみ使い、データの正しさはハッシュで担保する、という役割分担を維持する。

### 検証の実行場所

段階Dの全件検証は、**Ubuntu側でローカル実行する形を第一候補とする**。HDD直読み180MB/s程度でネットワークを使わないため、SMB越しの110MB/sより1.6〜2倍速く、MacとLANを占有しない。台帳はTSVなので `sha256sum -c` 形式へ変換すれば標準ツールで回せる。将来immichをUbuntuへ入れる方向とも整合する。Mac側の `photo-verify` は残し、両方を使えるようにする。

なお、ネットワークを2.5GbEにすると実効275MB/s程度となりHDD側が律速になるため、検証を削る動機自体が薄れる。コード変更を伴わない代替手段として記録しておく。

## 5. 着手前の前提作業

### P1. HDDをext4へ再フォーマットする

現在HDDはHFS+である。LinuxのHFS+書き込みは信頼性が低く、exFATにはhard linkが存在しない。Ubuntu側でSambaから書き込み可能に公開するにはext4とする。

**HDDは現在ほぼ空である（3.6TiB中2.9GiB使用、`_photo-manager/checksums.tsv` は未作成）。今なら移行コストが実質ゼロなので、運用開始前に必ず済ませる。**

### P2. SMBマウント上での実測

```sh
# hard link の可否（最重要）
touch /Volumes/<share>/a && ln /Volumes/<share>/a /Volumes/<share>/b

# flock の可否
python3 -c "import fcntl,os;fd=os.open('/Volumes/<share>/lock',os.O_RDWR|os.O_CREAT);fcntl.flock(fd,fcntl.LOCK_EX|fcntl.LOCK_NB)"

# F_NOCACHE の可否
python3 -c "import fcntl,os;fd=os.open('/Volumes/<share>/a',os.O_RDONLY);fcntl.fcntl(fd,fcntl.F_NOCACHE,1)"
```

- **hard linkが不可の場合が最悪ケースである。** 現行は「tmpへコピー → 検証 → `os.link` で正式化」とし、`os.link` が既存ファイルに必ず失敗する性質を上書き防止の構造的保証にしている（[`architecture.md`](../../architecture.md) の公開と永続化の不変条件1〜4）。代替は最終名へ `O_CREAT|O_EXCL` で直接書く方式となり、不変条件の書き換えとADR追加を伴う。見積もりの最大の分岐点。
- **flockが不可の場合**、ロックの扱いを決める必要がある。利用者は単一なので、ローカル側にロックファイルを置く方式への退避も選択肢になる。
- **`F_NOCACHE` の結果はL3を残すかどうかの判断材料**となる（第4節）。

## 6. 未決事項

### U1. XMPサイドカーの扱い

Lightroom等が生成する `20260818_192925_DSC00001.xmp` は、元ファイルと同じベース名を持ち、**現像設定を変えるたびに内容が変わる**。台帳は追記のみ・上書き禁止であるため、これを台帳管理下に置くと `photo-verify` が恒久的に失敗する状態になる。

次のいずれかを選ぶ。

1. バックアップ対象外とする
2. 台帳管理外のパターンとして明示的に除外し、データだけ置く
3. XMPを生成しない現像ワークフローにする

**この決定なしに仕様は書き起こせない。** 第7節の見積もりは選択肢1を前提としている。
