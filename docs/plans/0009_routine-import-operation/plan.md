# 0009: 日常の取り込み運用の確立

作成日: 2026-09-12

更新日: 2026-09-12

状態: 完了

## 目的

実運用規模の取り込みを一度通し、日常の取り込み手順を [docs/setup/mac.md](../../setup/mac.md) の正本として確定する。日常はプロファイルを指定してCLIを実行し、要約だけを見て終えられる状態を目指す（[proposal.md](../../proposal.md) 5.1）。あわせて、コピー元を削除してよいと判断するための確認条件を設計する。

## 範囲を絞った理由

[roadmap.md](../roadmap.md) では0009を「CLIでの両経路の通し確認」としていたが、0006と0007で両経路と例外処理は既に実機確認済みである。

- 経路a（SD → rsync over SSH → 主HDD）、経路b（SD → Mac `PhotoWork`）、経路c（`PhotoWork` → 主HDD、`--layout preserve`）は、いずれも0007で正規の配置先に対して実施済みである（[0007のvalidation.md](../0007_media-workflow-validation/validation.md)）。
- 衝突、中断、再実行、内容一致スキップ、`--only`、プロファイル、撮影日時の取得と日時不明の扱いは0006で実データ確認済みである（[0006のvalidation.md](../0006_copy-cli-foundation/validation.md)）。

これらを繰り返すと0007の焼き直しになるため、0009では未確認のまま残っている次の3点だけを扱う。フォルダ名も内容に合わせて `0009_routine-import-operation` とし、旧称 `0009_manual-archive-workflow` は使わない。

1. **規模**: 0006・0007の確認はいずれも10件以下である。SDカード1枚分をまとめて取り込んだときの所要時間と結果の見やすさは未確認である。[0006のdecisions.md](../0006_copy-cli-foundation/decisions.md) の未決定事項「ファイル数が多い場合のバッチ分割方法」もここでしか判断できない。現在の実装はrsync over SSHで1ファイルにつき1回rsyncを起動する（[src/photo_copy/rsync.py:286](../../../src/photo_copy/rsync.py#L286)）。SSH接続はControlMasterで多重化しているが、数百件規模での実測値はない。
2. **運用**: `docs/setup/mac.md` は現状CLIの使い方の説明であり、日常の流れとして固定されたプロファイルの実値がない。0014のGUIが前提とする「0009の操作が固まる」はこれを指す。
3. **コピー元整理**: 何を確認できたらSDカードやiPhoneのコピー元を消してよいかが未定である。

## 対象範囲と前提

- SDカード1枚分の未取り込み分を、経路a（SD → 主HDD）で一括して取り込む。選別はしない。件数は実際の撮影分に従い、事前に固定しない。
- 実行はプロファイル指定で行う。日常運用と同じ操作で通し、確認のための追加操作を挟まない。
- コピー元（SDカード・iPhone）は削除しない。0009では削除の判断条件と確認手順を定めるだけとする。0010で全件の欠損・内容一致を検証し、0013（第2 HDDへのバックアップ）の結果も条件に含めたうえで、0013の完了後に実際の削除を行う。
- 0008が完了し、0007のテストコピーが主HDDと `~/Pictures/PhotoWork/` の両方から削除済みであることを前提とする（0008の段階5）。
- 取り込み後に主HDDの内容を確認する方法は、CLIの要約と詳細ログを基本とする。全件の目視や件数の手書き転記は行わない。

## 範囲外

- 両経路の通し確認の再実施。0007の結果を再利用し、確認済みとして扱う。
- 全件の欠損・内容一致検証（0010）。0009では所要時間と例外の有無を記録するにとどめ、チェックサムによる全件照合は行わない。
- コピー元の実際の削除（0013の完了後）。
- バッチ分割やその他の性能改善の実装。0009では必要性の判断と方針の記録までとし、実装が必要なら別プランとして起票する。
- GUI（0014）、Amazon Photos（0008）、Immich（0011・0012）。

## 実施手順

結果は `validation.md` に記録する。CLIのログを再利用し、全件の手書き転記は行わない。

### 段階1: 開始状態を確認する

- [x] 0008の完了と、主HDD・`PhotoWork` にテストコピーが残っていないことを確認する。
- [x] `photo-copy check --host-config ./scripts/hosts/ubuntu-amane-yajima.env` が成功することを確認する。
- [x] 取り込み対象のSDカードの総件数・総容量と、内訳（ARW、JPEG、MP4）を記録する。

### 段階2: 実運用規模で一括取り込みする

- [x] `--dry-run` で対象件数と配置計画を確認する。要約が実運用規模でも読める形になっているかを見る。
- [x] 本実行し、開始・終了時刻、所要時間、コピー済み・スキップ・衝突・失敗・未処理・除外の件数を記録する。
- [x] 例外（衝突・失敗・未処理）があれば内容を確認して対応し、対応方法を記録する。日常運用で同じ例外が出たときにどうするかを手順として書けるようにする。
- [x] 同じコマンドを再実行し、2回目が内容一致スキップで短時間に終わることを確認する。再実行の所要時間も記録する。
- [x] 所要時間が実運用に耐えるかを判断する。耐えない場合は、1ファイル1回のrsync起動が支配的かをログから切り分け、バッチ分割などの改善方針と、それを別プランとするかを記録する。

### 段階3: 日常運用の手順を確定する

- [x] 経路ごとのプロファイル（SD→主HDD、iPhone取り込み後のPhotoWork→主HDDなど）の実値を確定し、`~/.config/photo-copy/profiles.ini` に設定する。
- [x] 確定した内容を [scripts/mac/profiles.ini.example](../../../scripts/mac/profiles.ini.example) へ反映する。秘密情報は含めない。
- [x] `docs/setup/mac.md` に日常の取り込み手順（SDを挿す、プロファイルを指定して実行する、要約を見る、例外だけ対応する）を追加する。どこまでが日常操作で、どこからが例外対応かを区別して書く。
- [x] dry-runを毎回行わない運用でよいことと、dry-runを使う場面（初回、設定変更、問題調査）を明記する。

### 段階4: コピー元削除の判断条件を設計する

- [x] SDカード・iPhoneのコピー元を削除してよいと判断するための確認項目を決める。主HDDへの保存と全件検証（0010）、第2 HDDへのバックアップ（0013）、写真のオフサイト保護が必要な場合のAmazon完了（0008）を、それぞれどう確認するかを具体的に書く。
- [x] 確認をどの手段で行うかを決める。CLIの要約とログで足りる範囲と、0010の全件検証で確認する範囲を分ける。
- [x] 上記を `docs/setup/mac.md` またはプラン内へ記載し、0010の全件検証結果と0013の第2 HDDバックアップ結果を条件へ組み込める形にする。
- [x] 0009では削除を実施しないことと、実施する時期（0013の完了後）を明記する。

### 段階5: 記録

- [x] 実測値（件数、容量、所要時間、例外）と判断を `validation.md` に記録する。
- [x] 0010・0013・0014へ渡す前提（確定したプロファイル、性能上の課題、削除条件の未確定部分）を明記する。
