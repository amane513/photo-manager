# 変更プラン

変更ごとに、次の形式でフォルダを追加する。

実施済みと今後予定しているプランの一覧、依存関係、着手順は、[roadmap.md](roadmap.md)を参照する。

```text
NNNN_short-description/
└── plan.md
```

例:

```text
0001_docs-refactor/
0002_initial-immich-setup/
0003_backup-workflow/
```

## 命名規則

- `NNNN` は0001からの4桁連番とし、推奨する着手順を表す。欠番は作らず、新規プランは末尾に採番する。
- 説明部分は、英小文字のkebab-caseを基本とする。
- 完了、保留などの状態はフォルダ名に含めず、`plan.md` に記録する。
- 推奨順が変わった場合は、ロードマップ全体を再採番する。フォルダ名、正本・他プランからの参照も同時に更新する。

## 基本構成

小さな変更は `plan.md` だけで完結させる。必要な場合に限り、次のファイルやフォルダを追加する。

- `decisions.md`: 実施中に生じた重要な判断
- `validation.md`: テストや検証の詳細
- `assets/`: 図、サンプル設定などの付属資料

完了したプランも、変更理由と判断を追跡できるよう削除せずに残す。

## 環境を変更するプラン

PCやHDD、ネットワーク、常駐サービスの設定を変更するプランは、次を成果物に含める。

- [../setup/](../setup/) の該当ホストの手順を、変更後の構成に合わせて更新する。
- 自動化した部分を [../../scripts/](../../scripts/) へ追加し、実機で実行して動作を確認する。
- 完了条件は可能な限り確認用スクリプトにし、再構築先で同じ状態になったことを判定できるようにする。

`plan.md` と `validation.md` は当時の記録であり、以後更新しない。新しいPCで環境を組み直すときは `setup/` と `scripts/` を参照する。実測値のうち再構築に必要なものは、`validation.md` に残すだけでなく `scripts/hosts/*.env` または手順書へ反映する。
