# 0006 決定記録

## 2026-09-11: 主HDDへの転送にrsync over SSHを使う

### 決定

- SDまたはMacの `PhotoWork` からUbuntuの主HDDへの転送にrsync over SSHを使う。
- rsyncデーモンは導入せず、構築済みのSSH接続を使う。
- 取り込みCLIはSMBマウントに依存させない。
- SMB共有は廃止せず、Amazon Photos Desktopからのバックアップと、必要時のFinder・現像ツールからの参照に使う。

### 理由

- 日常の取り込みからSMBのマウント、再接続、マウント位置への依存を外せる。
- SSH接続は構築済みであり、rsync用の別サービスや追加ポートを設ける必要がない。
- 転送の中断と異常終了をCLIから扱いやすく、ローカルの中間コピーを作らない通常経路を維持できる。
- Amazon Photos Desktopは主HDDをMacから参照する必要があるため、SMB自体を廃止すると構成全体は簡素にならない。

### 設計上の制約

- 撮影年月の分類、対応ファイルの組管理、同名候補の内容一致判定はrsyncに任せず、共通処理APIが転送計画を作る。
- 転送先は設定したSSHホストの `/mnt/camera_archive/` 以下に限定する。転送前にホスト、マウント元UUID、書き込み可否を確認する。
- コピー元削除、削除同期、インプレース書き込みは使わず、`--ignore-existing` を最後の上書き防止として使う。`--ignore-existing` によるスキップを内容一致とはみなさない。
- MacとUbuntuのrsyncの差異を実機で確認し、両方で確認したオプションだけを使う。

### 未決定事項

- 実際に使うrsyncオプションと一時ファイルの扱い
- ファイル数が多い場合のバッチ分割方法
- rsync出力と終了コードを構造化結果へ対応づける方法
- 既存同名ファイルの確認とチェックサム比較をMac側・Ubuntu側のどちらで行うか

## 2026-09-11: 実行環境はプロジェクト専用venvとrsync 3系に統一する

### 決定

- コピーCLIはPython 3.10以上を対象とし、プロジェクト専用の仮想環境（venv）へ導入する。
- macOSの送信側rsyncはHomebrewで導入するrsync 3系を使う。2026-09-11時点では3.5.0を確認した。Ubuntuの受信側はapt標準パッケージを使い、3.5.0へ更新しない。実機では3.2.7を確認し、3.2.6を互換性の下限とする。
- CLIは実行時にrsyncの実行ファイルとバージョンを検査し、使用した値を詳細ログへ記録する。転送オプションはmacOS 3.5.0とUbuntu 3.2.6の両方で使えるものに限定する。
- rsyncの導入・更新はdotfilesリポジトリで管理する。photo-managerには検査方法と、このCLIの導入・設定だけを置く。

### 理由

- macOS同梱のopenrsync 2.6.9へ合わせると、利用できる安全機能と実装選択が不必要に制限される。一方、UbuntuはOS標準パッケージの3.2.6を維持する。
- Pythonと依存ライブラリをOS環境から分離し、再構築時の導入内容を明示できる。
- rsync自体の管理責務をdotfilesに分離しながら、CLIが想定外の実行ファイルで動くことを防げる。

## 2026-09-11: 保存先はフラット化し、撮影日時をファイル名の先頭に付ける

### 決定

- SDカード内の `DCIM/` や `PRIVATE/` のサブフォルダは保存先へ持ち込まない。コピー先の `camera/` または `smartphone/` 直下へ配置する。
- ファイル名は、撮影日時のローカル時刻を `YYYYMMDD-HHMMSS_` として原名の前に付ける。原名と拡張子は保持する。
- RAW/JPEG/XMP、HEIC/MOVなど同じ撮影に属するファイルには同一の日時プレフィックスを付ける。
- 撮影日時を取得できないファイルは、推測で改名・配置せず未処理として結果とログへ記録する。
- 異なるファイルが同じ配置先名になった場合、自動的な連番付与や改名は行わず衝突として報告する。

### 理由

- 保存先のフォルダ構成を年月・機器別の2段階に保ち、SDカード固有の構成を日常の閲覧へ持ち込まない。
- 原名を残したまま日時を加えることで、人間が識別しやすく、カード交換や連番リセットによる同名衝突を減らせる。
- 未知の日時や衝突に対して推測・自動改名を行わず、安全性を優先する。

## 2026-09-11: ExifToolを撮影日時取得の共通実行環境とする

### 決定

- ARW、JPEG、HEIC、MOV、MP4、XMPの撮影日時取得にはExifToolを使う。
- ExifToolはphoto-managerの構築対象とし、MacとUbuntuの導入・検査手順を本リポジトリで管理する。
- CLIはExifToolのJSON出力を読み、写真では `DateTimeOriginal`、動画では `MediaCreateDate` を優先して日時を決める。後続候補として `CreateDate`、`TrackCreateDate` を使う。
- QuickTimeのUTC記録はExifToolの `QuickTimeUTC=1` を使い、実行ホストのローカル時刻へ変換してプレフィックスにする。

### 理由

- 対象形式に対して個別のPythonライブラリを組み合わせるより、取得規則を一つに統一できる。
- 外部コマンドとしてバージョンと出力を検査でき、Python仮想環境とは別に再構築できる。

## 2026-09-11: 基準不能な組ファイルはコピーせず未処理として記録する

### 決定

- SonyのRAW/JPEG/XMPはARWを、iPhoneのHEIC/MOVはHEICを撮影日時の基準ファイルとする。
- 基準ファイルがある組は、基準ファイルの撮影日時を組の全ファイルに適用する。
- 基準ファイルがない、または基準ファイルから日時を取得できない組は、保存先へコピーしない。コピー元は変更せず、組の全ファイルを未処理として要約と詳細ログへ記録する。
- 組に属さない対応形式のファイルは、そのファイル自身の日時を使う。未対応の形式も黙って除外せず、未処理として記録する。

### 理由

組を別の日時・月へ分断したり、日時を推測して改名したりすることを避ける。コピー元を保持して例外を明示するため、データを削除したり見失ったりしない。
