# コピーアプリケーションのアーキテクチャ

更新日: 2026-09-13

この文書は、`photo-copy`のCLIとmacOS GUIが共有するアプリケーション処理の境界と、利用者向け結果の意味を定める。変更プラン固有の作業記録ではなく、今後CLIまたはGUIを変更するときに維持する設計上の正本である。

## 1. 層と責務

依存方向は、GUI／CLIからアプリケーション層、コピー処理層、転送層への一方向とする。Qtをアプリケーション層以下へ持ち込まない。

| 層 | 主な責務 | 持たせない責務 |
|---|---|---|
| GUI | 画面状態、操作、Qtスレッドとシグナル、ログを開く操作 | プロファイル解決、転送生成、成功判定、ログ生成 |
| CLI | 引数解析、既存形式の標準出力、終了コードへの対応づけ | プロファイルから実行要求を組み立てる判断、転送生成、ログ生成 |
| アプリケーション層 | プロファイルと上書き値の解決、外部コマンド検出、転送の生成と終了処理、コピー処理の呼び出し、ログ保存、利用者向け結果判定、プロセス間排他 | Qt、標準出力、CLI引数解析、ファイルごとのコピー判断 |
| コピー処理層 | 配置計画、同一性判定、コピー、検証、構造化結果、進捗通知 | プロファイル、ログファイル、画面、終了コード |
| 転送層 | ローカルまたはrsync over SSHによる配置先操作 | 画面、プロファイル、全体の成功判定 |

現在`cli.py`にある`_resolve()`、`_load_profile_if_requested()`、`_request_from_parsed()`のうち引数オブジェクトに依存しない解決、`LocalTransfer`／`RsyncSshTransfer`の選択、`capture_timestamps`の準備、転送の`close()`、JSONログの組み立てと保存、結果判定をアプリケーション層へ移す。`argparse.Namespace`を共通APIへ渡してはならない。

## 2. アプリケーションAPI

アプリケーション層には次の概念を置く。具体的なモジュール名は`application.py`を既定とする。

- `RunRequest`: プロファイル名、プロファイル設定ファイル、CLIから明示された上書き値を保持する。GUIは許可された4プロファイルのいずれかだけを指定し、汎用設定値を組み立てない。
- `ResolvedRun`: `CopyRequest`、プロファイル名、ホスト設定パス、ログディレクトリ、タイムゾーン、解決済み外部コマンドを保持する。実行前表示にも使える読み取り専用の値とする。
- `RunOutcome`: `CopyExecutionResult`、`success`または`attention`の利用者向け分類、ログパス、開始・終了時刻、解決済み設定を保持する。
- `RunUnavailable`: 設定不正、必要な外部コマンドの欠如、転送の事前検査失敗、メタデータ取得不能など、コピーを開始または完了可能な状態にないことを表す。
- `resolve_run()`: プロファイルと上書き値を検証し、`ResolvedRun`を返す。リモート接続とコピーは行わない。
- `run_copy()`: 排他ロック取得からログ保存まで一つの利用者操作を実行し、`RunOutcome`を返す。転送の`close()`とロック解放は必ず`finally`で行う。

`success`は、現行CLIの終了コード0と同じく、コピーに衝突・失敗・保存対象の未処理・中断がなく、検証が成功した場合だけである。それ以外の構造化結果は`attention`とし、現行CLIの終了コード1に対応させる。`RunUnavailable`は終了コード2へ対応させる。予期しないプログラム不具合は`attention`へ丸めず、GUI側で「予期しないエラー」として捕捉し、CLIでは従来どおり例外を隠さない。

JSONログの`schema_version = 2`、既存キー、状態値の意味を維持する。CLIにある開始・終了時刻、プロファイル、ホスト設定、ログディレクトリ、タイムゾーン、rsyncバージョンの付加と保存をアプリケーション層へ移す。外部コマンドの絶対パスは新しい加算的なキーとして記録してよい。実行不能で`CopyExecutionResult`が存在しない場合は、互換性のないコピー結果ログを捏造しない。

## 3. 進捗通知

進捗は、戻り値とは別の同期コールバックで通知する。コールバックへQtの型を渡さず、コピー処理は通知先を知らない。通知が不要な既存呼び出しでは省略できるようにする。

`ProgressEvent`は少なくとも次を持つ。

- `phase`: 安定した列挙値
- `completed`: 完了数。件数を確定できない工程では`None`
- `total`: 総数。件数を確定できない工程では`None`
- `detail`: 診断用の短い補足。画面の主要な判定には使わない

工程は次の順序と意味に固定する。

| `phase` | 意味 | 進行値 |
|---|---|---|
| `preparing` | 設定解決、外部コマンド検出、排他取得 | 不定 |
| `planning` | コピー元の列挙、ExifToolによる日時取得、配置計画 | 不定。計画確定後に総数を通知する |
| `preflight` | ローカルまたはSSH転送先の事前検査 | 不定 |
| `comparing` | 既存候補のサイズ・SHA-256照合 | 処理対象数を取得できる場合だけ通知する |
| `copying` | ディレクトリ準備とファイル送信 | 各項目の確定後に完了数と総数を通知する |
| `verifying` | コピー後の全件検証とマニフェスト生成 | 各検証項目の確定後に完了数と総数を通知する |
| `finalizing` | 結果判定、JSONログ保存、後始末 | 不定 |

ExifTool、SSH先の一括ハッシュなど、外部コマンドが一括で処理する間は偽の割合を表示せず、不定進捗と現在工程を表示する。進捗通知のためにrsyncやハッシュ計算を細分化して性能を落とさない。進捗イベントは最終結果の正本ではなく、成功判定と件数表示は`RunOutcome`だけから行う。

コールバックは呼び出し元と同じワーカースレッドで同期実行される。短時間で戻り、コピー処理を呼び戻してはならない。段階2では、工程順、単調増加する完了数、通知を省略した既存呼び出しの互換性を自動テストする。

## 4. 多重実行と終了

GUI内では実行開始と同時に開始ボタンを無効にする。さらにGUI、CLI、別のGUIプロセスをまたいで重複しないよう、アプリケーション層が利用者単位の排他ロックを保持する。

- macOSの既定ロックファイルは`~/Library/Application Support/photo-copy/run.lock`とする。
- `fcntl.flock()`の非待機排他ロックを使う。ロックファイルが残っていても、プロセス終了時にカーネルがロックを解放するため、時刻によるstale判定は行わない。
- 初期版は経路ごとではなく全コピー操作を直列化する。別経路でも同時に保存先へ作用させない、安全側の制約である。
- ロック取得に失敗した場合は、転送を開始せず`RunUnavailable`にする。
- ロックパスはテスト時に一時ディレクトリへ注入できるようにする。

初期GUIにはキャンセル機能を設けない。実行中のウィンドウクローズ、Command-Q、Dockからの終了要求は、処理中であることを示して拒否する。Pythonのワーカースレッドを強制終了してはならない。OSの強制終了や電源断は防げないため、発生時はコピー元を保持して同じ操作を再実行する。既存の一時ファイル、上書き禁止、内容一致スキップがこの復旧経路を支える。

## 5. macOS GUI

GUIはQt Widgetsで実装し、単一ウィンドウとする。初期版では次の4プロファイルだけを選択できるようにし、任意のプロファイル名の入力や設定編集は設けない。

| 表示名 | プロファイル | 用途 |
|---|---|---|
| SDから主HDDへ | `sd-to-ubuntu` | 通常経路。起動時の既定値とする |
| SDからMacへ | `sd-to-mac` | 選別・現像のためPhotoWorkへ取り込む |
| Macから主HDDへ | `photowork-to-ubuntu` | PhotoWorkの既存配置を主HDDへ送る |
| iPhoneからMacへ | `iphone-to-photowork` | イメージキャプチャでPhoneImportInboxへ取得済みのファイルをPhotoWorkへ分類する |

iPhone本体から`PhoneImportInbox`への取得はGUIで行わず、引き続きイメージキャプチャを使う。通常経路は起動直後に選択済みとし、利用者は`取り込みを開始`だけで実行できる。別経路では選択後に実行内容を確認してから開始する。

画面には次だけを置く。

- 状態見出し: `実行前`、`実行中`、`正常完了`、`要確認`、`実行不能`を文字で示す。色だけで区別しない。
- プロファイル選択: 上記3経路を選ぶ。実行中は変更できないようにする。
- 実行内容: 選択したプロファイル名、コピー元、保存先、転送方式、配置モードを読み取り専用で示す。SSH転送では保存先を`user@host:配置先`として示す。
- 進捗: 現在工程、確定できる工程だけのプログレスバー、完了数／総数を示す。
- 結果: コピー済み、既存一致、衝突、失敗、保存対象の未処理と、検証の一致、欠損、不一致、読取不能、未解決を別のまとまりで示す。
- 操作: `取り込みを開始`と、結果がある場合の`詳細ログを開く`を置く。実行中は開始操作を無効にする。
- 安全表示: 結果にかかわらずコピー元を自動削除していないことを示す。正常完了以外では「コピー元を保持し、詳細ログを確認する」と明示する。

選択変更のたびに`resolve_run()`で表示内容を更新する。選択したプロファイルの解決失敗は`実行不能`として表示するが、別プロファイルへの選択変更は許可する。正常完了または要確認の後は同じ画面から再実行できる。ログを開く処理は`QDesktopServices`を使い、パスをシェルコマンドへ埋め込まない。

長時間処理は`QObject`のワーカーを専用`QThread`へ移して実行する。転送オブジェクトと外部コマンド呼び出しはワーカースレッド内で生成・破棄する。ワーカーは進捗、完了、実行不能、予期しない例外をQtシグナルでGUIスレッドへ渡し、ウィジェットはGUIスレッドだけから更新する。`QThread.terminate()`は使わない。

## 6. 設定と外部コマンド

GUIは`~/.config/photo-copy/profiles.ini`の`sd-to-ubuntu`、`sd-to-mac`、`photowork-to-ubuntu`、`iphone-to-photowork`を読む。Finderから起動したプロセスのカレントディレクトリを設定解決に使ってはならない。現行CLIとの互換性を保つため相対パスの意味は変更せず、GUIで使う4プロファイルの`source`、`destination-root`、`host-config`、`log-dir`は絶対パスにする。段階4のセットアップスクリプトが、プロジェクトルートの実パスを使ってGUI互換の設定を安全に生成または検査する。既存設定を無断で上書きしない。

GUIでプロファイルに`log-dir`がない場合は、カレントディレクトリへ書かず`~/Library/Logs/photo-copy`を上書き値として使う。CLIの既定`.photo-copy-logs`は互換性のため維持する。

Finder起動時の`PATH`はシェルと同じとは限らない。アプリケーション層は実行開始前に絶対パスを解決し、各外部コマンドへ注入する。macOSではApple Silicon Homebrewの`/opt/homebrew/bin`、Intel Homebrewの`/usr/local/bin`、システムの`/usr/bin`と受け取った`PATH`を候補にする。Homebrew側を先に探索してrsync 3系を選び、`ssh`、`rsync`、`exiftool`をすべて検査する。

このため、`capture_timestamps()`はExifTool実行ファイル、`RsyncSshTransfer`はrsyncとsshの実行ファイルをそれぞれ注入可能にする。テストでは実コマンドを呼ばず差し替える。転送前の既存バージョン下限検査は維持する。

## 7. 依存と`.app`の再構築

PySide6はCLIの通常依存に追加せず、`pyproject.toml`のGUI用optional dependencyとして正確なバージョンを固定する。GUIの構築には専用の`.venv-gui/`を使い、CLI用`.venv/`へ`pyside6-deploy`が追加する構築依存を混在させない。

初回実装ではPySide6 6.11.2 / Qt 6.11.2を採用する。公式の`pyside6-deploy`とリポジトリ管理下の`pysidedeploy.spec`を使い、診断しやすく起動時展開を避けるため`standalone`モードで`.app`を作る。PythonとQtはアプリへ含めるが、`ssh`、rsync、ExifTool、プロファイル、ホスト設定は外部に置き、起動時に検査する。

構築物はリポジトリへコミットせず、スクリプトで再生成する。ローカル利用だけを対象とし、第三者配布用のDeveloper ID署名、公証、DMG、Mac App Store対応は行わない。必要であれば構築後にad-hoc署名し、`codesign --verify`とFinder起動で検査する。構築・更新スクリプトはdry-runを持ち、既存の設定を無断で上書きしない。

## 8. 維持する互換性

- CLIのサブコマンド、引数、優先順位、標準出力の要約、終了コード0／1／2を維持する。
- JSONログのスキーマバージョン2と既存キー・状態値を維持する。
- `execute_copy()`の進捗通知は省略可能とし、既存利用者の戻り値を変えない。
- GUIとCLIの成功／要確認判定はアプリケーション層の同じ関数だけを使う。
- GUI追加を理由に上書き、削除同期、コピー元削除、強制キャンセルを追加しない。
