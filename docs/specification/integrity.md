# 整合性検証とミラー仕様

この文書はチェックサム台帳、`photo-verify`、`photo-mirror` の外部仕様を定める。台帳の厳密なレコード形式は [ADR 0002](../decisions/0002-checksum-ledger-format.md) を参照する。

## チェックサム台帳

主アーカイブごとに `<archive>/_photo-manager/checksums.tsv` を置く。台帳はデータと同じボリュームに置き、別のMacへ接続した場合や2台目HDDへ同期した場合もデータと一緒に移動できるようにする。

各レコードは次を保持する。

1. アーカイブルートからのPOSIX相対パス
2. ハッシュアルゴリズム
3. digest
4. バイトサイズ
5. 撮影日時
6. 取り込み日時

初期実装で受け付けるアルゴリズムは `sha256` のみとする。同一相対パスには正常なレコードを1件だけ持ち、同一内容の再取り込みで重複追記しない。

台帳は起動時に全行を検査する。末尾の書きかけレコードだけは、壊れた原本をホスト側ログディレクトリへ退避できた場合に限り、完全な行から台帳を再構築してアトミックに置換できる。途中の行の破損、構文不正、重複レコードは自動修復しない。

正式ファイルがあるのにレコードがない場合、SDカード上の元ファイルと正式ファイルの一致を確認できるimport時だけ補完できる。元ファイルがない状態で実ファイルの現在のハッシュを正しい値として自動採用してはならない。

## `photo-verify`

指定範囲について、台帳から実ファイルへ、実ファイルから台帳への両方向を検査する。

- 全レコードについてファイルの存在、サイズ、指定アルゴリズムのdigestを検証する。
- 欠落、サイズ不一致、digest不一致、重複レコード、台帳構文不正は失敗とする。
- 管理対象ツリーの正式ファイルにレコードがなければ「未登録」として失敗する。
- `_photo-manager/` は管理対象データの探索から除外する。
- 管理対象ツリーに残る旧形式または手動作成の `*.part` は自動削除せず、除外された残骸として警告する。
- その他の余分なファイルは警告する。

`--month YYYY-MM` と `--year YYYY` は、撮影日時欄ではなく `Camera/YYYY/YYYY-MM/` 形式の相対パスを対象範囲として選ぶ。両方を省略した場合は全件を検証する。

verifyはデータと台帳を変更しない。ただしimportやmirrorと競合しないよう、既存ロックファイルを使って共有ロックを取得する。安全にロックできない場合は、ロックなしで検証を続けず事前チェックエラーとする。

## `photo-mirror`

mirrorは主アーカイブから2台目HDDへの追加型・非破壊同期である。コピー元にない宛先ファイルの削除や、内容が異なる宛先ファイルの上書きは行わない。

処理順は次のとおり。

1. コピー元とコピー先のパス、Volume UUID、書込可否、hard link対応、容量を確認し、同一ボリュームなら中止する。
2. デッドロックを避ける一定の順序で両ボリュームをロックする。取得できなければデータを変更せず中止する。
3. コピー元台帳を構文検査し、転送対象となる全ファイルを台帳と照合する。欠落・未登録・不一致があればコピー先データを変更せず中止する。
4. コピー先にファイルがなければ、管理領域の一時ファイルへ排他的にコピーして再読込検証し、既存名を置換できない方法で正式化する。
5. コピー先に同名ファイルがあれば台帳と照合する。一致ならスキップし、不一致なら上書きせず失敗する。
6. コピー元にないコピー先ファイルは削除せず、余分なファイルとして警告する。
7. 全管理対象データをコピー先で検証してから、コピー元台帳のスナップショットを一時ファイルへ複写・検証し、管理ファイルに限ってアトミック置換する。
8. 台帳公開後、コピー元台帳の全管理対象がコピー先でも一致することを再検証する。

手順7の台帳公開前検証と手順8の公開後検証は異なる安全境界を守るため、同じデータを読む場合でも両方を実行する。

コピー元で破損したデータを正常なコピー先へ伝播させないことを優先する。競合時は両方のパス、期待値、実測値をログに記録し、修復は利用者の判断に委ねる。

## ログと障害時の原則

- 実行ログは `~/Library/Logs/photo-manager/` に置き、対象HDDが未接続でも確認可能にする。
- 台帳と管理用一時ファイルは `<archive>/_photo-manager/` に置く。
- 管理用一時ファイルの残骸は、対応する排他ロックを保持する変更処理だけが安全を確認して掃除できる。verifyは掃除しない。
- 管理ファイルのアトミック置換後に失敗した場合は、置換の成否を推測して新しいファイルを削除しない。
- いずれかの検証失敗、台帳不完全、競合があれば非ゼロで終了する。
