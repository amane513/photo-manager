# 0010: コピー時の全件自動検証

作成日: 2026-09-13

更新日: 2026-09-13

状態: 実装・正常系実機検証・隔離異常系検証完了。0013完了後のコピー元削除確認待ち

## 目的

`photo-copy copy` の一連の処理として、コピー元にある保存対象と主HDD上の配置結果を全件照合する。利用者は日常の取り込みコマンドを増やさず、コピー完了時に件数・総容量・ファイルごとのSHA-256一致まで確認できるようにする。

全件一致した取り込みには検証マニフェストを残し、「主HDDへ取り込み済み」と「内容検証済み」を同じ実行結果の中で区別する。この記録は0013の第2 HDDバックアップ完了と組み合わせ、コピー元を削除できる状態の判断に使う。

0009ではSDカード1枚から保存対象1,005件・27 GBを取り込み、同じコピーコマンドの再実行で内容一致を確認した。0010ではこの実データを使い、通常の取り込み1回でコピーと検証が完結する形を実装・確認する。0010完了後もコピー元は削除せず、実際の削除は0013完了後とする。

## 背景

- 現在の `photo-copy copy` は、同名の配置先が既にある場合だけサイズとSHA-256を比較する。新しくコピーしたファイルは転送成功を確認するが、配置後の全件ハッシュ検証は行わない。
- 0009の再実行では保存対象1,005件を約5分半かけて再度ハッシュ比較した。取り込み直後に独立した検証コマンドを毎回実行する方式では、操作が増えて実行忘れが起きうるうえ、コピー前に確認済みの既存ファイルを再計算する無駄がある。
- 写真は検証後にMacや主HDDで整理・削除することがある。検証は整理後のライブラリをコピー元と再比較する監査ではなく、「取り込み時点で全保存対象が正しく主HDDへ届いた」という証跡にする必要がある。
- 要件では全件検証をコピー処理の中核から分離し、後から導入できる設計を求めている。内部APIは分離したまま、CLIの1回の `copy` 操作からコピーと検証を連続実行する。

## 設計上の決定

### 1. `copy` が全件検証まで自動実行する

利用者が実行するコマンドは0009で確定したものから変えない。

```sh
.venv/bin/photo-copy copy --profile sd-to-ubuntu
```

通常実行の処理順を次にする。

```text
配置計画
  ↓
既存候補のサイズ・SHA-256比較
  ↓
未配置ファイルのコピー
  ↓
新規コピー分の配置後検証
  ↓
全対象の検証結果・マニフェスト生成
  ↓
コピー結果と検証結果の要約・JSONログ保存
```

`--dry-run` は従来どおり配置計画と既存候補の判定までを行い、コピーもコピー後検証も実行しない。dry-runを検証済みとして扱わず、マニフェストも生成しない。

独立した `photo-copy verify` コマンドは追加しない。コピー後の検証だけが失敗した場合も、同じ `copy` コマンドを再実行すれば、配置済みの全対象を内容一致として検証し直せるためである。全件検証を省略するオプションも設けない。

### 2. 内部ではコピーと検証を分離する

CLI操作は1コマンドにまとめるが、検証ロジックを転送処理へ埋め込まない。検証対象、ハッシュ結果、マニフェスト生成を扱う共通APIを設け、CLIの `copy` が転送処理の後に呼び出す。

これにより次を両立する。

- 日常操作は従来どおりプロファイル指定の `copy` だけで終わる。
- 将来のGUIは同じコピーAPIと検証APIを組み合わせて進捗・結果を表示できる。
- 0013は第2 HDDのバックアップ検証にマニフェスト生成規則を再利用できる。
- コピーの成否と検証の成否を結果モデル上で区別できる。

既存の `CopyResult` に検証結果を曖昧に混在させず、`VerificationResult` と、両者を束ねる実行結果を定義する。`copied` は転送が完了したこと、`matched` は配置後の内容検証が完了したことをそれぞれ表す。

### 3. コピーと同じ配置計画を検証対象の正本にする

検証対象と配置先の対応は、別のパス変換を実装せず `planning.build_plan()` の結果を使う。撮影日時、年月・機器、日時プレフィックス、組ファイル、`classify` / `preserve`、`--only` の意味をコピーと一致させる。

計画中に複数のコピー元が同じ配置先になる場合は、内容が同じでも検証不能とする。コピー時の配置先衝突判定を共通関数へ分離し、コピーと検証の双方で同じ結果を使う。

`classify` では、CLIが保存対象として対応する拡張子だけを全件検証の対象にする。Sonyの管理用XML・DBなど未対応形式は `not-targeted` として件数と理由をログに残すが、検証失敗にはしない。対応形式であるにもかかわらず撮影日時や配置先を決められないファイルは `unresolved` とし、検証失敗にする。判定が理由文字列に依存しないよう、現在の非公開 `_is_supported()` を公開の判定関数へ整理してコピーと検証で共有する。

`preserve` では、既存動作どおり、正しい4階層の配置にある通常ファイルを拡張子によらず対象とする。OSが作る雑多ファイルは両モードで `excluded` とし、失敗にはしない。

### 4. 既存一致の結果を再利用し、新規コピー分だけ配置後に読む

全件検証では対象ごとにコピー元と配置先のサイズ・SHA-256一致を必要とする。ただし、同じ実行内で既に確定した結果を捨てて全件を読み直さない。

- **既存ファイル**: コピー前の内容一致判定で得たコピー元サイズ・SHA-256と配置先サイズ・SHA-256を、そのまま検証成功結果として使う。
- **新規コピー**: 転送完了後に配置先の通常ファイル判定、サイズ、SHA-256を取得し、コピー元と比較する。コピー前にコピー元ハッシュを計算していない場合は、この段階で1回だけ計算する。
- **転送失敗・衝突・未処理**: 全件一致の前提を満たさないため検証成功にしない。存在する配置先を推測で採用しない。

これにより、初回取り込みでは新規コピー分だけを配置後に検証し、再実行ではコピー前の既存一致判定だけで全件検証を完了できる。ネットワークを通すのは配置先の事実とハッシュ値だけとし、比較のためにファイル本体をMacへ読み戻さない。

転送直後の配置先検証は対象パスをまとめて実行する。1ファイルごとにSSHを起動せず、NUL区切りの標準入力でパス一覧をUbuntuへ渡し、通常ファイル判定、サイズ、SHA-256を1回のSSH接続で取得する。

### 5. ファイル単位の状態と成功条件を固定する

| 状態 | 意味 | 全件検証への影響 |
|---|---|---|
| `matched` | 配置先が通常ファイルで、サイズとSHA-256が一致した | 成功 |
| `missing` | コピー済みとされた配置先が検証時に存在しない | 失敗 |
| `different` | 配置先のサイズまたはSHA-256がコピー元と異なる | 失敗 |
| `invalid-destination` | 同名のディレクトリやシンボリックリンクなどがある | 失敗 |
| `unreadable` | コピー元または配置先の事実・ハッシュを取得できない | 失敗 |
| `unresolved` | 対応形式だが配置先を決められない、入力内で配置先が衝突する、または転送結果が確定していない | 失敗 |
| `not-targeted` | `classify` で未対応の管理用形式など、保存対象外である | 対象外 |
| `excluded` | `.DS_Store`、`._*` などOSの雑多ファイルである | 対象外 |

サイズ一致だけを成功にせず、保存対象すべてのSHA-256一致を必須とする。対象件数、コピー元の総バイト数、`matched` の件数・総バイト数も集計し、全件一致の判定と要約に使う。

検証中にコピー元または配置先が変化した場合を成功扱いしない。ハッシュ計算の前後にサイズと更新時刻を取得し、変化したファイルを `unreadable` にする。SDカードへの撮影継続、PhotoWorkの編集、主HDD上の整理を、当該 `copy` コマンドの完了前には行わないことを手順へ明記する。

### 6. 主HDD上の余分なファイルと検証後の整理を許容する

全件検証は「今回のコピー元にある保存対象が、取り込み完了時点で主HDDに欠けず同一内容で存在したこと」を確認する。主HDDには過去の取り込み、別機器由来、現像済みJPEG、XMPなどが共存し、不要データの残存も要件上許容している。このため、対象ディレクトリにコピー元由来でないファイルがあっても列挙・失敗扱いにしない。

検証成功後にMacまたは主HDDで写真を整理・削除してよい。後日のライブラリが取り込み時のマニフェストと一致しなくなることは正常であり、過去の検証成功を取り消さない。同じ古いコピー元に対する `copy` の再実行は、意図的に削除したファイルを再取り込みする可能性があるため、整理後の通常手順には含めない。この再取り込みは要件上許容されるが、必要な場合だけ明示的に行う。

0013は0010のマニフェストとの完全一致を要求せず、バックアップ実行時点の主HDDを別の集合として検証する。0010のマニフェストは取り込み証跡であり、将来の主HDD全体の期待状態ではない。

これは主HDD全体の定期的な劣化検査やペア欠損検出ではない。RAW/JPEG/XMPまたはLive Photoの組の欠損検出は、必要性が生じた場合の0016で扱う。

### 7. 取り込み時点の検証マニフェストを残す

全対象が `matched` の場合、各対象の次の値を配置先相対パス順に並べ、集合全体の `manifest_sha256` を生成する。

```text
<配置先ルートからの相対パス> NUL <サイズ> NUL <ファイルのSHA-256> LF
```

パスはUTF-8、サイズは10進数、ファイルハッシュは小文字16進表記とする。区切りを固定し、空白やタブを含むファイル名でも曖昧にならないようにする。NULまたは改行を含む危険な配置先名は計画段階で `unresolved` になるため、マニフェストへ入れない。

`manifest_sha256` はファイル本体の代わりではなく、「この取り込みで、どの相対パス・サイズ・内容の集合を検証したか」を示す識別子である。不一致や未解決が1件でもある場合は完全な検証済み集合が成立しないため `manifest_sha256` を `null` とする。

検証後の整理で主HDDの内容が変わっても、当時の成功ログとマニフェストは変更しない。0013では現在の主HDDから新しいバックアップ対象マニフェストを作り、0010の値を現在状態の照合基準にはしない。

### 8. 要約、JSONログ、終了コードを拡張する

標準出力はコピー結果と検証結果を区別し、短く表示する。

```text
コピー結果: コピー済み 962件、既存一致 43件、衝突 0件、失敗 0件、保存対象の未処理 0件、対象外 10件、除外 7件
検証結果: 一致 1005件、欠損 0件、不一致 0件、読取不能 0件、未解決 0件、対象外 10件、除外 7件
合計: 対象 1005件 / 27000000000バイト、検証済み 1005件 / 27000000000バイト
マニフェストSHA-256: <64桁>
詳細ログ: .photo-copy-logs/copy-YYYYMMDD-HHMMSS-ffffff.json
```

未対応のSony管理情報は、コピー結果と検証結果の双方で `not-targeted` として対象外であることを明示する。現在は未対応形式を `unresolved` としているが、対応メディアの日時不明などと混同して終了コード1になるため、0010で状態を分離する。保存対象の未処理は引き続き失敗とする。

既存のコピーJSONログへ `verification` オブジェクトを追加し、少なくとも次を記録する。

- `schema_version`、開始・終了時刻、コピーと検証それぞれの所要時間
- プロファイル名と、秘密情報を含まない解決後の設定
- コピー状態別件数、検証対象件数・総バイト数、検証状態別件数
- `manifest_sha256`（完全一致時のみ）
- 各項目のコピー結果、検証結果、コピー元・配置先・配置先相対パス、両側のサイズとSHA-256、理由
- 接続先の識別情報、主HDD UUID、ローカル・リモートのツールバージョン

失敗時も、取得できたコピー結果と検証結果を同じログへ残す。パスワード、SSH鍵、環境変数の秘密値は記録しない。

終了コードは次にする。

- `0`: コピー処理が成功し、全保存対象が `matched` である。`not-targeted` と `excluded` は許容する。
- `1`: コピーの衝突・個別失敗・中断・保存対象の未処理、または検証の `missing`・`different`・`invalid-destination`・`unreadable`・`unresolved`・中断が1件以上ある。
- `2`: 引数・プロファイルが不正、SSH接続先や主HDDの事前検査に失敗したなど、一連の処理を開始できない。

転送が中断した場合は、未転送分が明らかなためコピー後検証を開始せず、検証結果を `not-run` としてログへ残す。コピー後検証だけが接続切断などで完了できなかった場合も終了コード1とし、同じ `copy` コマンドの再実行を案内する。再実行では全対象が既存候補になるため、コピー前の内容一致判定で検証を完了できる。

## 対象範囲

- 通常の `photo-copy copy` に続く全件自動検証
- コピー結果と検証結果を分離した共通API・結果モデル
- 既存一致判定で得たサイズ・SHA-256の再利用
- 新規コピーした配置先の件数・容量・SHA-256検証
- `classify` / `preserve`、`--only`、ローカル・rsync over SSHの全経路
- 完全一致時の `manifest_sha256` と拡張したJSONログ
- 0009で取り込んだSDカード1枚分・保存対象1,005件の実機検証
- `docs/setup/mac.md` とコピーCLIの検査スクリプトの更新

## 範囲外

- 独立した `photo-copy verify` コマンド
- 全件検証を省略するオプション
- 不一致、欠損、読取不能の自動修復や再コピー
- コピー元、主HDD、SDカード内の自動削除
- 主HDD上の余分なファイルの完全列挙・削除
- 検証成功後の整理内容と取り込み時マニフェストの一致維持
- 主HDD全体の定期的な劣化検査
- RAW/JPEG/XMP、HEIC/MOVなどのペア欠損検出（必要時の0016）
- 第2 HDDへのバックアップと、その時点の主HDDに対する内容検証（0013）
- Amazon PhotosやImmich上の内容検証
- 定期実行、通知、GUI（0014以降）
- ハッシュキャッシュや永続DB。実測で必要性が判明した場合に別プランとする

## 完了条件

- 既存の `photo-copy copy --profile sd-to-ubuntu` が、非dry-run時にコピー後の全件検証まで自動実行する。
- 利用者が独立した検証コマンドを実行する必要がなく、検証を省略して成功扱いにする経路もない。
- 既存一致のサイズ・SHA-256結果を再利用し、新規コピー分だけ配置後に読み取る。
- 件数・総容量・ファイルごとのSHA-256を照合し、欠損・不一致・読取不能・未解決があれば成功扱いしない。
- 全件一致時だけ取り込み時点の `manifest_sha256` を生成し、コピーJSONログへ残す。
- 0009で取り込んだ保存対象1,005件・27 GBを実機で検証し、全件一致、所要時間、マニフェストを `validation.md` に記録している。
- Sony管理情報10件とmacOS補助ファイル7件を対象外として明示し、対応メディアの欠損を対象外に紛れ込ませない。
- 異常系は一時ディレクトリとフェイクだけで確認し、コピー元と主HDDの実データを変更していない。
- `docs/setup/mac.md` と `scripts/mac/verify-copy-cli.sh` が実装後の操作に一致し、検査スクリプトを実機で確認している。

## 0011・0013・0014への引継ぎ

- **0011**: 0010で取り込み時点の全件一致を確認した主HDDのライブラリを、read-onlyのExternal Libraryとして登録する。0010後の意図的な整理は許容する。
