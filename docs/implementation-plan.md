# photo-manager 実装計画

## 1. この計画の目的

`docs/requirements.md` を唯一の仕様として、SDカードから外付けHDDへの安全な取り込み、保存済みデータの整合性検証、2台目HDDへの非破壊ミラーリングを段階的に実装する。

最優先する性質は次のとおり。

1. 元データおよび既存の保存データを上書き・削除しない
2. コピー後の再読込検証が完了するまで正式ファイルとして公開しない
3. 中断後に再実行でき、同じ入力に対して冪等に動作する
4. 失敗を成功として報告せず、eject 条件を厳密に守る
5. Python 3.8+ の標準ライブラリと exiftool だけで動作する

## 2. 実装対象と完了条件

### 実装対象

- `photo-import`: 対象列挙、日時判定、リネーム、月別配置、コピー、検証、台帳記録、条件付き eject
- `photo-verify`: 台帳と実ファイルの全方向照合、ビット腐敗・欠落・未登録の検出
- `photo-mirror`: コピー元を事前検証したうえでの非破壊同期とコピー先検証
- 設定ファイル、実行ログ、排他ロック、中断復旧、dry-run
- セットアップ・運用手順と無効状態の launchd テンプレート
- 正常系、異常系、中断系の自動テスト

### 完了条件

- 3コマンドが要件どおりの引数と終了コードで動作する
- 対象ファイルを一度も上書き・削除しないことをテストで確認できる
- コピー成功、スキップ、別名保存、日時不明、破損、容量不足、中断復旧を再現するテストが通る
- `checksums.tsv` の生成、補完、検証、末尾破損からの修復が仕様どおり動作する
- eject の全条件をテストし、1条件でも欠ける場合は eject されない
- 実機に存在する Python 3.9.6（`/usr/bin/python3`）と 3.10.13（pyenv）で単体テストが通る
- 3.8 は「言語機能の下限」とし、実行環境は用意しない。3.8 に無い API（`zoneinfo`、`str.removeprefix`、`dict` の `|` 統合など）を使わないことはレビューで担保する。タイムゾーンは `datetime.timezone(timedelta(...))` の固定オフセットだけで表現する
- 実機SDカードとテスト用HDDによる受け入れ確認が完了する

実行スクリプトは引数を共通CLI層へ渡すだけの薄いラッパーとする。安全性に関わる処理を3本のスクリプトへ重複実装しない。インストールを必須にせず、リポジトリから直接実行できる構成にする。

直接実行を成立させるため、各スクリプトの先頭で `Path(__file__).resolve().parent.parent / "src"` を `sys.path` へ挿入する。`resolve()` を使うことで、`PATH` 上へ張ったシンボリックリンク経由の起動でも正しい `src/` を解決できる。launchd テンプレートはスクリプトを絶対パスで起動するため、この解決方法と整合する。

## 4. 基本設計

### 4.1 処理の境界

処理を以下の層に分離する。

| 層 | 主な責務 |
|---|---|
| CLI | 引数解析、設定上書き、終了コードへの変換 |
| 事前チェック | パス、Volume UUID、書込可否、hard link対応、容量、依存ツール、同一ボリュームの検査 |
| 計画作成 | 対象列挙、XML対応付け、日時決定、宛先パス決定、衝突判定 |
| 実行 | ロック、`.part` コピー、ハッシュ検証、正式化、台帳更新 |
| 検証 | 台帳構文、登録ファイル、未登録ファイル、余分なファイルの照合 |
| 表示・ログ | 詳細ログ、進捗、集計、警告・失敗、終了メッセージ |

dry-run と実行時で同じ「計画作成」ロジックを使う。実行時は外部状態の変化に備え、事前チェックと衝突判定を再実施する。

dry-run は「計画作成」までで打ち切り、永続的な変更を一切行わない。台帳の修復と一時ファイルの掃除はHDDへの永続的な変更であるため、dry-run では実行せず「修復が必要」「削除予定 N 件」と表示するに留める。状態を変更する処理は、必ず dry-run の分岐より後ろに置く。

### 4.2 内部データモデル

Python 3.8で使える `dataclasses` と `enum` を用いて、少なくとも次の値を明示的に表現する。

- `Config`: 宛先、UUID、ソース、ミラー先、exiftool、オプション
- `SourceFile`: 元パス、種別、サイズ、mtime、対応MP4/XML
- `CaptureTime`: タイムゾーンを含みうる日時、取得方法、警告
- `TransferPlan`: 元パス、相対宛先、最終候補名、処理予定
- `TransferResult`: copied / skipped / warning / failed と詳細
- `LedgerRecord`: path / algorithm / digest / size / captured_at / imported_at
- `RunSummary`: コピー、スキップ、警告、失敗、台帳有効性、eject可否

処理結果は文字列だけでなく構造化して保持し、最終的な eject 判定を表示メッセージから独立させる。

### 4.3 macOSとの連携

- Volume UUID取得: `/usr/sbin/diskutil info -plist <path>` を実行し、`plistlib.loads()` で解析する。`plistlib.load()` はシーク可能なファイルオブジェクトを要求するため、`subprocess` の出力ストリームを直接渡すと `io.UnsupportedOperation` になる。必ず `stdout` のバイト列を受け取って `loads()` を使う
- eject: 事前に確定した `ParentWholeDisk`（実測例: `disk8`）を対象に `diskutil eject` を実行する。`DeviceIdentifier`（実測例: `disk8s1`）はパーティションであり、カードリーダーの取り外し対象としては誤りである。UUID照合に使ったのと同じ `diskutil info` の結果から両方を取得し、実行直前にマウントポイントが変わっていないことを再確認する
- ロック: `_photo-manager/import.lock` を開き、`fcntl.flock` を使う。import と mirror は `LOCK_EX | LOCK_NB`、verify は `LOCK_SH | LOCK_NB` を取得する
- 永続化: `fcntl.fcntl(fd, fcntl.F_FULLFSYNC)` を使う。macOSの `os.fsync` はドライブのライトキャッシュへのフラッシュを命令しないため、電源断でデータを失いうる。`F_FULLFSYNC`（`/usr/bin/python3` 3.9.6 の `fcntl` に存在、値51）が `OSError` になった場合だけ `os.fsync` へフォールバックし、その旨をログへ残す。正式化後は親ディレクトリも同様に同期する
- 再読込検証: 検証用に開き直した読み取りfdへ `fcntl.fcntl(fd, fcntl.F_NOCACHE, 1)`（同3.9.6の `fcntl` に存在、値48）を設定してからハッシュを計算する。設定しない場合、直前に書いた内容がページキャッシュから返るため、検証しているのはメモリの内容であって媒体へ落ちたビットではない。`F_NOCACHE` は完全な保証ではないが、キャッシュ読みを避ける努力として必須とする。`photo-verify` のビット腐敗検出でも同じ設定を行う
- 正式化: `.part` から正式名への `os.link` を使い、既存名を置換せずに公開してから `.part` を unlink する。`os.link` は宛先が存在すると `FileExistsError` を送出するため、置換は構造的に起こらない
- hard link 依存: 上記の正式化は宛先ファイルシステムが hard link を提供することを前提とする。`os.rename` は既存ファイルを黙って置換するため代替にならない。宛先がHFS+/APFSでない構成に備え、事前チェックで実測する（4.1、Phase 1）

外部コマンドの出力やロケール依存のテキストは判定に使わず、可能な限り plist や終了コードを使用する。

### 4.4 一時ファイルの配置（要件からの変更）

要件 §9 手順1 は `.part` を宛先ディレクトリに作るとしているが、本計画では `_photo-manager/tmp/<最終ファイル名>.part` に作り、そこから `<subdir>/YYYY/YYYY-MM/` の正式名へ hard link する。同一ボリューム内なのでリンクは成立する。

変更する理由。

1. Amazon Photos が監視する `Camera/` ツリーに一時ファイルが一切現れない
2. 「ツール所有の `.part`」の判定が「管理ディレクトリ配下にあるか」で自明になり、ユーザーが置いたファイルを誤って削除する経路が消える。命名規則やファイル所有者からの推測が不要になる
3. verify の未登録ファイル検査から `.part` を除外する特例が不要になる

この変更は要件書の記述と異なるため、`docs/decisions/` にADRとして記録し、要件書 §9 手順1も併せて更新する（7.1）。互換のため、verify は `<subdir>/` 配下の `*.part` も引き続き未登録検査の対象外として扱う（旧バージョンや手動操作の残骸）。掃除の対象にはせず、警告として報告するに留める。

## 5. フェーズ別実装計画

### Phase 0: 骨格とテスト基盤

**実装**

- 推奨ディレクトリ構成を作成する
- 3つの実行スクリプトと共通CLI入口を作成する
- `unittest` ベースのテスト実行方法を用意する
- `config.example.ini` と `.gitignore` を追加する
- ログの初期化と終了コード `0` / `1` / `2` の共通例外設計を作る
- `scripts/` から `src/` を解決する `sys.path` 挿入を実装する（3章）
- SIGINT / SIGTERM を捕捉する共通ハンドラを用意する。作成中の `.part` を削除し、ロックを解放し、部分的な結果をログへ書いてから終了コード1で終了する

**受け入れ条件**

- 各コマンドの `--help` が要件のCLIを表示する
- 不正な引数は終了コード2になる
- 外部パッケージなしでテストを実行できる
- リポジトリ外に張ったシンボリックリンク経由で起動しても `src/` を解決できる
- SIGINT / SIGTERM でロックが解放され、作成中の一時ファイルが残らない

### Phase 1: 設定、Volume検証、ロック

**実装**

- 既定の `~/.config/photo-manager/config.ini` と `--config` を読み込む
- CLI指定値を設定値へ上書きし、組み合わせ制約を検証する
- `hash_algorithm = sha256` 以外を設定エラーにする
- 宛先の存在、UUID、書込可否、hard link対応、空き容量を検査する
- hard link対応は `_photo-manager/tmp/` 内で実際に `os.link` を試行して確認し、失敗した場合は何も変更せず終了コード2で中止する。正式化の安全性がこの機能に依存しているため、推測で通さない
- `[dest] subdir`（既定 `Camera`）を読み込み、以降の宛先生成・verify走査範囲・mirror転送対象の基準にする。`Camera` をハードコードしない
- ソースを明示指定または `/Volumes` 直下から一意に自動検出する
- 同一宛先に対し、import と mirror は排他ロック `LOCK_EX`、verify は共有ロック `LOCK_SH` を取得する。verify は読み取り専用なので verify 同士は並行できるが、4TB全件検証は214MB/sでも5時間を超えうるため、その間 import と mirror はブロックされる。これは意図した動作であり、運用手順に明記する
- mirrorはUUID辞書順で2ボリュームのロックを取得する

**テスト**

- 設定欠落、不正値、CLI片側指定、UUID不一致
- ソース候補0件、1件、複数件
- hard link非対応の宛先で終了コード2になり、何も書き込まないこと
- `subdir` を変更した場合に宛先生成とverify走査範囲が追随すること
- ロック競合時に管理ロック以外を変更しないこと
- verifyが `LOCK_SH`、import/mirrorが `LOCK_EX` を取り、verify同士は並行でき、verify中のimportはブロックされること
- mirrorで引数順に関係なく同じ順序でロックすること

### Phase 2: 対象列挙と撮影日時判定

**実装**

- 許可された4パターンだけを列挙し、除外対象を最初から計画へ入れない
- パスと拡張子の照合はカメラ媒体上の実態を考慮し、大文字小文字を区別しない
- MP4と `<stem>M01.XML` を同一ディレクトリ内で対応付ける
- 複数候補を曖昧エラー、孤立XMLを失敗にする
- XMLの `CreationDate` を `xml.etree.ElementTree` で読む
- 静止画とMP4のメタデータをexiftoolのJSON出力から取得する
- 各種優先順位とmtimeフォールバックを実装する
- XMLは対応MP4の日時を継承する

**実装上の注意**

- exiftoolは設定された絶対パスを直接実行する
- exiftoolには `-json` と必要タグだけを指定し、パスと結果の対応を厳密に確認する
- QuickTime日時は `CreateDate` と `TimeZone` の組を明示的に解釈する。XMLがある場合は常にXMLを優先する
- mtimeはソースファイルシステムが返すローカル時刻として扱い、UTCへ正規化しない
- 日時の出所をログへ残す

**テスト**

- JPG/ARWのEXIF成功とmtimeフォールバック
- XML日時、MP4タグ、mtimeの各優先順位
- 海外タイムゾーン付きXML
- 壊れたXML、XMLなしMP4、孤立XML、複数XML候補
- 日時を一切取得できないファイルがコピー計画に入らないこと

### Phase 3: 命名、配置、重複判定

**実装**

- `Camera/YYYY/YYYY-MM/<YYYYMMDD>_<HHMMSS>_<original>` を生成する
- 拡張子と原ファイル名をそのまま保持する
- MP4とXMLに同じ日時プレフィックスを付ける
- 既存なし、同名同内容、同名別内容を判定する
- 別内容の場合は `_2`, `_3`, ... を拡張子の直前へ付ける
- 採番候補に既存ファイルがある場合もサイズ、sha256の順で比較する
- 同内容スキップ時に台帳レコードの有無を後続処理へ伝える

**テスト**

- JPG/ARWペアとMP4/XMLがファイル名順で隣接すること
- 月境界をまたぐSDカードが複数月へ振り分けられること
- 同名同サイズ同内容、同サイズ別内容、別サイズ
- `_2` が同内容、`_2` が別内容、`_3` が空いているケース
- 拡張子の大文字小文字を変更しないこと

### Phase 4: 排他的コピーと中断復旧

**実装**

- `.part` を `O_CREAT | O_EXCL` で新規作成する
- 元ファイルをチャンク単位で1回読み、書込みとsha256計算を同時に行う
- `.part` をflush/fsync後に読み直してsha256を計算する
- コピー前後で元ファイルのサイズとmtimeを比較する
- 検証後にmtimeを反映し、失敗時はツールが作成した `.part` だけを削除する
- hard linkで正式化し、競合した場合は重複判定と採番をやり直す
- 起動時は命名規則に合うツール所有の `.part` だけを掃除する
- ファイル単位の失敗を記録し、可能な範囲で後続ファイルを続行する

**テスト**

- 正常コピー後に元・先ハッシュが一致すること
- 書込み失敗、再読込不一致、mtime設定失敗、正式化競合
- コピー中の元サイズ変更・mtime変更
- SIGINT相当の中断後に正式名の不完全ファイルがないこと
- 無関係な `*.part` を削除しないこと
- 既存の正式ファイルをどの経路でも置換しないこと

### Phase 5: チェックサム台帳

**実装**

- `csv` のTSV方言で6列を読み書きする
- 起動時に全レコードの列数、型、相対POSIXパス、アルゴリズム、ハッシュ形式、重複を検査する
- パストラバーサル、絶対パス、管理領域を指すレコードを拒否する
- 正式化後にレコードを追記し、flush/fsyncする
- 同一パス・同一内容のレコードを重複追加しない
- スキップした正式ファイルをSD上の元と照合できた場合のみ不足レコードを補完する
- 末尾の書きかけだけを、ログディレクトリへの原本退避後にアトミック修復する
- 途中の破損行は変更せず失敗する

**台帳形式の確定事項**

実装前にヘッダーの有無と日時の文字列表現を固定し、READMEにも記載する。推奨はヘッダーなし、日時は秒精度のISO 8601、取り込み日時はタイムゾーン付きISO 8601とする。要件と異なる解釈を生まないよう、必要ならADRに残す。

**テスト**

- 正常な追記と再読込
- タブ、改行、非ASCII文字を含むパスのCSVエスケープ
- 重複レコード、列不足、サイズ不正、ハッシュ不正、不正パス
- 末尾だけの破損と途中行の破損
- 退避に失敗した場合に台帳を変更しないこと
- 正式化後・台帳追記前の中断から補完できること

### Phase 6: `photo-import` の統合

**処理順**

1. 引数と設定を確定する
2. 実行ログを開始する
3. 状態を変更しない事前チェックを行う
4. 宛先ロックを取得する
5. 台帳を検査し、許容される末尾破損だけを修復する
6. ツール所有の古い `.part` を掃除する
7. 対象、日時、宛先、衝突結果を含む計画を作る
8. 全対象サイズから空き容量を検査する
9. dry-runなら計画と集計を表示して終了する
10. 各ファイルをコピーまたは検証済みスキップし、必要な台帳行を記録する
11. 全対象の結果と台帳レコードを再確認する
12. eject条件を純粋関数で評価する
13. 条件成立時だけejectし、カメラ内フォーマット推奨を表示する

容量チェックは保守的に「新規コピーおよび別名保存が必要な総サイズ × margin」で行う。実行中に容量不足が起きた場合は当該ファイルを失敗とし、以降も安全に処理できる範囲で継続する。

**統合テスト**

- 初回取り込み、全件再取り込み、一部再取り込み
- 成功、非阻害警告のみ、失敗ありの各終了コードとeject判定
- dry-runで宛先、台帳、SD、eject状態を変更しないこと
- 台帳補完完了前に成功扱いしないこと
- ログに全ファイルの結果と最終集計が残ること

### Phase 7: `photo-verify`

**実装**

- 台帳構文を検査する
- `--month`、`--year`、全件の対象レコードを相対パスで抽出する
- 登録ファイルの存在、サイズ、指定アルゴリズム、ハッシュを確認する
- 対象ディレクトリを走査し、未登録ファイルを失敗、余分なファイルを警告にする
- `.part` と `_photo-manager/` を未登録検査から除外する
- verify中も同一宛先ロックを取得し、常に読み取り専用で動作する

**テスト**

- 月、年、全件の範囲選択
- 欠落、サイズ不一致、ハッシュ不一致、未登録、余分なファイル
- 月外の破損が月指定結果へ混入しないこと
- 台帳の重複・構文不正が終了コード1になること
- verifyがファイルと台帳を変更しないこと

### Phase 8: `photo-mirror`

**実装**

- コピー元・先のパス、UUID、同一ボリューム、書込可否、容量を事前検査する
- 2ボリュームをUUID順にロックする
- コピー元台帳と全転送対象を完全検証してから、コピー先の変更を開始する
- コピー先なしはPhase 4と同じ排他的コピーを行う
- コピー先ありは台帳と照合し、一致ならスキップ、不一致なら上書きせず失敗する
- コピー先だけにあるファイルを削除せず警告する
- 全対象検証後に限り、コピー先の台帳を一時ファイル経由でアトミック置換する
- 最後にコピー先をコピー元台帳で再検証する

**テスト**

- 空のコピー先、途中まで同期済み、完全同期済み
- コピー元の欠落・破損・未登録時にコピー先を変更しないこと
- コピー先の同名不一致を上書きしないこと
- コピー先だけのファイルを削除しないこと
- 台帳更新前の失敗と、再実行による復旧
- dry-runでデータ、台帳、管理ディレクトリを変更しないこと

### Phase 9: ドキュメントと実機受け入れ

**READMEへ記載する内容**

- 前提環境と依存ツール
- 設定ファイルの作成方法
- 3コマンドの使用例と終了コード
- 初回は `--dry-run` を使う手順
- SDカードをスクリプトで消去しないこと
- 成功後にカメラ内フォーマットする運用
- `shasum -a 256` による手動検証例
- Amazon Photosの対象設定と動画が対象外である注意
- 2台目HDDの導入・ミラー手順
- ログと台帳の場所、障害時の確認方法

**実機受け入れ手順**

1. 重要データを含まないテスト用SDとテスト用ボリュームでdry-runする
2. JPG、ARW、MP4、XMLを含む少量データを取り込む
3. 元ファイルと保存先を別コマンドでもsha256照合する
4. 同じSDで再実行し、全件スキップと台帳非重複を確認する
5. 意図的な同名別内容、壊れたXML、孤立XMLを試す
6. コピー中断後の再実行を試す
7. verifyで1バイト変更、欠落、未登録を検出できることを試す
8. eject成功・抑止の両方を確認する
9. 2台目のテストボリュームでmirrorと再mirrorを確認する
10. 実HDDで少量データを取り込み、結果確認後に通常運用へ移行する

launchdテンプレートは同梱するが、手動運用で信頼性を確認するまでは有効化しない。

## 6. 横断的なテスト方針

### 単体テスト

- ファイルシステム操作は `tempfile.TemporaryDirectory` で隔離する
- exiftool、diskutil、ejectは `unittest.mock` で戻り値と呼出引数を検証する
- 時刻とUUIDを注入可能にし、テスト結果を決定的にする
- 小さなfixtureを使い、必要なメタデータ結果はJSON/XMLで再現する

### 結合テスト

- SDとHDDを模した2つの一時ディレクトリでコマンド全体を実行する
- 実ボリューム依存部分だけを差し替え、それ以外は実際のファイルI/Oを使う
- 各障害点へ例外を注入し、`.part`、正式ファイル、台帳の最終状態を確認する

### 安全性の不変条件

全テストで次を重点的に確認する。

- SD側への書込みAPIを呼ばない
- 既存の正式ファイルを置換しない
- 検証前のデータを正式名にしない
- 台帳は正式化後にだけ更新する
- 台帳更新に失敗しても正式ファイルを削除しない
- 失敗が1件でもあればejectしない
- dry-runでは永続的な変更を行わない
- mirror開始前にコピー元全体が正常である

## 7. 実装時に明文化する詳細

要件の意図を変えず、実装間の解釈差を防ぐため、以下は最初の実装時にテストと文書で固定する。

1. `checksums.tsv` のヘッダー有無、日時の正確な書式
2. mtimeフォールバック時のタイムゾーン表現
3. QuickTime `CreateDate` と `TimeZone` のexiftool出力形式ごとの解釈
4. ログファイル名が同一秒で衝突した場合の採番
5. XMLファイル名の対応判定で許可する大小文字以外の差異
6. 「余分なファイル」と「未登録ファイル」の分類対象
7. ejectコマンド成功後の表示と、eject自体が失敗した場合の終了コード

仕様判断が必要になった場合は、推測で安全条件を緩めない。動作互換性や将来のデータ解釈に関わるものは `docs/decisions/` にADRとして記録する。

## 8. 推奨実装順とマイルストーン

| マイルストーン | 対象Phase | 到達点 |
|---|---:|---|
| M1: 基盤 | 0〜1 | CLI、設定、Volume検証、ロックが動く |
| M2: 取込計画 | 2〜3 | 全対象の日時・宛先・重複処理をdry-run表示できる |

| M4: 保守 | 7 | 月・年・全件の整合性検証ができる |

各マイルストーンで自動テストを通し、特にM3は実機受け入れ前に異常系と中断系を完了させる。`photo-mirror` は `photo-import` と `photo-verify` の安全なコピー・台帳・検証部品を再利用して実装する。
