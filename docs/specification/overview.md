# 概要と基本方針

photo-manager は、Sony カメラの SD カードから外付けHDDへ写真・RAW・動画を安全に取り込み、長期的な整合性検証と2台目HDDへの非破壊ミラーリングを行う macOS 向けツールである。

## 目的とスコープ

目的は、SDカードからHDDへの取り込みを自動化し、保存されたデータが元データと一致していることを検証可能にすることである。

スコープに含むもの:

- SDカードからHDDへのコピー、リネーム、月別配置、再読込検証
- 保存済みデータのチェックサムによる整合性検証
- 2台目HDDへの非破壊ミラーリング
- 設定、ログ、排他制御、中断後の再実行、dry-run

スコープに含まないもの:

- SDカード上のファイルの変更や削除
- スマートフォンからの取り込み
- 現像、編集、カタログ管理
- ミラー先の余分なファイルの削除や競合ファイルの上書き

## 対応環境と依存関係

- macOS
- Python 3.8以上。外部Pythonパッケージは使用しない
- `exiftool`。launchd の最小PATHから見えないことがあるため絶対パスで設定する
- 書き込み可能で、hard linkを利用できる取り込み先・ミラー先ボリューム
- ボリュームの取り違えを防ぐためのVolume UUID

macOS標準の古い `rsync` には依存せず、コピーしながらPythonの `hashlib` でsha256を計算する。メタデータは独自解析せず、成熟した `exiftool` を利用する。

## 基本ワークフロー

1. SDカードと主アーカイブHDDを接続する。
2. `photo-import --dry-run` で対象、宛先、競合、必要容量を確認する。
3. `photo-import` でコピー、再読込検証、チェックサム台帳への記録を行う。
4. 全対象の成功と台帳の完全性を確認できた場合だけSDカードをejectする。
5. ログと結果を確認し、必要ならカードをカメラ本体でフォーマットする。
6. 定期的に `photo-verify` を実行し、2台目HDDには `photo-mirror` で同期する。

Mac内蔵SSDを経由するステージングは行わず、SDカードからHDDへ直接コピーする。

## アーカイブ構成

```text
<archive>/
├── Camera/
│   └── 2026/
│       └── 2026-08/
├── Phone/
│   └── 2026/
│       └── 2026-08/
└── _photo-manager/
    ├── checksums.tsv
    ├── import.lock
    └── tmp/
```

- `Camera` と `Phone` は機種名ではなく役割名である。
- 写真、RAW、動画、動画サイドカーを同じ月フォルダへ置く。
- イベント別・日別には分割せず、年と月で管理する。
- 管理ファイルと一時ファイルはAmazon Photosの対象外となる `_photo-manager/` に置く。
- Amazon Photosを利用する場合は `Camera/` と必要に応じて `Phone/` を対象にし、ファイル種別を写真のみにする。

アップロード開始後のパスやファイル名の変更は再アップロードや重複につながりうるため、保存構成は安定した契約として扱う。

## 安全性の不変条件

1. SDカードは読み取り専用として扱い、変更・削除・リネームしない。
2. 既存の正式データファイルを上書きまたは削除しない。
3. コピー後の再読込検証が完了するまで正式名で公開しない。
4. 台帳は正式化後にだけ更新し、台帳更新失敗時も正式ファイルを削除しない。
5. 中断後に再実行でき、同じ入力に対して冪等に動作する。
6. 失敗を成功として報告せず、1件でも失敗があればejectしない。
7. dry-runでは永続的な変更を行わない。
8. mirrorはコピー元全体が正常であることを確認してからコピー先を変更する。

## 既知の制約と将来課題

- 動画はクラウドバックアップの容量制約を受けやすいため、2台目HDDを主な冗長化手段とする。
- 静止画のカメラ内連番は一周するが、日時プレフィックスと競合時の別名保存により上書きは起こらない。
- スマートフォン用の `Phone/` 構成は予約済みだが、取り込み手段は未定である。
- 大文字小文字を区別しないファイルシステムでは、綴りの大小だけが違う名前も競合として扱われる。
