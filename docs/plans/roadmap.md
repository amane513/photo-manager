## 番号とフェーズの扱い

- プラン番号は推奨する着手順を表す。番号が小さいものから進める。
- 番号は0001から連番とし、欠番を作らない。新規プランは末尾に採番する（現時点では0024以降）。
- 推奨順が変わった場合は、ロードマップ全体を再採番し、フォルダ名と参照も合わせて更新する。
- フェーズは作業のまとまりを示す。同一フェーズ内は番号順を基本とし、並行できる箇所は[推奨する着手順](#推奨する着手順)に示す。
- 未着手プランのフォルダと `plan.md` は着手時に作成する。
- 環境を変更するプランは、[../setup/](../setup/) と [../../scripts/](../../scripts/) の更新までを成果物に含める。

### 0006の段階分け

1. **最小版**: ローカル転送とrsync over SSH、撮影日時による年月分類・日時プレフィックス・フラット配置、dry-run、無断上書き禁止、コピー元保持、SSH接続先・マウント確認、一時ファイル処理、構造化結果とログを実装する。この時点で初期動作確認を開始する。
2. **直後の改善**: 日時不明の明示年月による救済、同名候補の内容比較とスキップ、部分失敗後の再実行、定型設定の再利用を追加する。Mac→HDDは既存の相対配置を維持する。

CLIは共通処理APIを呼ぶ。保存確定、イベント指定、HTTPサーバー、全件チェックサム、削除履歴管理は0006の範囲に入れない。同名候補の内容比較は日常の再実行を楽にするため前倒しし、全件のコピー後検証とは分ける。

主HDDへの取り込みはSMBマウントに依存させない。SMBはAmazon Photosと必要時の参照用に残す。

SDはMacに接続する。iPhoneの機器からの取得はイメージキャプチャを使い、その後の配置に共通処理を使う。

## 推奨する着手順

番号順が基本だが、次の並行関係を使って待ち時間を減らせる。

```text
0002 ─> 0005 主HDD・SMB ──────────┐
0004 + 構築済みSSH ────────────┴─> 0006 rsync最小CLI ─> 初期動作確認
                                  ├─> 0007 基本確認 ──────┐
                                  ├─> 自動分類・同名スキップ ─┴─> 0008 Amazon ─> 0009 日常運用確立
0006 最小版 ─> 0009 日常運用確立 ─> 0010 全件検証 ─> 0011 Immich ─> 0012 表示・DB復元
0002 + 0005 ────────────────────────────────────────────────┴─> 0013 バックアップ・原本／DB復元
0012 + 0013 ─> 0022 ImmichによるiPhone直接バックアップ
0006 + 0009 ─> 0014 GUI
0007 選別・現像 ─> 必要になったときに確認（上記工程の前提にしない）
```

## 検証と日常運用

- 初期確認は各形式1〜2組を目安とし、形式・操作・例外を代表するケースで行う。一律10組や1か月の手動運用を必須にしない。
- 0006では正常コピー、異なる同名、同一スキップ、複数月、日時不明、切断、再実行を確認する。各後続プランは結果を再利用する。
- 日常はCLI実行と要約確認で終える。失敗・衝突・未処理だけ対応し、詳細ログは自動保存する。代表ファイルを毎回開いたり、全件の件数を手書きしたりしない。
- Amazon確認と第2 HDDバックアップは原則週次にまとめる。復元試験は導入時・変更時・定期確認に行う。
- コピー元の削除は別操作とする。0009で判断条件を設計し、0010で全件検証、0013で第2 HDD保存の結果を組み込む。実際の削除は0013の完了後に行い、それまではコピー元を保持する。
