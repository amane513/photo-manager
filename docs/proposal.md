# 写真・動画管理環境 最終提案書

作成日: 2026-08-23  
対象: Sony α7C II、iPhone 13、MacBook Air、Ubuntu常時稼働PC

## 1. 結論

次の構成を推奨する。

- MacBook Airを、取り込み・選別・必要時のRAW現像を行う一時作業場所とする。
- Ubuntuへ常時接続する4TB HDDを、選別済み写真・動画の正本とする。
- ImmichはUbuntu上で動かし、主HDDを読み取り専用のExternal Libraryとして参照する。
- ImmichではSony RAW（ARW）を除外し、JPEG、HEIC、動画、現像済みJPEGを表示する。
- Amazon Photosには、Macで選別済みの静止画だけを公式Macアプリから保存する。iPhoneからの自動保存は使わない。
- 第2 HDDを追加し、主HDDの原本とImmichのDB・設定をバックアップする。通常時は取り外しておく。
- 祖父母への共有は当面「みてね」を継続する。
- 最初の1か月程度は手作業で運用し、不便と事故ポイントを確認してから段階的に自動化する。
- iCloud+は利用しない。Macへ取り込むまでのiPhone写真・動画が端末内の1コピーだけになるリスクは受容する。

この構成では、Immichを保管場所ではなく、通常のフォルダとして保存した正本を見やすくする閲覧・検索システムと位置づける。Immichを停止・移行しても、写真と動画は一般的なファイルとして取り出せる。

## 2. 2案の比較と採用判断

| 論点 | Claude案 | Codex案 | 最終判断 |

| 全体方針 | 詳細な自動化と厳密な一方向フロー | 手作業から始める簡潔な構成 | **Codex案をベース**にし、安全面はClaude案を採用 |
| Mac作業フォルダ | `01_inbox` / `02_working` / `03_staging` | `PhotoInbox` / `ReadyForArchive` | **Codex案**。初期は2段階にする |
| イベント配置 | 月フォルダと同じ階層 | 月フォルダ内の `events/` | **Claude案**。月フォルダの兄弟にする |
| 機器別フォルダ | `a7c2` / `iphone13` | `a7c2` / `iphone13` | **`camera` / `smartphone`** に変更 |
| ファイル名 | 撮影日時を付けて一律リネーム | 原則維持、衝突時だけ変更 | **Codex案**。最初は原名を維持 |
| Mac→Ubuntu転送 | rsync over SSHを前提 | SMBで手動コピー | **最初はSMB**、安定後にrsyncを検討 |
| 第2 HDD | rsync＋削除履歴退避 | resticによる世代管理 | **初期は削除なしの追加コピー**。運用確認後に履歴方式を決める |

Claude案は完成形の運用設計として優れているが、リネーム、兄弟ファイルの自動削除、複数ステージ、API連携を最初から導入すると、実際の使い勝手が分からない段階で仕組みが固定される。今回の方針にはCodex案の簡潔さが合う。安全性に直結するread-only構成、RAW除外、切り離した第2 HDD、復元試験はClaude案の考え方を取り入れる。

## 3. 全体構成

```text
Sony SDカード ─┐
                ├─> Mac: PhotoWork
iPhone ─────────┘       │
                         ├─ 不要データを削除
                         ├─ 必要なRAWだけ現像
                         ├─ 選別済み静止画をAmazon Photosへ保存
                         │
                         └─ 選別済みデータを主HDDへ追加コピー
                                      │
                                      v
                         Ubuntu + 4TB主HDD（正本）
                             │              │
                             │              └─> 第2 HDD（通常は取り外す）
                             │
                             └─> Immich External Library（read-only）
                                      └─ ARWを除外して閲覧
```

データは原則としてMacから下流へ一方向に流す。ImmichやAmazon Photosを整理元にせず、削除・移動・現像は正本へ保存する前にMacで完了する。

## 4. フォルダ構成

### 4.1 Macの作業ディレクトリ

初期はCodex案の2段階構成を採用する。

```text
~/Pictures/PhotoWork/
├── PhotoInbox/
│   └── current/                  # 取り込み直後、未選別
└── ReadyForArchive/
    └── 2026/
        ├── 2026-08/
        │   ├── camera/
        │   ├── smartphone/
        │   └── edited/
        └── 2026-08-10_summer-trip/
            ├── camera/
            ├── smartphone/
            └── edited/
```

- `PhotoInbox/current/` は今回の取り込みだけを置く一時領域とする。
- 選別と現像が完了したら、HDDへ保存する構成のまま `ReadyForArchive/` へ移す。
- `ReadyForArchive/` をAmazon Photos Desktopのバックアップ対象とする。ただし動画は対象外にする。
- 主HDD、Amazon Photos、第2 HDDへの保存確認後、完了分をMacから削除する。
- 将来、作業中とAmazonアップロード待ちを区別する必要が実際に生じた場合だけ、Claude案の `working` / `staging` 分割を追加する。

### 4.2 主HDDのディレクトリ

```text
/srv/photo-library/
└── 2026/
    ├── 2026-08/
    │   ├── camera/
    │   │   ├── DSC00001.ARW
    │   │   ├── DSC00001.JPG
    │   │   └── DSC00001.ARW.xmp
    │   ├── smartphone/
    │   │   ├── IMG_0001.HEIC
    │   │   └── IMG_0001.MOV
    │   └── edited/
    │       └── DSC00001_edit.jpg
    └── 2026-08-10_summer-trip/
        ├── camera/
        ├── smartphone/
        └── edited/
```

#### イベントを月フォルダと同じ階層にする判断

`2026-08-10_summer-trip/` のような大イベントは、`2026-08/` の中ではなく、その兄弟として配置する。この方式に技術的な背反はない。Immichの通常タイムラインは撮影日時を基準にするため、時系列表示にも影響しない。

トレードオフは、2026年8月のファイルが `2026-08/` とイベントフォルダの2か所に分かれ、月単位でファイルを直接集計するときに両方を見る必要があることだけである。一方、旅行や行事をフォルダ単位で受け渡し・復元しやすく、FinderやImmichのFolder Viewからも見つけやすい。今回はこちらの利点を優先する。

運用ルールは次のとおりとする。

- 通常撮影は `YYYY-MM/` に置く。
- 旅行、七五三、運動会など、後から名前で探したい大きなイベントだけ `YYYY-MM-DD_event-name/` にする。
- 月をまたぐイベントは開始日の年月日に寄せる。
- イベント名は英小文字とハイフンを基本とし、`/` や `:` は使わない。
- イベントとして分ける判断は、主HDDへ保存する前に行う。
- Immichへ登録した後は、原則として移動・改名しない。

#### `camera` / `smartphone` にする判断

機種名ではなく役割名を使う。カメラやスマートフォンを買い替えてもフォルダ構成が変わらず、年をまたいだ検索や自動化ルールを維持できる。複数台を同時利用するようになった場合だけ、`camera/sony-a7c2/` のように1階層追加する。

#### 現像後のファイルを `edited/` に分ける理由

`edited/` に置くのは現像済みJPEGだけであり、RAWやカメラ撮って出しJPEGを作業後に別フォルダへ移すという意味ではない。分ける目的は次の3点である。

- カメラ生成のJPEGと、人が調整した完成版を明確に区別する。
- 同じ写真の撮って出し版と現像版が存在しても、上書きや取り違えを防ぐ。
- 完成版だけを探す、渡す、再書き出しする作業を簡単にする。

技術的には必須ではなく、`camera/DSC00001_edit.jpg` のように接尾辞だけで区別することもできる。ただし `edited/` は固定の1フォルダを増やすだけで意味が明確なため、最終案では残す。現像済みJPEGは再生成可能な派生物だが、再現の手間を避けるため原本と同様に主HDD・第2 HDD・Amazon Photosへ保存する。

### 4.3 Ubuntu内蔵SSD

内蔵SSDにはOS、Docker、Immich、PostgreSQL、サムネイル、機械学習モデル、変換済み動画を置く。写真・動画の正本は置かない。

```text
/srv/immich/
├── postgres/
├── thumbs/
├── encoded-video/
├── model-cache/
└── profile/
```

頻繁に読むサムネイルとDBをSSD、容量の大きい原本をHDDへ分けることで、HDDを正本にしながらImmichの閲覧速度を確保する。

## 5. 日常ワークフロー

### 5.1 取り込みと選別

1. SDカードまたはmacOSの「イメージキャプチャ」から `PhotoInbox/current/` へ取り込む。
2. コピーしたファイル数を確認する。Live Photoは静止画とMOVの組を維持する。
3. Finder、Quick Look、QuickTime Playerを使い、まずJPEG・HEIC・動画を手作業で選別する。
4. 不採用写真は、同じベース名のRAW、JPEG、XMP、Live PhotoのMOVを組で削除する。
5. 重要な写真だけdarktableでRAW現像し、フル解像度・sRGBのJPEGを `edited/` へ書き出す。
6. darktableのXMPサイドカーはRAWと一緒に保存する。
7. 保存先の月またはイベントを決め、`ReadyForArchive/` へ移す。

最初はRAW+JPEGとLive Photoを各10組程度で試し、削除と現像の挙動を確認する。自動一括削除や一律リネームはまだ行わない。

### 5.2 ファイル名

- 原則としてカメラ・iPhoneの元ファイル名を維持する。
- 同じ保存先に同名ファイルがあっても上書きしない。
- 衝突した場合だけ撮影日時等を付け、RAW/JPEG/XMPなどの対応ファイルを同じベース名へまとめて変更する。
- 一律リネームは、手作業を数回経験して必要性が確認できてから検討する。

### 5.3 保存確定

1. `ReadyForArchive/` の今回分を、FinderのSMB共有から主HDDの対応先へ追加コピーする。
2. ファイル数、合計容量、代表的な写真・動画が開けることを確認する。
3. Amazon Photosで静止画のアップロード完了を確認する。
4. 第2 HDDへバックアップし、結果を確認する。
5. ImmichのExternal Libraryをスキャンし、表示を確認する。
6. すべて確認してから、SDカード、iPhone、Macの作業コピーを削除する。

初期は既存データを削除する同期を使わず、今回分の追加コピーだけを行う。手順が安定したら、Mac→Ubuntuをrsyncで再実行可能にする。ただし自動化後も、コピー元の削除をコピー先へ伝播させる `--delete` は日常の転送では使わない。

## 6. Amazon Photos

- Mac版Amazon Photos Desktopを使い、`ReadyForArchive/` だけをバックアップ対象にする。
- 写真（JPEG、HEIC、ARW、現像済みJPEG）のみを対象にし、動画は対象外にする。
- iPhoneのAuto-Saveは無効にし、Mac経由の1経路に統一する。
- 初回にα7C IIのARW、HEIC、JPEGを少数アップロードし、ダウンロードして開けることを確認する。
- ローカル削除がAmazon Photos側へ伝播しない「バックアップ」設定であることをテストする。
- Amazon Photosはオフサイトコピーであり、正本や唯一の保管先にはしない。

iCloud+は採用しない。これにより、Macへの取り込み前はiPhone本体が唯一のコピーとなる。重要な写真は主にカメラで撮るという前提でこのリスクを受容するが、旅行や行事でiPhoneも重要な撮影に使った日は、通常より早くMacへ取り込む。

## 7. Immich

### 7.1 基本構成

- Ubuntu 64-bit上でDocker Composeを使う。
- PostgreSQLとImmichの作業データは内蔵SSDへ置く。
- `/srv/photo-library` をコンテナへ読み取り専用でマウントする。
- Upload LibraryではなくExternal Libraryを主に使う。
- Immichから原本の削除・整理を行わない。
- 初期は家庭内LANだけで利用し、ルーターからImmichのポートを直接公開しない。

マウントの考え方は次のとおり。

```yaml
volumes:
  - /srv/photo-library:/external/photo-library:ro
```

### 7.2 RAW除外

External Libraryの除外パターンに次を設定する。

```text
**/*.ARW
**/*.arw
```

これにより、RAWは主HDD・第2 HDD・Amazon Photosに保持しながら、Immichには撮って出しJPEGや現像済みJPEGだけを表示できる。フォルダ名ではなく拡張子で除外するため、`camera` やイベント構成を変更しても設定が影響を受けにくい。

### 7.3 段階導入

1. CPUだけで基本動作、タイムライン、検索、動画再生を確認する。
2. 小規模なテストフォルダでARW除外、HEIC、Live Photo、動画、現像済みJPEGを確認する。
3. DBバックアップと復元を確認する。
4. 問題がなければ全ライブラリをスキャンする。
5. その後、必要に応じてRTX 4060 Tiによる機械学習や動画変換の高速化を有効にする。

## 8. バックアップ

### 8.1 コピー構成

| データ | 主HDD | 第2 HDD | Amazon Photos | 評価 |
|---|---:|---:|---:|---|
| JPEG / HEIC | 正本 | バックアップ | オフサイト | 3コピー |
| ARW | 正本 | バックアップ | オフサイト | 3コピー |
| XMP | 正本 | バックアップ | なし | ローカル2コピー |
| 動画 | 正本 | バックアップ | なし | ローカル2コピー |
| 現像済みJPEG | 正本 | バックアップ | オフサイト | 3コピー |
| Immich DB・設定 | SSD | バックアップ | なし | ローカル2コピー |

第2 HDDはバックアップ時だけ接続し、完了後に取り外す。主HDDと常時接続したままにすると、誤削除、マルウェア、電源障害の同時被害を受けやすい。

動画にはオフサイトコピーがないため、火災・盗難・大規模災害では主HDDと第2 HDDを同時に失う可能性がある。現時点ではこのリスクを受容し、将来、動画の重要度や容量が増えた時点で有料クラウドまたはHDDの別拠点保管を再検討する。

### 8.2 初期のバックアップ方法

最初は主HDDから第2 HDDへ、削除を伝播させない追加コピーを手動で行う。写真・動画を通常ファイルのまま保存し、専用ツールなしでも取り出せる状態を優先する。

手作業が定着した後、次のどちらかを選ぶ。

- rsyncで通常ファイルのミラーを作り、変更・削除前のファイルを日付別フォルダへ退避する。
- resticで世代管理、整合性検査、復元をまとめて行う。

現時点ではどちらかに固定しない。実際にXMPをどの程度更新するか、誤削除からどこまで戻したいか、第2 HDDの容量にどの程度余裕があるかを確認した後に決める。これは初期運用を始めるためのブロッカーではない。

最低限の対象は次のとおり。

- `/srv/photo-library` 全体
- ImmichのPostgreSQLダンプ
- Docker Composeファイルと `.env`
- Immichプロフィール等、原本やDBから再生成できないデータ

サムネイルと変換済み動画は原本から再生成できるため、初期はバックアップ対象外でよい。

### 8.3 頻度と検証

- 新しい取り込み後: 可能ならその日のうちに第2 HDDへバックアップする。
- 定期: 少なくとも週1回。
- Immich DB: 日次ダンプをSSDに作り、第2 HDD接続時にコピーする。
- 半年に1回: 写真・動画・XMPとDBを一時領域へ実際に復元する。
- 年1回: 使用量と年間増加量を測り、主HDD・第2 HDDの容量計画を更新する。

第2 HDDは8TBとする。α7C IIは購入直後で年間増加量を予測できないため、4TB主HDDの全量バックアップ、ImmichのDBダンプ、設定ファイル、追加コピー時の余裕を確保する初期構成として決める。実運用開始から1年後、または主HDDの使用率が60%に達した時点で容量計画を見直す。

## 9. 選別・現像ツール

初期は次の無料ツールで始める。

- Finder / Quick Look / QuickTime Player: 写真・動画の選別。
- darktable: 評価、非破壊RAW現像、XMP保存、JPEG書き出し。
- Sony Imaging Edge Desktop: Sony純正の色や処理が必要な場合の補助。
- macOS イメージキャプチャ: iPhoneからの原本取り込み。

darktableの操作やRAW+JPEGの管理が継続的な負担になった場合に、Lightroom Classicを再検討する。現像ソフト内だけに編集内容を閉じ込めず、XMPサイドカーと完成JPEGをファイルとして残す。

## 10. 導入ロードマップ

### Phase 0: 小規模検証と測定

1. 現在の写真・動画総容量と直近1年の増加量を測る。
2. 実データ各10組程度で、RAW+JPEG、XMP、Live Photo、動画の扱いを確認する。
3. Amazon Photosで各静止画形式のアップロード、再ダウンロード、ローカル削除時の挙動を確認する。
4. 第2 HDDの容量を決める。

### Phase 1: 手作業の保存フロー

1. 主HDDをUbuntuへ接続し、`/srv/photo-library` を用意する。
2. Macから利用できるSMB共有を設定する。
3. 1回分の撮影データをMacで選別・現像する。
4. 主HDD、Amazon Photos、第2 HDDへの保存と復元を確認する。
5. 1か月程度、同じ手順を手作業で繰り返す。

### Phase 2: Immich

1. 内蔵SSDへImmichを導入する。
2. 主HDDをread-onlyのExternal Libraryとして登録する。
3. RAW除外と各形式の表示を確認する。
4. DBのバックアップと復元を確認する。
5. 必要性を確認した後にGPUアクセラレーションを追加する。

### Phase 3: 必要な箇所だけ自動化

手作業で時間がかかる、または間違えやすいことが確認できた処理だけを自動化する。候補は次の順とする。

1. Macから主HDDへの再実行可能なコピーと検証。
2. 第2 HDDへのバックアップと実行結果の通知。
3. Immich DBの日次ダンプ。
4. RAW/JPEG/XMP/Live Photoの組チェック。
5. 必要性が確認できた場合だけ、一括リネームやペア削除。

### Phase 4: 共有方法の見直し

管理基盤が安定してから、1イベントだけで「みてね」とImmich等を比較する。祖父母本人の操作感を確認し、明確な利点がある場合だけ移行する。

## 12. 主なリスク

| リスク | 対応 |
|---|---|
| 主HDD故障 | 第2 HDDとAmazon Photos。第2 HDDは通常取り外す |
| 動画のオフサイトコピーがない | 現時点では受容。将来クラウドまたは別拠点HDDを再検討 |
| iPhone取り込み前は1コピー | iCloud+は使わず受容。重要時は早めにMacへ取り込む |
| 誤削除がバックアップへ伝播 | 初期は削除なしの追加コピー。将来は削除履歴または世代管理を導入 |
| RAWとJPEGがImmichで二重表示 | External LibraryでARWを拡張子除外 |
| Immich障害 | 正本を通常フォルダで保持し、Immichはread-onlyで参照 |
| Immich DB喪失 | DBダンプを第2 HDDへ保存し、復元試験を行う |
| 保存後の移動・改名でImmich内情報が失われる | 月・イベント分類をMacで確定してから保存する |
| Amazon Photosの重複 | アップロード元をMacの `ReadyForArchive` に一本化 |
| 自動化による誤処理 | 手作業で運用を確立し、dry-runと小規模テストを経て導入 |

## 13. 現時点で判断不要な保留事項

次はPhase 0または実運用後に決めればよく、導入開始前の回答は不要である。

- 第2 HDDの具体的な容量: 現在量と年間増加量の測定後に決める。
- rsyncとresticの選択: 手動運用で必要な履歴粒度を確認してから決める。
- Macの作業フォルダを3段階へ増やすか: `ReadyForArchive` の滞留が問題になった場合だけ検討する。
- ファイル名の一律変更: 衝突や検索上の不便が発生した場合だけ検討する。
- GPUアクセラレーション: CPU構成での動作確認後に判断する。
- 祖父母向け共有の変更: 管理基盤が安定してから別途評価する。

## 14. 最終推奨

まず、Macで選別し、Ubuntuの主HDDへ保存し、静止画をAmazon Photosへ送り、第2 HDDへバックアップする一連の流れを手作業で確立する。その後にImmichをread-onlyで接続し、RAWを除外して閲覧する。

フォルダはMac側を2段階に留め、保存先では月フォルダと大イベントを同じ階層に置き、機器名には `camera` / `smartphone` を使う。現像済みJPEGだけは、撮って出しとの区別が明確になるため `edited/` に分ける。

この運用を数回繰り返してから、コピー、検証、バックアップ、DBダンプの順に必要な部分だけを自動化する。
