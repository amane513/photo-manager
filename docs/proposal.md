# 写真・動画管理環境 提案書

作成日: 2026-08-23

更新日: 2026-09-13

対象: Sony α7C II、iPhone 13、MacBook Air、Ubuntu常時稼働PC

## 1. 基本方針

普段は取り込むだけで終わり、人が対応するのは例外と必要な編集だけとする。運用にかかる時間を減らすため、コピー・配置・結果記録を自動化し、不要データの残存とバックアップ先ごとの差異を許容する。

- 4TB主HDDを正本とし、作業領域との分割や保存確定の操作は設けない。
- 通常はMacに挿したSDからrsync over SSHで主HDDへ直接コピーし、選別しない。
- 必要時だけMacの `~/Pictures/PhotoWork/` を経由する。選別・現像はこの経路でも任意である。
- MacとHDDは年月・機器別の構成に統一し、イベントフォルダは廃止する。
- Amazon PhotosはMacからSMB上の正本の静止画をバックアップする。Mac内の作業コピーは対象にしない。
- Immichは正本をread-onlyのExternal Libraryとして参照し、ARWを除外する。
- 8TB第2 HDDへ正本とImmich DB・設定をバックアップし、通常時は取り外す。
- コピー用CLIを初期検証より先に用意し、共通処理APIを将来のGUIでも使う。
- 環境構築はスクリプトと手順書として残し、新しいPCで同じ環境を組み直せるようにする。
- 祖父母への共有は当面「みてね」を継続する。iCloud+は利用しない。

## 2. 許容することと基本的な保護

| 論点 | 方針 |
|---|---|
| 不要な写真・未現像RAW | 残ってよい。選別・現像を取り込みの前提にしない |
| 保存先の違い | HDDで削除した写真がAmazonや第2 HDDに残ってよい |
| 削除済み写真の再取り込み | SDやMacに残っている場合の復活を許容し、初期は削除履歴を管理しない |
| バックアップの遅れ | 取り込みと別に進める。保護が薄い期間を許容する |
| 分類 | 撮影年月と機器だけに統一する。日時不明は黙って推測せず例外として報告する |
| 上書き・失敗 | 取り込みでは無断上書きせず、失敗・未処理を成功扱いにしない |
| コピー元削除 | 自動化しない。試験中は保持し、日常は別途確認して判断する |

## 3. コピー経路

```text
経路a（通常）: Macに挿したSD ─ rsync over SSH ─> Ubuntuの主HDD
経路b（必要時）: SD ─> Mac: PhotoWork ─ rsync over SSH ─> Ubuntuの主HDD
                         └─ 必要なときだけ選別・現像

iPhone ─ イメージキャプチャ ─> Mac: PhotoWork ─ rsync over SSH ─> 主HDD

主HDD: photo-library ─ SMB経由でMacのAmazon Photosアプリ ─> Amazon（静止画のみ）
                    ├─> 第2 HDD（原則週1回、接続時にバックアップ）
                    └─> Immich External Library（read-only、ARW除外）
```

経路aではMac内に中間コピーを保存しない。UbuntuへSDカードを挿す運用は対象外とする。HDDへのコピー完了を保存完了とし、選別の承認や公開操作を追加しない。保存完了はバックアップ完了・内容検証済みと同義ではない。

主HDDへの取り込みはSMBマウントに依存させない。SMBはAmazon Photos Desktopからの参照と、必要時のFinder・現像ツールからの参照に限定する。rsyncデーモンは導入せず、構築済みのSSH接続を使用する。

## 4. フォルダ構成

### 4.1 Macと主HDD

Macの `~/Pictures/PhotoWork/` とHDDの `/mnt/camera_archive/photo-library/` 以下を、同じ相対構成とする。

主HDDの正本のルートは `/mnt/camera_archive/` 自体ではなく、その1階層下の `photo-library/` とする。Amazon Photos Desktopが、SMBでマウントしたボリューム自体（`/Volumes/CameraArchive`）をバックアップ対象に指定できず、その1つ下の階層のフォルダしか指定できないためである。年フォルダを `/mnt/camera_archive/` 直下に置くと、年が変わるたびに対象フォルダの追加が必要になり、追加を忘れるとその年が黙って保護されない。ライブラリルートを1階層下げることで、Amazonのバックアップ対象は `photo-library` の1フォルダに固定でき、年が変わっても対象指定を変えずに済む（0008）。SMBの共有名・共有パス（`CameraArchive` = `/mnt/camera_archive`）とMac側のマウント位置 `/Volumes/CameraArchive` は変わらない。Macの `~/Pictures/PhotoWork/` にはこの階層を追加しない。

```text
<ルート>/
└── 2026/
    └── 2026-09/
        ├── camera/
        │   ├── 20260911-143052_DSC00001.ARW
        │   ├── 20260911-143052_DSC00001.JPG
        │   ├── 20260911-143052_DSC00001.ARW.xmp
        │   └── 20260911-143052_DSC00001_edit.jpg
        └── smartphone/
            ├── 20260911-143052_IMG_0001.HEIC
            └── 20260911-143052_IMG_0001.MOV
```

- イベント名の入力、イベント用の配置、月またぎの特例を設けない。
- 機器は役割名の `camera` / `smartphone` を使う。
- 月は撮影日時から判定する。同じ写真のRAW/JPEG/XMPやLive Photoの組が別月に分かれないよう、対応ファイルの配置規則を0006で定める。全件のペア欠損検出は後続とする。
- SDカード由来の `DCIM/` や `PRIVATE/` などのサブフォルダは保存先へ持ち込まず、機器別フォルダ直下へ配置する。
- 撮影日時のローカル時刻を `YYYYMMDD-HHMMSS_` として原名の前に付ける。原名と拡張子はそのまま保持する。RAW/JPEG/XMPとHEIC/MOVなど同じ撮影に属するファイルには同じプレフィックスを使う。
- 撮影日時を取得できないファイルは推測で改名・配置せず未処理として報告する。日時不明の救済方法は0006で決める。
- Mac→HDDでは既にある相対配置を維持し、コピー時刻やXMP更新時刻で再分類しない。
- 現像済みJPEGは元RAWと同じ `camera/` に `_edit` 付きで置く。XMPもRAWの隣に置く。
- 旧 `PhotoInbox` / `ReadyForArchive` やイベントフォルダに実データがある場合は、残存データを確認して別途移行する。本書の更新では実ファイルを変更しない。

### 4.2 Ubuntu内蔵SSD

SSDにはOS、Docker、Immich、PostgreSQL、サムネイル、モデル、変換済み動画を置く。原本は主HDDに置く。

```text
/srv/immich/
├── postgres/
├── thumbs/
├── encoded-video/
├── model-cache/
└── profile/
```

`/mnt/camera_archive/` は配置案であり、0005でHDDのマウント・共有と対応づける。未マウント時にSSDやMacのローカルディレクトリへ誤書込みしないようにする。

## 5. 操作と自動化

### 5.1 日常の取り込み

1. SDをMacへ接続し、CLIを実行する。通常の保存先はHDDとし、Mac経由のときだけ保存先を切り替える。接続先などの定型値は設定に保存する。
2. CLIが対象を列挙し、フォルダ作成とコピーを行い、結果の要約を表示する。
3. 失敗・衝突・未処理があるときだけ内容を確認して対応する。通常はここで取り込み作業を終える。

Mac経由の場合は、必要なら選別・現像してからCLIでHDDへコピーする。iPhoneの機器からの取得はイメージキャプチャを使い、その後の配置を共通処理に通す。日常の全件目視、件数の手書き転記、毎回のdry-runを必須にしない。dry-runは初回・設定変更・問題調査に使える機能として備える。

### 5.2 取り込み処理の振る舞い

- SDの `DCIM/` だけでなく `PRIVATE/` 内の動画も対象とする。未知の形式を黙って捨てず、未処理として報告する。
- コピー元を変更せず、既存ファイルを無断上書きしない。
- 主HDDへの転送はrsync over SSHを使う。コピー元削除、削除同期、インプレース書き込みは使わず、`--ignore-existing` を最後の上書き防止として使う。同一性の判定は `--ignore-existing` に任せない。
- 最小版では同名衝突を報告する。直後の改善で同名候補の内容を比較し、同一ならスキップ、異なるなら衝突として報告する。名前・サイズだけで同一とは断定しない。
- 同名衝突があっても無関係なファイルは処理し、結果を部分完了として返す。HDD切断など継続できない障害では中断する。
- 異なる同名ファイルは、対応するRAW/JPEG/XMP等を確認して衝突分だけ改名する。一律リネームは行わない。
- コピー中は一時名を使い、正常終了後に最終名へ切り替える案を0006で確認する。利用者が管理する作業領域は設けない。Amazon・Immichが途中ファイルを取り込まないことは実機検証し、未確認のまま保証しない。
- 再実行時は内容一致が確認できた既存ファイルをスキップする。途中ファイルを完成済みとして扱わず、残存時の再試行方法を決める。
- 対象・コピー済み・同一スキップ・衝突・失敗・未処理をログへ自動記録する。同名候補の比較と、全件のコピー後検証は別機能とする。

### 5.3 後日の選別・現像

HDD上の不要なファイルは後から削除してよい。削除時に必要ならRAW/JPEG/XMPやHEIC/MOVの対応を確認するが、全件の整理を義務にしない。バックアップ側に不要ファイルが残ることは許容する。

現像は保存後でもよい。元RAWを保持し、現像済みJPEGを追加してXMPを保存する。SMB上の現像が不便なら必要なファイルをMacへコピーし、同じ相対構成で作業する。更新済みXMP等をHDDへ戻す操作は通常取り込みの衝突処理と区別し、0007で対象を指定した明示的な更新手順を確認する。初期から自動上書き・双方向同期は導入しない。

### 5.4 共通APIと段階導入

コピー処理をCLIから分離し、共通APIとして呼べるようにする。GUIは後から同じ処理を利用する。HTTPサーバー、認証、ジョブDBは初期の必須範囲としない。

| 段階 | 範囲 |
|---|---|
| 0006の最小版 | 対象列挙、明示年月での配置、ローカルコピーとrsync over SSH、dry-run、上書き禁止、コピー元保持、接続先・マウント確認、一時ファイル処理、構造化結果とログ |
| 0006の直後の改善 | 撮影年月の自動分類、同名候補の内容比較とスキップ、設定値の再利用、失敗後の再実行 |
| 0013 | コピー後の全件数・容量・チェックサム等による欠損／内容一致検証 |
| 0014・0015 | 共通APIを使うGUI、バックアップの自動実行・通知 |

最小版が使える時点で初期動作確認を始める。0006全体や0013の完成を待つ必要はない。

### 5.5 結果確認とコピー元の整理

コピー結果は毎回短い要約で確認し、詳細ログは自動保存する。代表ファイルの閲覧や復元試験は導入時・変更時・定期確認で行い、毎回の取り込み手順にはしない。

Amazonと第2 HDDのバックアップは別に進める。SD・iPhone・Macのコピー元を消す場合だけ、今回分の主HDDへの保存と第2 HDDへのバックアップを確認する。写真のオフサイト保護まで必要な場合はAmazon完了も確認する。全件検証導入前は元データを保持するか、0009・0010で定める手動確認の結果を簡潔に記録して削除を判断する。Immichへの表示は原本保存の検証の代わりにしない。

## 6. Amazon Photos

- Mac版Amazon Photos Desktopで、SMBマウントした主HDDの `photo-library/` フォルダ1つをバックアップ対象に指定する。Macの `PhotoWork/` は対象にしない。年が変わっても対象指定は変えない（0008、4.1参照）。
- JPEG、HEIC、ARW、現像済みJPEGを対象とし、動画を対象外にする。動画は年月・機器別フォルダの中に静止画と混在しており対象フォルダの指定では分離できないが、アプリ側で自然に除外されることを0008で確認した。
- SMB経由のバックアップ、形式ごとの再取得（SHA-256一致）、動画除外、ローカル削除時にAmazon側が残ること、転送中の一時ファイルを取り込まないことを0008で実機確認した。
- HDDで削除した写真がAmazonに残っても整理しない。両者の完全一致を目指さない。
- SMB切断時はアプリ上に「DISCONNECTED」等の状態が明示される。再接続するとMac側のマウントは自動で戻るが、**アプリ自体はSMB復旧を自動検知せず、手動での再起動が必要**である（0008で確認）。週次のバックアップ確認では、アプリの状態表示を見て、正常表示（バックアップ完了）でなければアプリを再起動する。
- 取り込みごとの完了待ちはしない。週次のバックアップ確認時などに進捗・停滞をまとめて確認する。
- 旧Macフォルダからアップロード済みのデータがある場合は少数で挙動を確認してから切り替える。不要写真の残存を許容しても、大量の意図しない重複は避ける。
- iPhoneのAuto-Saveは無効とし、Amazonへの入口をこの経路に統一する。

iCloud+は採用しない。取り込み前のiPhone本体が唯一のコピーとなるリスクは受容し、重要な撮影をした日は早めに取り込む。

## 7. Immich

### 7.1 基本構成

- Ubuntu 64-bit上でDocker Composeを使う。
- PostgreSQLとImmichの作業データは内蔵SSDへ置く。
- `/mnt/camera_archive` をコンテナへ読み取り専用でマウントする。
- Upload LibraryではなくExternal Libraryを主に使う。
- Immichから原本の削除・整理を行わない。
- 初期は家庭内LANだけで利用し、ルーターからImmichのポートを直接公開しない。

マウントの考え方は次のとおり。

```yaml
volumes:
  - /mnt/camera_archive/photo-library:/external/photo-library:ro
```

### 7.2 RAW除外

External Libraryの除外パターンに次を設定する。

```text
**/*.ARW
**/*.arw
```

これにより、RAWは主HDD・第2 HDD・Amazon Photosに保持しながら、Immichには撮って出しJPEGや現像済みJPEGだけを表示できる。年月・機器別のフォルダ名に依存せず、拡張子で除外する。

### 7.3 段階導入

1. CPUだけで基本動作、タイムライン、検索、動画再生を確認する。
2. 小規模なテストフォルダでARW除外、HEIC、Live Photo、動画、現像済みJPEGを確認する。
3. DBバックアップと復元を確認する。
4. 問題がなければ全ライブラリをスキャンする。
5. その後、必要に応じてRTX 4060 Tiによる機械学習や動画変換の高速化を有効にする。

## 8. バックアップ

### 8.1 コピー構成

| データ | 主HDD | 第2 HDD | Amazon Photos | 評価 |
|---|---:|---:|---:|---|
| JPEG / HEIC | 正本 | バックアップ | オフサイト | 3コピー |
| ARW | 正本 | バックアップ | オフサイト | 3コピー |
| XMP | 正本 | バックアップ | なし | ローカル2コピー |
| 動画 | 正本 | バックアップ | なし | ローカル2コピー |
| 現像済みJPEG | 正本 | バックアップ | オフサイト | 3コピー |
| Immich DB・設定 | SSD | バックアップ | なし | ローカル2コピー |

第2 HDDはバックアップ時だけ接続し、完了後に取り外す。主HDDと常時接続したままにすると、誤削除、マルウェア、電源障害の同時被害を受けやすい。

動画にはオフサイトコピーがないため、火災・盗難・大規模災害では主HDDと第2 HDDを同時に失う可能性がある。現時点ではこのリスクを受容し、将来、動画の重要度や容量が増えた時点で有料クラウドまたはHDDの別拠点保管を再検討する。

### 8.2 初期のバックアップ方法

最初は主HDDの正本から第2 HDDへ、削除を伝播させない追加コピーを行う。接続と実行開始は手動とし、ファイルのコピーはコマンドでまとめて行う。写真・動画を通常ファイルのまま保存し、専用ツールなしでも取り出せる状態を優先する。

追加コピーの運用確認後、必要に応じて次のどちらかを選ぶ。

- rsyncで通常ファイルのミラーを作り、変更・削除前のファイルを日付別フォルダへ退避する。
- resticで世代管理、整合性検査、復元をまとめて行う。

現時点ではどちらかに固定しない。実際にXMPをどの程度更新するか、誤削除からどこまで戻したいか、第2 HDDの容量にどの程度余裕があるかを確認した後に決める。これは初期運用を始めるためのブロッカーではない。

最低限の対象は次のとおり。

- `/mnt/camera_archive` 全体
- ImmichのPostgreSQLダンプ
- Docker Composeファイルと `.env`
- Immichプロフィール等、原本やDBから再生成できないデータ

サムネイルと変換済み動画は原本から再生成できるため、初期はバックアップ対象外でよい。

削除済みの写真が第2 HDDに残り、全件復元時に戻ることは許容する。一方、保存後に更新するXMPや現像済みJPEGは取りこぼさないよう、0010で変更ファイルの検出と旧版の扱いを決める。取り込みCLIの「異なる同名ファイルは上書きしない」規則を、更新バックアップへそのまま適用しない。

### 8.3 頻度と検証

- 第2 HDD: 原則週1回にまとめて接続し、1コマンドでバックアップする。重要な撮影後やSDの再利用前は必要に応じて前倒しする。
- 取り込みのたびに第2 HDDの接続やAmazon完了待ちを要求しない。次回バックアップまでの保護が薄い期間は許容する。
- Immich DB: 日次ダンプをSSDに作り、第2 HDD接続時にコピーする。
- 半年に1回: 写真・動画・XMPとDBを一時領域へ実際に復元する。
- 年1回: 使用量と年間増加量を測り、主HDD・第2 HDDの容量計画を更新する。

第2 HDDは8TBとする。α7C IIは購入直後で年間増加量を予測できないため、4TB主HDDの全量バックアップ、ImmichのDBダンプ、設定ファイル、追加コピー時の余裕を確保する初期構成として決める。実運用開始から1年後、または主HDDの使用率が60%に達した時点で容量計画を見直す。

## 9. 選別・現像ツール

初期は次の無料ツールで始める。

- Finder / Quick Look / QuickTime Player: 写真・動画の選別。
- darktable: 評価、非破壊RAW現像、XMP保存、JPEG書き出し。
- Sony Imaging Edge Desktop: Sony純正の色や処理が必要な場合の補助。
- macOS イメージキャプチャ: iPhoneからの原本取り込み。

darktableの操作やRAW+JPEGの管理が継続的な負担になった場合に、Lightroom Classicを再検討する。現像ソフト内だけに編集内容を閉じ込めず、XMPサイドカーと完成JPEGをファイルとして残す。

## 10. 環境構築の再現性

新しいPCへの入れ替えや、故障・OS再インストールからの復旧に備え、環境構築の作業を再現できる形で残す。手順の正本は [setup/](setup/)、自動化した実体は [scripts/](../scripts/) に置く。変更プランの `plan.md` と `validation.md` は当時の記録であり、再構築の手順としては使わない。

### 10.1 進め方

作業後に手順を清書するのではなく、作業時にスクリプトを書いて実行し、実機で動いたものを残す。実機で動かしていないスクリプトは完成として扱わない。自動化できない操作は手順書へ手動手順として明記する。

| 区分 | 例 | 扱い |
|---|---|---|
| 自動化する | fstabによるマウント、ディレクトリと権限、Samba設定、Docker Composeでのimmich起動、Macのツール導入、SSH・rsyncの取り込み設定とSMBマウント | `scripts/` |
| 手動で行う | HDDの物理接続とフォーマット判断、Amazon Photos Desktopのログインと対象指定、みてね等のアカウント操作 | `docs/setup/` に手動手順として記載 |
| 確認する | マウント状態、SSH・rsyncでの安全な書き込み、SMBの読み書き、未マウント時に書き込めないこと、Immichの起動とライブラリ参照 | 確認用スクリプトとし、プランの完了条件に対応づける |

### 10.2 スクリプトの規約

- 冪等とし、再実行しても既存の設定やデータを壊さない。
- dry-runを備え、変更内容を事前に確認できるようにする。
- 既存の設定やデータを無断で上書きせず、失敗を成功として扱わない。取り込みCLIと同じ保護を環境構築にも適用する。
- ホスト固有の値（HDDのUUID、マウント先、共有名、利用アカウント）は `scripts/hosts/*.env` に分離し、スクリプトへ直書きしない。パスワード等の秘密情報はコミットせず、実行時に入力する。

### 10.3 対象範囲

Ubuntu側は主HDDのマウントと共有、SSH・rsyncの受入れ、Immichとバックアップまでを対象とする。Mac側は取り込みと現像に使うツール、SSH・rsyncの送信設定、SMBマウント、取り込みCLIの導入を対象とする。どちらのPCを入れ替える場合でも、必要な手順を選んで実行できるよう、`docs/setup/` をホスト別に分ける。

環境を変更するプランは、その完了時に `docs/setup/` と `scripts/` を現在の構成へ反映する。最初の整備は0005で行う。

## 11. 導入ロードマップ

状態と依存関係は [plans/roadmap.md](plans/roadmap.md) を正とする。

1. 0005で主HDDのマウントとSMBを整える。SMBはAmazon Photosと必要時の参照用に残す。0006で構築済みのSSH接続を使ったrsync転送を整える。あわせて `docs/setup/` と `scripts/` に反映し、最小CLIはローカル試験から先行できる。
2. 最小CLIで0007の取り込み・閲覧確認と0008のAmazon確認を進める。0006の自動分類・同一スキップも続けて追加する。
3. 0009で実運用規模の取り込みを通して日常運用手順を確定し、0010で週次バックアップと原本復元を確認する。両経路自体の通し確認は0006・0007で済んでいる。
4. 0011・0012でImmichを導入し、表示とDB復元を確認する。0007の任意の選別・現像検証は導入の前提にしない。
5. 0013の全件検証はコピー機能が動いた後に追加し、Immich完了を待たず進めてよい。
6. バックアップ自動実行とGUIは別途追加する。

固定の手動運用期間や形式ごとに一律10組の試験を要求しない。代表形式と同名衝突・日時不明・切断などの具体的なケースで判断する。

## 12. 主なリスクと対応

| リスク | 対応 |
|---|---|
| 主HDD故障 | 第2 HDDとAmazonへバックアップする |
| バックアップ前の故障 | 間隔中のリスクを許容し、コピー元の整理は別途判断する |
| 動画のオフサイトコピーがない | 現時点では受容し、必要になった時点で再検討する |
| 誤削除の伝播 | 削除同期を使わない。復元時に不要写真も戻ることを許容する |
| 保存後の更新漏れ | XMP・現像済みJPEGの変更を0010のバックアップ対象に含める |
| コピー途中のファイルを閲覧側が取り込む | 一時ファイルの扱いをCLIと各アプリの実機試験で確認する |
| Immich障害・DB喪失 | 原本は通常ファイルで保持し、DB・設定のバックアップと復元を確認する |
| ファイル移動・改名による閲覧側への影響 | 年月配置を維持し、不要な移動・改名をしない |
| 自動化による誤処理 | 上書き禁止、失敗報告、元データ保持を処理側で守る |
| PC入れ替え・OS再インストール時の再構築 | 環境構築をスクリプトと手順書として残し、環境変更のたびに更新する |

## 13. 後続で判断する事項
