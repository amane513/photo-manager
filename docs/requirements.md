# 要件定義: photo-manager

Sony α7C II で撮影したデータを、SDカードから外付けHDDへ安全に取り込むためのツールの要件定義。
2026-08-22 のヒアリングで合意した内容を記録する。**実装はこの文書を仕様として進める。**

---

## 1. 目的とスコープ

**目的**: SDカード → 外付けHDD への取り込みを自動化し、検証済みであることを保証する。

**スコープに含む**
- SDカードから HDD への取り込み（コピー・リネーム・月別配置・検証）
- 取り込み済みデータの整合性検証（ビット腐敗検出）
- 2台目HDDへのミラーリング

**スコープに含まない**
- SDカードの消去（後述のとおり、意図的に実装しない）
- スマートフォンからの取り込み（フォルダ構成だけ用意し、取り込み手段は将来検討）
- 現像・編集・カタログ管理

## 3. ワークフロー

```
1. カードリーダーとHDDを同時接続
2. photo-import を実行
     - 事前チェック（HDD確認・容量確認）
     - EXIF から撮影日時を取得
     - 月フォルダへコピー（リネームしながら）
     - sha256 で全件検証
     - checksums.tsv へ記録
3. 全対象ファイルの取り込み完了を確認 → SDカードを自動 eject
4. 「カメラ内フォーマットを推奨」と表示（スクリプトは消さない）
5. 手動でカメラに戻してカメラ内フォーマット
```

**Mac内蔵SSDを経由するステージングは行わない。** SDカード → HDD へ直接コピーする。

Amazon Photos は HDD 上の `Camera/` と `Phone/` をバックアップ対象とし、**ファイル種別フィルタを「写真のみ」に設定**する（ARWは写真として扱われバックアップされる／動画は対象外）。バックアップモード＝一方向アップロード。

## 4. HDDのフォルダ構成

```
/Volumes/CameraArchive_M/
├── Camera/                          ← α7C II（将来のカメラも同じ場所）
│   └── 2026/
│       └── 2026-08/                 ← 写真・RAW・動画を混在
├── Phone/                           ← スマートフォン（将来）
│   └── 2026/
│       └── 2026-08/
└── _photo-manager/                  ← 管理ファイル（Amazon Photos 対象外）
    └── checksums.tsv
```

**決定事項**

- **機材名は「役割名」を使う**（`Camera` / `Phone`）。`Camera_a7C2` のような機種名は使わない
- **写真・RAW・動画を同一フォルダに混在させる**。種別によるフォルダ分割は行わない
- **月単位で管理する**。イベント名は付与しない。日付ごとの分割もしない
- **年フォルダを設ける**（`2026/2026-08/`）
- 1回のSDカードに複数月のデータがある場合、**月ごとに自動で振り分ける**
- 管理ファイルは `_photo-manager/` に置き、`Camera/` `Phone/` の外に出す

> **注意**: Amazon Photos はローカルのフォルダパスを追跡するため、**アップロード開始後に構成やファイル名を変更すると、大量の再アップロードや重複が発生しうる**。フォルダ構成と命名規則は、アップロードを開始する前に確定させること。

## 5. ファイル命名規則

```
<YYYYMMDD>_<HHMMSS>_<原ファイル名>.<原拡張子>
```

**例**

```
Camera/2026/2026-08/
├── 20260818_192925_DSC00020.JPG
├── 20260819_191210_DSC00105.ARW    ← ペアは必ず隣接（A < J）
├── 20260819_191210_DSC00105.JPG
├── 20260818_202220_C0001.MP4
└── 20260818_202220_C0001M01.XML    ← 動画の直後に並ぶ
```

**規則**

| 項目 | 決定 |
|---|---|
| 原ファイル名 | **必ず残す**。連写で同一秒に複数枚来ても衝突しない。カメラ番号も失わない |
| 拡張子 | 元のまま（`.JPG` `.ARW` `.MP4` `.XML`）。大文字小文字も変換しない |
| タイムゾーン | **EXIFの値をそのまま使う（現地時刻）**。UTCへの正規化はしない |
| 動画のサイドカーXML | 対応するMP4と同じプレフィックスを付ける |

**検証済みの事実**
- JPG と ARW の `DateTimeOriginal` は **52ペア全てで完全一致**。ペアが分離することはない
- ファイル名は28文字程度に収まる

| SD上のパス | 扱い | 宛先 |
|---|---|---|
| `DCIM/**/*.JPG` | ✅ 取り込む | `Camera/YYYY/YYYY-MM/` |
| `DCIM/**/*.ARW` | ✅ 取り込む | `Camera/YYYY/YYYY-MM/` |
| `PRIVATE/M4ROOT/CLIP/*.MP4` | ✅ 取り込む | `Camera/YYYY/YYYY-MM/` |
| `PRIVATE/M4ROOT/CLIP/*.XML` | ✅ 取り込む | `Camera/YYYY/YYYY-MM/` |
| `PRIVATE/M4ROOT/THMBNL/*.JPG` | ❌ 除外 | サムネイル。`.JPG` なので Amazon Photos のタイムラインを汚す |
| `PRIVATE/M4ROOT/SUB/` | ❌ 除外 | プロキシ動画（現在は空）。派生データ |
| `PRIVATE/M4ROOT/GENERAL/`, `TAKE/` | ❌ 除外 | 管理データ |
| `PRIVATE/M4ROOT/MEDIAPRO.XML` | ❌ 除外 | クリップ一覧。フォーマットで再生成される |
| `PRIVATE/DATABASE/DATABASE.BIN` | ❌ 除外 | カメラの管理DB |
| `AVF_INFO/` | ❌ 除外 | カメラの管理DB |
| `._*` (AppleDouble) | ❌ 除外 | macOSが書いたゴミ。**実測で6個検出** |
| `.DS_Store`, `.Spotlight-V100`, `.fseventsd`, `.Trashes` | ❌ 除外 | macOSが書いたゴミ |

**動画のサイドカーXMLを取り込む理由**（`CLIP/C0001M01.XML`, 約2KB）

MP4側のメタデータには存在しない情報を持つことを実測で確認した。

```xml
<CreationDate value="2026-08-18T20:22:20+09:00"/>   ← タイムゾーン付きの撮影日時
<Lens modelName="FE 20-70mm F4 G"/>                 ← レンズ名（MP4には無い）
<Item name="CaptureGammaEquation" value="rec709"/>  ← ガンマ・色域
```

## 7. 撮影日時の判定

**優先順位**

| 対象 | 判定順 |
|---|---|
| 静止画 (JPG/ARW) | 1. EXIF `DateTimeOriginal` → 2. ファイル更新日時 |
| 動画 (MP4) | 1. **サイドカーXMLの `<CreationDate>`**（タイムゾーン付き） → 2. QuickTime `CreateDate` + `TimeZone` タグ → 3. ファイル更新日時 |
| サイドカーXML | 対応するMP4の判定結果を継承 |

**注意点**

- **動画のファイル更新日時は録画「終了」時刻**（実測で17秒差）。必ず録画開始時刻を使う
- MP4 の `CreateDate` はUTC保存。exiftool の `-api QuickTimeUTC=1` は**取り込んだMacのタイムゾーン**で変換するため、海外で撮影して日本で取り込むとずれる。サイドカーXMLの `+09:00` 付き日時を優先することでこれを回避する
- MP4 `C0001.MP4` に対応するXMLは、同じディレクトリの `C0001M01.XML` とする。大文字小文字を区別せず照合するが、対応候補が複数ある場合は曖昧として失敗する
- XMLが存在しないMP4は、MP4単体の判定順で取り込む。対応するMP4が存在しない孤立XMLは取り込まず、**失敗**として記録する
- XMLが壊れている場合、MP4はMP4側のフォールバックで判定する。XMLは対応するMP4の判定結果を継承して保存し、非阻害警告を出す
- **どの方法でも日時が取得できない対象ファイルは、コピーせず失敗として記録する**（推測した日付でどこかに置かない）

**実測**: 実写真78枚は全て `DateTimeOriginal` を保持していた。ファイル更新日時へのフォールバックは純粋な保険。

## 8. 重複・再取り込み時の挙動

宛先パスが撮影日時から決定的に決まるため、**ファイルシステム自体が索引として機能する**。重複判定のための状態（インデックス）を持たない。

**判定フロー**

```
1. 宛先パスに何も無い          → コピーする
2. 同名あり・サイズ一致        → sha256 を照合
     ├ 一致   → スキップ（取り込み済み）。checksums.tsv に有効な行がなければ検証後に補完
     └ 不一致 → 別名保存 + 警告
3. 同名あり・サイズ不一致      → 別名保存 + 警告
```

サイズを先に比較するのは高速化のため。**新しいSDカードからの通常の取り込みでは、同名ファイルが存在しないため重複判定のハッシュ計算は1回も走らない。**

**別名保存の規則**: `20260818_193253_DSC00023_2.JPG`（`_2`, `_3`, ... と採番）。採番候補も同じ重複判定を行い、既存ファイルを上書きしない。

**取り込み対象のデータファイルは絶対に上書きしない。** 管理ファイルのアトミック更新はこの限りではない。

**受け入れたトレードオフ**

> HDD上で写真を削除した後、同じSDカードから再実行すると、その1枚が復活する。

インデックスに取り込み履歴を持てば回避できるが、そのために状態管理という壊れうる仕組みを常時抱えることになる。運用が「取り込み → 検証OK → すぐカメラ内フォーマット」である以上、この窓は短いため受け入れる。

## 9. コピーと検証

**手順（1ファイルごと）**

```
1. 宛先に `<最終ファイル名>.part` という一時名で排他的に新規作成する。既に存在する場合は上書きしない
2. 元ファイルを読みながら、同時に sha256 を計算しつつ書き込む
     → SDカードの読み出しは1回で済む
3. 一時ファイルを flush / fsync して閉じ、書き込んだファイルを読み直して sha256 を再計算
4. 元ハッシュと一致し、コピー中に元ファイルのサイズ・更新日時が変化していないことを確認する
     ├ 不一致・変化あり → .part を削除し、失敗として記録して次のファイルへ
     └ 一致・変化なし → 次へ
5. 元ファイルの更新日時を一時ファイルに反映する。失敗した場合は .part を削除し、失敗として記録する
6. `.part` を、既存の正式ファイルを置換できない方法（同一ボリューム内でのhard link作成と `.part` のunlink等）でアトミックに正式化し、宛先ディレクトリを fsync する。正式化時に同名ファイルが出現していた場合は上書きせず、重複判定と採番をやり直す
7. `checksums.tsv` に追記して flush / fsync する
```

正式ファイルへの確定後、チェックサム追記前に停止した場合、正式ファイルは削除しない。再実行時にSD上の元ファイルと正式ファイルを照合し、一致した場合だけ不足するチェックサム行を補完する。補完が完了するまでその実行は成功とみなさず、SDカードをejectしない。

**ハッシュアルゴリズム: sha256**

- blake2b は4倍高速だが、macOS標準CLIで検証できない
- sha256 なら `shasum -a 256 <file>` で手動照合できる
- **アルゴリズム名を `checksums.tsv` に記録し、将来変更可能にしておく**

**rsync は使用しない。** この環境の rsync は 2.6.9（2006年版）であり、Homebrew版を追加すると「外部依存は最小限」の原則に反する。また `rsync --checksum` は「転送要否の判定」にチェックサムを使うだけで、**転送後の検証ではない**。

**SDカードは読み取り専用として扱う。** スクリプトは SDカード上のファイルを一切変更・削除しない。

## 10. エラー処理

**事前チェック（1つでも失敗したら、何もせずに中止する）**

- 宛先ボリュームがマウントされている
- **ボリュームUUIDが設定値と一致する**（同名HDDの取り違え防止。2台目導入時に効く）
- 宛先が書き込み可能
- 空き容量 ≧ 取り込み予定サイズ × 1.1
- exiftool が実行可能（絶対パスで確認）
- 取り込み元にDCIMまたはPRIVATE/M4ROOTが存在する

自動検出では、`/Volumes` 直下にあり `DCIM` または `PRIVATE/M4ROOT` を持つ、宛先とは異なるボリュームを候補とする。候補が0件または複数件なら推測で選ばず、候補一覧を表示して中止する。

**実行中のエラー**

- ファイル単位のエラー（日時不明・孤立XML・読み取り失敗・検証不一致・容量不足）は**失敗として記録して継続**する
- 最後にサマリを表示（コピー成功 / スキップ / 警告 / 失敗）
- 失敗が1件でもあれば非ゼロで終了する
- 警告は、取り込み自体が完了した「非阻害警告」と、未取り込みを伴う「失敗」に分類する。別名保存や、MP4から日時を継承できた壊れたXMLは非阻害警告とする

**ejectの条件**

- 検出した全対象ファイルが「コピーと検証に成功」または「宛先の同一内容を確認済み」のいずれかである
- 必要な全ファイルについて `checksums.tsv` に有効なレコードがある
- 失敗が0件である（非阻害警告だけならejectしてよい）
- dry-runではejectしない

上記を1つでも満たさない場合は、設定にかかわらずejectせず、カメラ内フォーマットを促す成功メッセージも表示しない。

**中断からの復旧**

- 検証を通ったファイルだけが正式名になるため、**不完全なファイルが正式名で残らない**。中断時には `.part` が残ることがある
- 宛先ごとに `_photo-manager/import.lock` を `fcntl.flock` でロックして排他制御し、同じ宛先に対する import / verify / mirror を同時実行しない。ロックファイルは常設し、ファイルが存在すること自体を実行中の判定には使わない。OSロック取得に失敗したら何も変更せず中止する
- ロック取得後、起動時に「有効な取り込み先ファイル名 + `.part`」に一致するツール所有の一時ファイルだけを削除する。任意の `*.part` を一括削除しない
- 再実行すれば、取り込み済みはスキップされ、続きから進む

## 11. ログとチェックサム

| 種類 | 置き場所 | 内容 |
|---|---|---|
| 実行ログ | `~/Library/Logs/photo-manager/import-YYYYMMDD-HHMMSS.log` | 何をどこにコピーし、何をスキップし、何が失敗したか |
| チェックサム | `/Volumes/CameraArchive_M/_photo-manager/checksums.tsv` | 相対パス / アルゴリズム / ハッシュ値 / サイズ / 撮影日時 / 取り込み日時 |

- 実行ログは macOS の慣習に従い `~/Library/Logs` に置く。**HDDが未接続でも読める**
- チェックサムは HDD 上に置く。**データと一緒に旅する**ので、Mac買い替えや別のMacからの取り込みでも一貫する。2台目HDDにも同じものが同期される
- チェックサムは論理的に追記のみ。UTF-8、タブ区切り、LF改行とし、パスはHDDルートからのPOSIX相対パスで記録する。フィールドの引用・エスケープにはPython `csv` のTSV方言を使う
- 同一相対パスには正常なレコードを1件だけ持つ。再取り込みで同一レコードを重複追記しない
- 起動時に台帳を全行検査する。末尾の書きかけレコードだけは、壊れた原本を実行ログと同じ場所へコピー退避できた場合に限り、完全な行だけを一時ファイルへ書き、fsync後にアトミック置換して修復できる。途中の行が壊れている場合は自動修復せず失敗する
- 正式ファイルがあるのにレコードがない場合は、SD上の元ファイルとの一致を確認できるimport時に限り補完できる。元ファイルがない場合は自動的に正しいハッシュを採用したことにせず、verifyで「未登録」として失敗する
- チェックサムファイル自体の構文不正は検証失敗とし、成功扱いしない
- 10年分でも数MB程度を想定する

**`photo-verify` の判定**

- 指定範囲の全レコードについて、実ファイルの存在・サイズ・指定アルゴリズムのハッシュを検証する
- レコードにあるファイルの欠落、サイズ不一致、ハッシュ不一致、重複レコード、台帳の構文不正は失敗とする
- `Camera/` の指定範囲にある正式ファイルのうち、レコードがないものは「未登録」として失敗する
- `.part` と `_photo-manager/` は未登録ファイル検査の対象外とする。その他の余分なファイルは警告する
- `--month` と `--year` は撮影日時欄ではなく、相対パスの `Camera/YYYY/YYYY-MM/` を対象範囲とする。両方省略時は全件を検証する

## 12. 設定

`~/.config/photo-manager/config.ini`（INI形式 / `configparser` = 標準ライブラリ）

JSONを採らないのはコメントが書けないため。TOMLは `tomllib` が Python 3.11+ でないと標準で読めない（この環境は3.9）。

```ini
[dest]
root        = /Volumes/CameraArchive_M
volume_uuid = EEE32629-5947-39D0-8842-DEA8A879BDF2
subdir      = Camera

[source]
# 省略時は /Volumes 配下から DCIM を持つボリュームを自動検出する
# root = /Volumes/CameraSD

[mirror]
# 2台目HDD（導入後に設定）
# root        =
# volume_uuid =

[tools]
exiftool = /opt/homebrew/bin/exiftool

[options]
hash_algorithm     = sha256
free_space_margin  = 1.1
eject_after_import = true
```

- 実行時に変更する必要があるパス、Volume UUID、ejectの有無はCLIフラグで上書きできる。その他の値は設定ファイルで変更する
- リポジトリには `config.example.ini` を置き、実体は `.gitignore` に入れる
- 初期実装で受け付ける `hash_algorithm` は `sha256` のみとし、その他の値は設定エラーにする。台帳にアルゴリズム列を持たせることで、将来の移行を可能にする

## 13. CLI仕様

```
photo-import  [--dry-run] [--source PATH] [--dest PATH --dest-volume-uuid UUID] [--no-eject] [--config PATH] [-v]
photo-verify  [--month YYYY-MM | --year YYYY] [--dest PATH --dest-volume-uuid UUID] [--config PATH] [-v]
photo-mirror  [--to PATH --to-volume-uuid UUID] [--dry-run] [--config PATH] [-v]
```

| コマンド | 動作 |
|---|---|
| `photo-import` | SDカード → HDD へ取り込み、検証、checksums.tsv 追記、10章のeject条件をすべて満たした場合だけeject |
| `photo-verify` | checksums.tsv と実ファイルを突き合わせ、**HDDのビット腐敗を検出**する |
| `photo-mirror` | HDD1 → HDD2 へ同期し、checksums.tsv で検証する |

**状態を変更する `photo-import` と `photo-mirror` は `--dry-run` に対応する。** 実際に何が起きるか（どのファイルがどこにどんな名前でコピーされるか）を事前に一覧表示する。`photo-verify` は常に読み取り専用なので `--dry-run` を持たない。dry-run後に元ファイル・設定・空き容量・宛先内容が変化しない限り、実行時にも同じ計画を使用する。実行開始時には事前チェックと衝突判定を再実施するため、外部状態が変化した場合は安全側に中止または再採番できる。

`--dest` は `--dest-volume-uuid` と同時に指定しなければならず、片方だけなら使用方法エラーとする。`--to` と `--to-volume-uuid` も同様とする。設定ファイルのパスを使う場合は、対応する設定済みUUIDを必ず照合する。CLIによるパス指定を理由にUUID検証を省略しない。

**終了コード**

- `0`: 対象がすべて成功（非阻害警告を含む場合がある）
- `1`: 取り込み・検証・ミラーの失敗、未登録、データ不一致
- `2`: 使用方法・設定・事前チェックの誤り

### `photo-mirror` の非破壊同期仕様

1. コピー元とコピー先のパス・Volume UUID・書き込み可否・容量を確認し、同一ボリュームなら中止する
2. UUIDの辞書順で両ボリュームのロックを取得し、取得できなければ何も変更せず中止する
3. コピー元の `checksums.tsv` を構文検査し、転送対象となる全ファイルを台帳と照合する。欠落・未登録・不一致が1件でもあれば、手順2の管理用ロック以外はコピー先へ何も書かず中止する
4. コピー先にファイルがない場合だけ `.part` へ排他的に新規作成してコピーし、コピー元台帳のハッシュと再読込ハッシュが一致した後に、既存ファイルを置換できない方法で正式化する
5. コピー先に同名ファイルがある場合は台帳と照合する。一致ならスキップし、不一致なら**上書きせず**失敗する
6. コピー元にないコピー先ファイルは削除せず、余分なファイルとして警告する。したがって本コマンドは削除を伴わない非破壊ミラーである
7. 全管理対象ファイルがコピー先で検証できた後、コピー元の `checksums.tsv` をコピー先の一時ファイルへ複写・再読込検証し、管理ファイルに限ってアトミック置換する
8. 最後に、コピー元台帳に記録された全管理対象がコピー先でも一致することを検証し、不一致があれば非ゼロで終了する。コピー先だけにある余分なファイルはこの最終検証の対象外とし、手順6の警告として扱う

コピー元で既に破損したデータを正常なコピー先へ伝播させないことを最優先とする。コピー先の不一致ファイルを自動修復・上書きする機能は設けず、ログに両方のパスと期待値・実測値を出して手動判断を求める。

**SDカードの消去機能は実装しない。** `--delete` 相当のフラグも用意しない。検証OK後に以下を表示するだけ。

```
✓ 134件を取り込み、全件の検証に成功しました（スキップ 0 / 警告 0 / 失敗 0）
  SDカードは安全に取り外せます（eject済み）
  → カメラに戻して「カメラ内フォーマット」を実行することを推奨します
```

カメラ内フォーマットを推奨するのは、Sonyの管理DB（`PRIVATE/DATABASE/`, `AVF_INFO/`）を正しく作り直すため。Mac側での消去より安全。

## 14. 設計原則

- **SDカードは読み取り専用として扱う。** スクリプトから SDカード上のファイルを削除・変更しない
- **破壊的操作はデフォルト無効。** 削除機能自体を実装しない
- **冪等性。** 同じコマンドを2回実行しても壊れない
- **ドライラン。** `--dry-run` で実行前に全件の挙動を確認できる
- **検証が通るまで何も消さない**
- **外部依存は最小限。** Python標準ライブラリ + exiftool のみ
- **中断されても不完全なデータを正式ファイルとして扱わず、次回実行で検出・復旧できる**

**実装言語: Python 3.8+（標準ライブラリのみ）**

`/usr/bin/python3`（3.9.6）でも pyenv の 3.10.13 でも動作すること。使用モジュールは `pathlib` / `hashlib` / `subprocess` / `shutil` / `argparse` / `configparser` / `datetime` / `csv` 程度。外部パッケージは使わない。

**exiftool は依存として許容する。** EXIF/QuickTimeメタデータの自前パースは技術的には可能だが、**パーサのバグは「写真が間違った月フォルダに入る」という形で静かに現れる**。20年以上枯れている exiftool に任せるほうが安全。「外部依存は最小限」は「ゼロ」ではない。

## 15. 主要な決定の根拠

意思決定の理由を記録する。詳細は必要に応じて `docs/decisions/` にADRとして切り出す。

**なぜ全ファイルに日時プレフィックスを付けるのか**

Sonyの**動画クリップ番号はカードをフォーマットするとC0001にリセットされる**。運用が「取り込み後にカメラ内フォーマット」であるため、同じ月に2回撮影すると `C0001.MP4` が確実に衝突する。静止画（DSC番号）は連番設定なら衝突しないが、全ファイルに付けることで以下が同時に得られる。

- **カメラ設定（連番/リセット）への依存が消える**
- 写真と動画を同じフォルダに混在させても、**ファイル名順＝時系列順**になる
- 将来2台目のカメラを追加して同じ撮影秒・原ファイル名が重なっても、別名保存により上書きせず両方を保持できる

原ファイル名を残すため、連写で同一秒に複数枚来ても衝突しない。

**なぜ機材名に機種名を使わないのか**

`Camera_a7C2` のように機種名を含めると、買い替えのたびに階層が増殖し、**同じイベントの写真が複数フォルダに分裂する**。役割名（`Camera` / `Phone`）なら10年後も構造が変わらない。機種情報はEXIFとファイル名に残るため、何も失われない。

**なぜ写真と動画を同じフォルダに混在させるのか**

当初は Amazon Photos のバックアップ対象から動画を外すためにフォルダを分ける計画だったが、**Amazon Photos はファイル種別フィルタで動画を自動除外できる**ことが判明したため、分離の根拠が消えた。混在させることで、同じイベントの写真と動画が1箇所にまとまる。

**なぜ重複判定にインデックスを持たないのか**

宛先パスが撮影日時から決定的に決まるため、ファイルシステム自体が索引になる。状態を持たない設計はズレて壊れることがない。チェックサムは記録するが、それは**重複判定ではなく長期的な整合性検証（ビット腐敗検出）のため**であり、目的が異なる。

**なぜ Python なのか**

- `hashlib` により**コピーしながら同時にハッシュを計算できる**ため、SDカードの読み出しが1回で済む（シェルなら2回。128GB満杯で約11分の差）
- 最悪の失敗モードは「コピーに失敗しているのに成功と報告する」ことであり、シェルはこれを見落とす経路が多い（コマンド置換内のエラー、パイプの中間、サブシェル、`set -e` の例外規則）。例外と `try/finally` なら構造的に守られる
- 標準ライブラリのみで足りるため、外部依存は増えない

**なぜSDカードの物理ロックスイッチを使わないのか**

ロックすれば macOS による書き込み（`._*` 等）を防げるが、**解除を忘れると撮影本番で撮れない**。一方、防げるのは数KBのゴミだけで写真データは傷つかず、SDはどうせカメラでフォーマットする。**リスクが非対称であり、割に合わない。** スクリプト側で `._*` と `.DS_Store` を除外することで対応する。

**なぜ最初は手動コマンドなのか**

`launchd` でSDマウント時に自動起動させると、HDD未接続のまま挿したときに毎回失敗し、4TBへの書き込みが意図しないタイミングで走る。まず手動で動かして信頼できるようになってから自動化する。plistのテンプレートは同梱し、後から有効化できるようにする。
**自動化する場合、`exiftool` は `/opt/homebrew/bin` にあり最小PATHからは見えないため、絶対パス指定が必須。**

## 17. 既知のリスクと将来課題

**動画のバックアップ（対応方針: 2台目HDDを導入）**

Amazon Photos は動画が5GB制限のため実質アップロードできない。実測で1080p60は約9GB/時であり、**運動会1回で5GBを使い切る**。したがって動画はHDD 1コピーのみとなる。

対応として**2台目HDDを購入し、`photo-mirror` で同期する**。可能であれば2台目を実家や職場に置き、年数回持ち帰って同期することで、火災・盗難にも対応できる。写真とRAWは Amazon Photos でオフサイト化されるため、**2台目HDDの主目的は動画**となる。

`photo-import` の宛先は単一とし、2台目へは `photo-mirror` で別途同期する。SDカードから2台へ同時にコピーすると、SDを2回読むため遅く、カードを長く占有するため。

**その他**

- 静止画のファイル番号は9999で一周する（年2000枚なら約5年後）。日時プレフィックスがあるため衝突はしないが、番号の重複は発生する
- スマートフォンからの取り込み手段は未検討。`Phone/` ツリーの構成だけ先に確定してある
- HFS+ は大文字小文字を区別しないため、拡張子の大小が混在しても衝突する。現状カメラは常に大文字を出力するため問題ない
