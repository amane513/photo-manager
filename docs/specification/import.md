# 取り込み仕様

この文書は `photo-import` の対象列挙、撮影日時、命名、コピー、検証、エラー処理、eject条件を定める。

## 取り込み対象

| SDカード上のパス | 扱い |
|---|---|
| `DCIM/**/*.JPG` | 取り込む |
| `DCIM/**/*.ARW` | 取り込む |
| `PRIVATE/M4ROOT/CLIP/*.MP4` | 取り込む |
| `PRIVATE/M4ROOT/CLIP/*.XML` | 対応するMP4のサイドカーとして取り込む |
| `PRIVATE/M4ROOT/THMBNL/*.JPG` | サムネイルのため除外 |
| `PRIVATE/M4ROOT/SUB/` | プロキシ動画のため除外 |
| `PRIVATE/M4ROOT/GENERAL/`, `TAKE/`, `MEDIAPRO.XML` | カメラ管理データのため除外 |
| `PRIVATE/DATABASE/`, `AVF_INFO/` | カメラ管理データのため除外 |
| `._*`, `.DS_Store`, `.Spotlight-V100`, `.fseventsd`, `.Trashes` | OS管理データのため除外 |

動画サイドカーXMLは、タイムゾーン付き撮影日時のほか、レンズ、ガンマ、色域などMP4にない情報を持つため保存する。

取り込み元を自動検出する場合は、`/Volumes` 直下にあり、`DCIM` または `PRIVATE/M4ROOT` を持つ、宛先とは異なるボリュームを候補とする。候補が0件または複数件なら推測で選ばず中止する。

## 撮影日時

判定順は次のとおり。

| 対象 | 判定順 |
|---|---|
| JPG / ARW | EXIF `DateTimeOriginal`、ファイル更新日時 |
| MP4 | サイドカーXMLの `<CreationDate>`、QuickTime `CreateDate` + `TimeZone`、ファイル更新日時 |
| サイドカーXML | 対応するMP4の判定結果を継承 |

- MP4 `C0001.MP4` に対応するXMLは、同じディレクトリの `C0001M01.XML` とする。大文字小文字を区別せず照合し、候補が複数なら曖昧として失敗する。
- XMLがないMP4はMP4側のフォールバックで処理する。
- 孤立したXMLは取り込まず、失敗として記録する。
- XMLが壊れている場合、MP4はMP4側のフォールバックを使う。XMLはMP4の日時を継承して保存し、非阻害警告を出す。
- QuickTimeのnaiveな `CreateDate` はUTCとして解釈し、`TimeZone` のオフセットへ変換する。詳細は [ADR 0004](../decisions/0004-quicktime-capture-time.md) を参照する。
- 現地の壁時計値をファイル名と月フォルダに使い、UTCへ正規化しない。
- ファイル更新日時は動画の録画終了時刻になりうるため、最後のフォールバックに限る。
- どの方法でも日時を取得できない対象は、推測せずコピーを失敗させる。

## 命名と配置

```text
<subdir>/<YYYY>/<YYYY-MM>/<YYYYMMDD>_<HHMMSS>_<original-name>.<original-extension>
```

例:

```text
Camera/2026/2026-08/20260819_191210_DSC00105.ARW
Camera/2026/2026-08/20260819_191210_DSC00105.JPG
Camera/2026/2026-08/20260818_202220_C0001.MP4
Camera/2026/2026-08/20260818_202220_C0001M01.XML
```

- 原ファイル名と拡張子の大文字小文字を保持する。
- JPG/ARWペアとMP4/XMLペアには同じ日時プレフィックスを付ける。
- 原ファイル名を残すことで、同一秒の連写でも衝突を避ける。
- カードのフォーマットで動画番号がリセットされても、日時プレフィックスによって通常の衝突を避ける。

## 重複と競合

宛先パスを索引として使い、取り込み履歴のための別インデックスは持たない。

1. 宛先に同名ファイルがなければコピーする。
2. 同名かつ同サイズならsha256を比較する。
3. 内容が一致すればスキップし、有効な台帳レコードがなければ検証後に補完する。
4. サイズまたは内容が違えば `_2`, `_3`, ... を原ファイル名の末尾へ付け、空いている候補を同じ規則で調べる。
5. 採番中に外部から同名ファイルが現れた場合も上書きせず、再計画する。

HDD上で取り込み済みファイルを削除した後、同じSDカードから再実行するとそのファイルは復活する。この挙動は、壊れうる取り込み履歴インデックスを持たないこととのトレードオフとして受け入れる。

## コピーと検証

1ファイルごとに次の順で処理する。

1. `<archive>/_photo-manager/tmp/<final-name>.part` を排他的に新規作成する。既存の一時ファイルは上書きしない。
2. 元ファイルを読みながら一時ファイルへ書き、同時にsha256を計算する。
3. 一時ファイルをflushし、媒体への同期を試みて閉じる。
4. 一時ファイルを開き直してsha256を再計算し、元ハッシュと比較する。
5. コピー中に元ファイルのサイズまたはmtimeが変化していないことを確認する。
6. 元のmtimeを一時ファイルへ反映する。
7. 同一ボリューム内のhard linkで正式名を排他的に公開し、一時ファイルをunlinkする。親ディレクトリも同期する。
8. `checksums.tsv` にレコードを追記し、同期する。

検証不一致や元ファイルの変化があれば、公開前の一時ファイルを削除して失敗として記録する。正式化後、台帳追記前に停止した場合は正式ファイルを削除しない。再実行時にSDカード上の元ファイルとの一致を確認できた場合だけ台帳を補完する。

sha256を使用するのは、macOS標準の `shasum -a 256` で独立して確認でき、想定する媒体速度に対して十分だからである。

## 事前チェック

状態を変更する前に、少なくとも次を確認する。

- 宛先がマウントされ、設定したVolume UUIDと一致する
- 宛先が書き込み可能でhard linkに対応する
- 空き容量がコピー予定サイズに設定した余裕率を掛けた値以上である
- 設定した `exiftool` が実行可能である
- 取り込み元に `DCIM` または `PRIVATE/M4ROOT` がある
- 既存台帳が読み取り可能で、計画作成に必要な状態を安全に解釈できる

事前チェックが失敗した場合は、データ、台帳、一時ファイルを変更せず終了する。ロック取得後には、外部状態の変化に備えて計画と必要容量を再確認する。

dry-runは読み取り専用で対象、宛先、競合、失敗予定、必要容量を表示する。ロックファイル作成、書込プローブ、台帳修復、一時ファイル掃除、コピー、ejectは行わない。

## エラー、中断、eject

- 日時不明、孤立XML、読取り失敗、検証不一致などのファイル単位エラーは記録し、可能な範囲で残りを処理する。
- 別名保存や、MP4から日時を継承できた壊れたXMLは非阻害警告とする。
- SIGINT / SIGTERMなどの実行中断は通常のファイル失敗として握り潰さず、現在の処理を止めて資源を解放する。
- 宛先ごとの `_photo-manager/import.lock` をOSロックとして使用する。ファイルの存在だけでは実行中と判定しない。
- 自動掃除は、管理領域にあり厳密な命名規則に一致するツール所有の一時ファイルだけを対象にする。

SDカードをejectできるのは、次をすべて満たす場合だけである。

1. dry-runではない。
2. 全対象がコピー・再読込検証済み、または宛先との同一内容を確認済みである。
3. 全対象について有効な台帳レコードがある。
4. 失敗が0件である。非阻害警告だけならejectしてよい。
5. eject直前の宛先確認とマウントポイント確認に成功する。

条件を満たさない場合はejectせず、カメラ内フォーマットを促す成功メッセージも表示しない。ejectはSDカードの消去ではなく、安全な取り外しである。データ消去機能や `--delete` 相当のオプションは実装しない。
